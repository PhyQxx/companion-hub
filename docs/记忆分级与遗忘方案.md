# 记忆分级与遗忘方案（MEM-LIFECYCLE）

日期：2026-11-11。状态：待实施设计，未改变运行规则。本文是 docs/03-记忆与时间线.md 的增量设计；以下天数、权重、容量是 v1 建议默认值，需配置化并经真实验收校准，不是已验证的人类认知模型。

## 1. 产品原则与范围

**能记则记，先保存，再通过实际使用、重要程度和时间管理可见性；自然遗忘只降级，不删除。**

- 每条有来源、可以准确表达的事实、偏好、习惯、关系、经历、目标和约定都应成为记忆候选，不以低重要性拒绝入库。
- 原始聊天继续保存在 message，活动保存在 Timeline；结构化记忆保存可独立理解的事实及来源，不逐字复制全部聊天。寒暄、问题本身、重复文本不生成无意义的新事实，但原始记录依然存在。
- 新记忆默认中级。importance 表示语义重要程度，tier 表示当前记忆强度；二者分开。2026-11-12 起放宽：AI 提取器可依据内容分析建议初始等级（仅可建议 medium/important/core，不得低于中级），用户身份、家人关系等直接陈述的长期核心事实可在入库时即为核心；建议须经入库围栏（置信度/重要性门禁、开关、待决冲突除外）与生命周期审计约束，后续晋降级仍由真实使用驱动。
- 不把模型猜测当成用户事实，不将助手重复说出旧事实计作用户再次确认。未确定事实以不确定语义保存，默认不能作为确定证据；歧义实体待澄清。
- 自然降级不改变真实性、来源、隐私和有效期；低等级仍可能正确，核心也可能过时。
- 沿用现有 owner、隐私 L0–L3、来源删除围栏和用户主动删除合同。自然遗忘不删除；用户明确要求删除仍走删除台账及后代清理，不能用冷存档替代。
- 观察屏幕等偏好不等于授予操作权限。聊天、浏览、屏幕仅在现有授权范围内采集。

## 2. 现有代码差距

当前 memory 已有 importance、pin、status、confidence、valid_from/to、last_accessed_at、access_count 和来源链。retrieval.py 已混合向量、词法、精确事实槽、重要性加权及类型配额；稳定事实不按时间衰减。store.record_access 不修改语义 updated_at，但在检索选中时增加 access_count，不能据此自动升级。

extraction_rules.py 当前 MAX_EXTRACT_INPUT_CHARS=4000、MAX_LLM_CANDIDATES=4；extraction_core.py 异常回退规则后可能返回零候选。自动逐消息提取缺少足够的前文消歧。此前 JSON 血缘反序列化缺陷已单独修复，本地曾出现新旧 Hub 共用队列。分级系统必须以可靠入库和可追溯任务结果为前提。

## 3. 六级强度

| 存储值 | 展示名 | 定位 | 默认召回 |
|---|---|---|---|
| core | 核心 | 长期、反复用于决策或被用户固定的事实 | 优先参与相关检索，不整库常驻提示词 |
| important | 重要 | 近期多次实际用到 | 优先参与相关检索 |
| medium | 中级 | 新记忆的默认起点（AI/管理端可建议更高的初始等级） | 正常参与检索 |
| ordinary | 一般 | 一段时间未使用 | 少量探索及不足时扩展 |
| low | 不重要 | 长期少用；名称不代表事实价值判断 | 强相关/显式回忆时扩展 |
| dormant | 冷存档 | 自然遗忘终点，仍保留原文与索引 | 精确查找、深度回忆与正常检索不足时唤醒 |

不要复用现有 status=archived 表示冷存档。status 继续表达 active/archived/superseded/conflict，tier 是独立维度。普通查询只使用有效、授权、无待决冲突的 active；历史查询允许明确标注旧版本。过期承诺不能因等级高继续执行。

## 4. 入库流程：宽进、可追溯、可恢复

1. 回合提交同事务登记持久提取 Job，绑定消息、用户、来源修订、提取器版本。记录 worker 实例及代码版本，开发和容器使用独立数据库。
2. 当前用户消息全文分块（建议每块3000字符、重叠200），提供最近6条对话作消歧上下文。当前消息是新事实证据；上下文只能辅助理解，不能凭助手推测补用户事实。
3. 多事实分别提取。单批输出上限12条以控制成本，达到上限或覆盖不全必须分批续提，不静默截断；记录块游标、覆盖范围和未完成原因。达到费用上限时保留待处理状态。
4. 结构化校验：主语、事实槽、时间、来源引用、隐私、确定性。每条必须可回指证据；低重要性允许入库，明显幻觉拒绝并登记原因。
5. 去重增加独立来源支持，不重复建事实；变化事实通过明确纠正/时间范围形成版本，含糊矛盾进入冲突。新增事实默认中级，提取器可建议更高的初始等级（见 §6 初始定级）；重复支持不重置成中级、不无限续保鲜。
6. 模型超时/限流按指数退避有限重试（建议30秒、2分钟、10分钟，遵守Retry-After）；凭据/配置错误暂停并提示，禁止盲重试。规则可先保存明确事实，但未覆盖部分仍待补偿。
7. 成功结果必须报告 scanned/created/supported/conflict/rejected/deferred。模型正常返回空与模型失败后规则为空不能同为“成功无记忆”。只有所有块终态才算任务完成。
8. 展示“已记住N条”必须来自提交后的保存回执；仅发起任务显示“记忆整理中”。不要求聊天等待全部提取完成。

案例：到家时间只能由用户说的内容保存；助手估计“8、9点到家”不作为事实。女儿生日应绑定女儿实体，保存年月日，而不是易过时的“两岁半”；省略年份需结合对话年代解析，存在歧义则保留原说法或澄清。

## 5. 什么算一次使用

分开记录以下信号，维护扫描、管理页查看、评测回放一律不算真实使用：

| 事件 | 用途 | 强化分 |
|---|---|---|
| retrieved | 候选被检索选中，诊断可见性 | 0 |
| injected | 实际注入提示词 | 0 |
| used_in_answer | 已提交回答确实引用该事实，并通过来源/内容校验 | 1 |
| used_in_action | 实际行动决策使用该事实，行动达到定义成功条件 | 2 |
| user_reaffirmed | 新用户证据主动重申已有事实 | 2 |
| user_confirmed | 用户明确确认记忆内容正确 | 3 |

v1 优先支持结构化 fact_key、服务端工具参数/计划证据和明确确认。自由文本引用只有可验证时才计分；模型返回 memory_ids 只是候选，必须在已授权注入集合内并有内容对应。难以判断时宁可不升级，不用“注入了”代替使用。

每条记忆同一回合只取最高分；同一天强化上限3分；事件有幂等键，重复刷新、失败重试、模型自问自答不能刷分。用于升级的活跃天数来自有效使用，不来自检索。

## 6. 晋级、降级与唤醒（v1确定性规则）

采用滚动窗口分数而非永久累加，避免早期高频使用永久垄断。

### 晋级

- 中级→重要：最近30天强化分≥6、至少3个独立活跃日。
- 重要→核心：最近90天强化分≥18、至少8个独立活跃日，并已在重要级停留≥14天。
- 每个事件最多晋一级；低置信、待决冲突、失效来源不得自动晋升。
- 用户可以显式设等级或“永远记住”：先按中级完成入库，再同事务记录用户固定事件及最终等级，保留“新建中级”的审计。固定等级覆盖自动变化，可解锁。
- 一般/不重要/冷存档经实际有效使用，直接唤醒到中级，开始新的保鲜期；旧累计数据不允许同回合直接冲到核心。

### 初始定级（2026-11-12 新增，MEM-LIFE-02C）

- 新记忆默认中级；AI 提取器可在候选中建议初始等级 tier（仅 medium/important/core，不得低于中级），管理端手动创建可显式传 tier。
- 围栏在入库处强制执行：AI 建议的 core 需置信度与重要性均≥0.8，important 需≥0.6，未提供置信度视为不达标；非法值、更低等级建议、待决冲突记忆一律落回中级。开关 `ARIA_MEMORY_AI_INITIAL_TIER`（默认开，置 0 回退为全部中级）。
- 管理端显式定级只做合法值钳制，不受置信度门禁约束（对应“用户显式设等级”流程）。
- 初始等级不是固定：仅因被模型判为高重要不豁免降级；保鲜期与降级按新等级的规则执行（核心180天），用户可另行固定。
- 非 medium 的初始定级与记忆同事务写 `memory_lifecycle_event`（reason=ai_initial/manual），等级历史可回溯。

### 降级

新记忆中级保鲜30天。每日定时计算，使用 max(创建时间、最后有效使用、最后等级变化时间) 为本级等待起点：

| 当前级别 | 无有效使用基础天数 | 下一等级 |
|---|---:|---|
| 核心 | 180 | 重要 |
| 重要 | 90 | 中级 |
| 中级 | 30 | 一般 |
| 一般 | 60 | 不重要 |
| 不重要 | 180 | 冷存档 |

等待天数乘重要性系数：importance<0.4 为1倍，0.4≤importance<0.8 为2倍，≥0.8 为4倍。分数为空迁移为0.5。因此默认0.5的新中级记忆60天未有效使用后才降一般。重要程度降低遗忘速度，但不会自动升级。

- 每轮最多降一级；调度停机补跑不一次降到底；固定记忆跳过。
- 用户要求保留的关键事实可固定等级；仅因被模型判为高重要，不永久免降级。
- 使用事件与降级通过行锁/乐观版本在同事务裁决，有新使用就重新计算。按user/day/memory/policy_version幂等。
- 周年事实另有 next_relevant_at 时间触发召回，例如生日前窗口；提前进入检索不计使用，真实帮助后才强化。若没有日历功能，也能通过精确询问从任一级取回生日。

## 7. 按等级检索，但不能形成“低级永远找不到”

顺序为：授权/来源/有效期→事实匹配及相关性门槛→等级优先和多样性→提示词预算。等级不制造相关性，核心无关事实不能挤掉低级精确答案。

- 第一阶段：核心/重要/中级向量+词法混合召回；同时执行全等级实体+fact_key精确召回，包括冷存档。精确事实冲突应澄清，不按等级武断选胜者。
- 第二阶段：高等级证据不足，或用户问历史/“以前提过”，扩展一般与不重要，再检索冷存档。即使第一阶段足够，也保留约20%候选探索名额给低等级强相关记录，前提是过相关性门槛。
- v1候选预算示例：正常候选64，扩展追加64，总128；最终最多8条/2000 tokens（取更严格者），长事实摘要仍保留来源链接。超预算可续查，不在同一轮无界扫描全库。
- 非精确候选排序建议：0.70×相关性 + 0.15×等级分 + 0.10×importance + 0.05×近期有效使用。等级分依次1/0.8/0.6/0.4/0.2/0；未使用记忆的近期使用分为0。pin表示固定强度，不绕过证据门槛。
- 精确匹配另一路优先合并；相关性用现有词法/向量与grounded策略，权重需离线校准，不把向量值当事实置信度。
- 按用户、主体、类型控制重复，不能返回8条同一作息的近重复。核心只形成很小的相关摘要，不整库注入每个回合。
- v1冷存档与热记忆使用同一数据库和向量能力，通过tier过滤；不先做物理搬迁以免漏查。达到实际容量瓶颈后再引入冷索引，保留可重建与显式深搜接口。

## 8. 数据与接口

### memory 增量字段

- tier（默认medium）、tier_changed_at、tier_locked（默认false）。
- last_used_at、use_count（有效回合数）、last_reaffirmed_at。
- next_decay_at、lifecycle_version（并发控制）、lifecycle_policy_version。
- 可选 next_relevant_at（周期事实再激活）；沿用 importance/confidence/status/来源/version。

### 新表

- memory_usage_event：owner_id、memory_id、turn/run_id、event_kind、points、occurred_at、evidence_ref、dedupe_key、policy_version；唯一键防重复，按用户及时间索引。不重复保存敏感全文。
- memory_usage_daily：按owner/memory/date聚合分数及是否活跃，支撑30/90天窗口。事件可按运维策略压缩为日汇总（例如180天），这不删除记忆，且总数/窗口计算结果应一致。
- memory_lifecycle_event：旧/新等级、原因码、触发来源、策略版本、时间。允许解释“为何降级”；不提供一键恢复已删除来源。
- 提取结果优先复用Job和步骤表，补充分块游标、覆盖计数、结构化失败阶段与worker版本，而非再建第二套任务系统。

### API/UI

沿用现有记忆端点扩展返回tier、last_used_at、next_decay_at、use_count、固定状态和变更理由；按实际路由规范定稿，不假定以下路径已存在：

- PATCH /memories/{id}/lifecycle：手动等级、固定/解锁，要求expected_version。
- GET /memories/{id}/lifecycle-events：分页变更记录。
- POST /memories/search：normal/deep/history模式，返回触发了哪些层和来源依据。
- 记忆列表显示等级标签，支持全部/热记忆/冷存档、主体、时间、状态筛选；默认按最近新增可见，避免新记录藏在重要性排序后。
- 聊天展示保存回执；管理员可看提取任务、失败阶段、worker版本和重试入口。明确“冷存档”和“删除”不同按钮。

## 9. 架构、事务和运行治理

领域层实现纯 MemoryLifecyclePolicy 与 MemoryLifecycleService；仓储端口扩展按等级检索和幂等使用登记，SQLAlchemy逻辑留在memory/persistence。不让chat直接操纵等级。

回答提交后登记有效使用；工具行动按真实终态登记；事务提交后才对前端发送保存/等级变化事件。升降级使用独立lifecycle_version，不修改语义updated_at，避免再次让来源快照失效。语义更正、来源支持变更仍沿用现有修订保护。

每日维护Job分用户、分页、可恢复处理next_decay_at索引，不全表常驻扫描；过期任务重复执行不重复降级。所有查询、索引和唯一键必须考虑owner隔离。冷存档同样受删除台账、隐私与备份恢复围栏约束。

运行隔离优先：IDE与Docker不能共用验收数据库；worker上报代码/策略版本并保留领取者审计。灰度期间不兼容worker不得领新版任务；停止旧worker后再启用策略。

## 10. 迁移、灰度与回退

1. 仅增量DDL，旧数据tier=medium、tier_changed_at=迁移时间、开启保鲜期，避免历史时间造成上线立即降级。
2. 旧access_count保留为历史检索统计，不转换为有效use_count，不凭它升级；旧pin迁移为固定中级，显式人工调整优先。
3. status/conflict/来源链不改；superseded等不能因迁移重新激活。
4. 开关分层：collect_usage、tiered_retrieval、auto_promotion、auto_decay，先记录后影子计算，再启用分层检索，再晋级，最后降级。
5. 回退先关升降级/分层检索，保留新增字段和审计，恢复旧检索策略；不删表、不重置内容、不恢复来源已删除记录。不自动降级到不认识新字段的二进制。
6. 灰度观察至少一个完整采集周期，遗忘时间行为用模拟时钟覆盖；不必等180天才能验证边界。

## 11. 验收与监控

- 入库：合成家庭/作息/生日样例逐事实核对；超过4条事实、超过4000字符、跨句指代、日期归属、模型失败/空输出、重复和冲突均覆盖。真实模型验收单独记录，不拿mock通过率替代。
- 生命周期：新建中级、3独立日晋级、同日刷调用不晋级、90天窗口过期、每级降级边界、重要性延缓、锁定、唤醒、并发和重复Job、停机补跑。
- 检索：冷存档精确命中、无关核心不挤掉相关低级、低级探索、高等级不足扩展、失效/私密/他人/删除来源任何等级都不泄漏。
- 可靠性：真实SQL JSON往返、消息提交→队列→提取→memory→新会话召回的全链路；双worker同版本、混合版本阻断、崩溃/重启/幂等。
- 建议发布目标（待实测）：明确事实标注集提取召回≥95%，正确率≥98%；精确事实检索命中≥99%；取消/失败必须有原因码，模拟回放重复写入为0。未达标应报告样本与原因，不静默放宽。
- 性能目标待基线：在目标机器按每用户1万/10万/100万条数据测热/深搜p50/p95、SQL次数、索引大小、写放大和tokens，不先承诺未经测量的毫秒数。
- 仪表盘：提取覆盖与积压、created/supported/empty/error、各等级数量及迁移率、实际使用/注入比例、冷存档唤醒命中、冲突/纠错率、检索延迟及token成本。数量更多不等于记忆质量更高。
