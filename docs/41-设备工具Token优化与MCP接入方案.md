# 设备工具 Token 优化与 MCP 接入方案

日期：2026-09-08  
状态：A/B 与通用 MCP-C0 已实现（2026-09-08）；C1/D 等有明确外部 MCP 目标后启动。  
适用范围：Aria Companion Hub 的 HA 设备工具、聊天提示词及后续 MCP 扩展。

## 1. 结论与实施顺序

先移除聊天提示词中的全量设备动作明细，增加本地设备检索，继续使用现有 HA REST/WebSocket 链路。随后把设备访问封装为稳定适配器接口，再按实际外部服务需求引入 MCP 客户端。

MCP 是工具发现和调用协议，本身不会减少模型输入。节省 Token 的关键是控制交给模型的工具定义、设备候选和调用结果。设备目录和 MCP 工具目录可以缓存在应用内，不必全部写入模型上下文。

实施分为四批：

1. A：建立基线，合并重复能力描述，提供回退开关。
2. B：按需检索设备，移除全量明细，完成会话指代与回归验收。
3. C：增加 MCP 客户端适配器，先试点一个只读外部工具。
4. D：根据需要接入 MCP 写工具、评估 HA 替换，或另建 Aria MCP Server。

## 2. 当前代码事实

| 位置 | 当前行为 | 优化关注点 |
|---|---|---|
| `server/app/chat/service.py` | 每轮获取 `available_actions(user_id)`，通过 `render_reality_grounding` 写入 system message | 普通聊天路径未按当前问题筛选设备；存在特定意图例外，实施时保留其行为 |
| `server/app/chat/capabilities.py` | 将传入的每个能力逐行渲染为 ID、名称、说明 | 同一设备多个动作重复携带名称和说明 |
| `server/app/home_assistant/manager.py` | 枚举已配置、允许读取、非 L3 且状态可用的实体；输出状态、历史和各控制动作 | 是可用实体能力集合，不等于 HA 全部实体；当前实现忽略传入的 user_id |
| `server/app/home_assistant/bridge.py` | `resolve` 对实体 ID、名称、别名做去首尾空格及忽略大小写后的精确匹配 | 本地执行，不消耗模型 Token；不支持房间或模糊检索 |
| `server/app/home_assistant/tools.py` | 提供状态、历史、控制工具，并检查隐私、动作权限、参数和确认条件 | 保留执行检查，增加检索入口与明确的失败结果 |
| `server/app/tools/registry.py` | 注册工具并生成模型工具定义 | 后续 MCP 适配器复用入口 |
| `server/app/config/models.py` | 实体有名称、别名、授权动作等配置 | 房间检索需要补充目录元数据；配置已有名称/别名唯一性校验 |

HA 当前通过 `/api/states` 读取状态，通过 `/api/services/{domain}/{service}` 控制设备，通过 `/api/websocket` 订阅状态变化。MCP 不在现有控制链中。

## 3. 第一阶段：当前可实施方案

### 3.1 提示词改造

将现实能力边界拆成两部分：

- 保留现有人设及现实执行约束，不因本次优化改写伴侣角色行为。
- 设备部分只写能力类别、在线概况和使用规则，不逐设备列出动作。

建议设备部分文案：

> 当前可通过工具查询和控制已授权的家庭设备。设备名称、可用性及支持动作以工具返回为准。名称明确时可以直接调用设备工具；无法匹配时先检索，存在歧义时询问用户。不得编造具体设备，不得在工具确认成功前声称操作完成。提出涉及具体设备的主动建议前，应先确认该设备及相应能力可用。

HA 未连接时使用明确的不可用概述。其他设备类别保持各自的可用性判断。后台完整能力集合仍可用于权限、调度和工具挂载，不因为精简模型文本而删除。

批次 A 可先将每台设备的多个动作压成一行，便于快速验证。它只是过渡模式，最终默认采用按需检索。

### 3.2 本地设备目录

新增 `DeviceDirectory`（建议文件 `server/app/home_assistant/directory.py`），从现有授权配置、HA 实体/设备/区域元数据构建索引。

目录字段：实体 ID、显示名称、别名、HA domain、房间/区域、允许动作、隐私级别、状态可用性。品牌与型号仅在元数据可靠时纳入，不从名称猜测后作为确定事实。

目录留在应用内存；配置发布、HA 重连或元数据刷新时重建。状态变化更新可用性。查询和执行时仍检查当前权限，不能把索引中的旧授权当作执行许可。

房间来源优先使用 HA 区域信息，允许后台覆盖；没有区域信息时返回 null，并允许按名称检索。按实际持久化结构决定是否需要配置升级或数据库迁移。

当前 HA provider 忽略 user_id：不能把它描述为已有按用户隔离。若项目仍使用全局家庭授权，保持并明确该范围；对多用户或对外 MCP 开放前，必须增加用户/家庭作用域，并使其参与查询过滤和缓存键。

### 3.3 新增 search_devices 工具

建议参数：

```json
{
  "query": "小米台灯",
  "room": "卧室",
  "domain": "light",
  "action": "turn_on",
  "limit": 5,
  "cursor": null
}
```

字段均可选；limit 默认 5、最大 5。无过滤条件时返回第一页授权设备，用于浏览；cursor 使用不透明游标。room/domain/action 是过滤条件，query 用于名称、别名及可信元数据检索。

建议返回：

```json
{
  "devices": [
    {
      "entity_id": "light.bedroom",
      "name": "卧室台灯",
      "room": "卧室",
      "available": true,
      "actions": ["turn_on", "turn_off", "set_brightness"],
      "confirmation_required_actions": [],
      "match_kind": "alias_exact"
    }
  ],
  "has_more": false,
  "next_cursor": null
}
```

以上为示例数据。默认不返回完整 HA attributes、原始注册表、凭据或不相关动作说明。读取授权和当前隐私级别过滤必须发生在排序、计数和分页之前，避免通过候选泄露未授权设备。

排序建议：实体 ID/名称/别名精确命中优先，其次房间和类型约束下的关键词匹配，再做轻量文本相似度排序。第一版不引入向量库或额外模型。相似度只决定候选顺序，不产生执行授权。

### 3.4 查询与控制流程

1. 名称明确时，模型直接调用现有 `home_control` 或查询工具。
2. 后端精确匹配唯一实体后，检查当前授权、隐私、可用动作、参数和确认条件。
3. 精确匹配失败，返回 `ha_entity_not_found` 及建议调用 `search_devices` 的结构化提示。
4. 多个匹配返回 `ha_target_ambiguous`；模型查询候选或询问用户，不自动选择第一项。
5. 检索结果明确符合用户指定条件时，使用实体 ID 调用工具。仅有弱相似候选或条件不一致时仍需澄清，即使只返回一个候选。
6. 执行前重新校验，执行后沿用已有状态验证链路；结果不确定时报告未确认完成。

建议每轮最多两次设备检索；仍无法确定则询问用户，避免模型循环搜索。分页浏览可以进入下一用户回合。

### 3.5 会话设备指代

建议新增会话级 `RecentDeviceReference`：entity_id、显示名称、来源 turn_id、确定方式、更新时间和授权作用域。只记录用户明确选定或成功精确匹配的设备，不把全部搜索候选保存成当前对象。

默认保留最近 3 个已完成用户回合且不超过 10 分钟（可配置的初始值）。只有一个明确的近期对象时，向模型附带一行引用信息；多个对象或切换话题后无法判断时询问。使用引用时重新校验权限。

设备引用仅解决“它是哪台设备”，不能作为用户对某个动作的确认。确认仍绑定实际设备、动作及参数，复用项目现有确认机制并检查各路径是否一致。

### 3.6 工具挂载与结果预算

第一版保留少量通用家庭工具定义：检索、状态、历史、控制；根据连接状态和配置决定是否可用。不要把每个设备或动作注册成单独的模型工具，也不要仅靠关键词隐藏工具，导致口语表达无法调用。

历史查询限制条数和字段，优先摘要；搜索最多 5 项；工具输出尽量结构化。工具往返产生的消息也计入本轮 Token 统计。应用本地目录缓存不会自动减少已写入提示词的 Token。

### 3.7 建议改动清单

| 文件/模块 | 改动 |
|---|---|
| `chat/service.py` | 用简短设备概述替代设备明细；挂载搜索工具；注入有限近期引用 |
| `chat/capabilities.py` | 区分内部完整能力和模型可见摘要；保留现实边界 |
| `home_assistant/manager.py` | 暴露目录查询入口，复用可用性与授权配置 |
| 新增 `home_assistant/directory.py` | 精确索引、筛选、排序、分页与更新 |
| `home_assistant/tools.py` | 新增搜索工具、错误指引和精简返回；保留执行门禁 |
| `config/models.py` 与后台实体页 | 必要时增加区域覆盖与别名维护字段 |
| `main.py` / 工具注册位置 | 注册新工具及目录依赖 |
| `server/tests/` | 新增真实行为回归，覆盖搜索、权限与提示词体积 |

具体注册位置与确认接口在实现时重新核对；当前工作区存在其他进行中的修改，不应覆盖它们。

## 4. 第二阶段：引入 MCP

### 4.1 两种方向分别实施

- Aria 作为 MCP 客户端：调用外部 MCP Server，扩展设备或其他外部服务。
- Aria 作为 MCP Server：把 Aria 的受控工具提供给其他 AI 应用。

本阶段优先第一种。第二种只有在出现对外复用需求时实施。

### 4.2 统一接口与适配器

```text
聊天模型
   ↓ 统一工具接口
参数校验 / 身份与隐私 / 授权 / 确认 / 审计
   ├─ HA 适配器 → HA REST / WebSocket
   └─ MCP 适配器 → 外部 MCP Server → 目标系统
```

保持 `search_devices`、`home_get_state`、`home_get_history`、`home_control` 对模型的接口稳定。MCP 服务的工具名称和数据结构由适配器转换，不要求模型了解不同供应商细节。

建议新增 `server/app/integrations/mcp/`，包括连接管理、工具目录、schema 映射、调用适配和结果裁剪。SDK 版本和传输类型在实施时按目标服务及当时官方文档确定。

### 4.3 MCP 工具发现与按需加载

1. 建立连接并协商服务能力，调用 `tools/list` 获取目录。
2. 目录缓存在应用侧；服务声明支持目录变化通知时响应变化，否则按需或定期刷新。
3. 只有配置允许的工具进入内部注册表，保留服务命名空间避免名称冲突。
4. 家庭功能仍向模型暴露稳定的少量通用工具；目录不直接全量注入。
5. 跨领域工具增多时再增加工具检索入口，按当前任务加载定义。动态加载必须接入模型调用循环，不能只注册检索工具却不把检索到的定义提供给后续请求。
6. 调用通过 `tools/call` 执行，结果转换为现有 `ToolResult` 并裁剪字段、条数和体积。

工具发现是应用行为；模型看到什么仍由 Aria 控制。更换协议后保留原全量提示词，不会实现本方案的 Token 目标。

### 4.4 连接与执行约束

建议配置包含：server_id、enabled、transport、endpoint 或受信任启动命令、凭据引用、允许工具列表、超时、工具目录缓存时长。凭据通过现有 secret 通道管理，不进入模型上下文。

读操作可对短暂连接失败有限重试。写操作超时后先验证实际状态，不能自动重复调用或切换 HA 直连重发，防止 toggle 等动作执行两次。主备切换应发生在确定尚未发送动作时，或由后续明确的新请求触发。

外部返回文本仅作为工具数据，不能覆盖 Aria 的系统规则和授权范围。远端工具的描述或注解不能取代项目自己的写操作分类和确认判断。

### 4.5 试点与 HA 替换条件

先接入一个有实际需求的只读 MCP 工具，验收连接、发现、映射、隐私过滤、超时与 Token 预算，再接入写工具。

HA MCP 是否替换直连需逐项核对，不能假定与现有 API 等价：

| 能力 | 必须验证 |
|---|---|
| 设备查询 | 能否检索并稳定映射 entity_id；能否限制授权范围 |
| 当前状态 | 字段、时效和不可用状态是否足够 |
| 历史与日志 | 是否提供项目现有历史/Logbook 需求 |
| 控制动作 | 亮度、温度、媒体和音量等动作及参数是否齐全 |
| 状态订阅 | 是否支持主动感知需求；缺失时继续保留 HA WebSocket |
| 执行结果 | 能否验证成功、失败和不确定结果 |

允许混合模式，例如 MCP 提供额外能力，HA WebSocket 继续承载实时状态。无需为统一协议而移除必要链路。

### 4.6 可选：Aria MCP Server

在需要其他 AI 客户端复用 Aria 时，暴露上述稳定工具接口。入口完成调用方认证与用户/家庭作用域映射，复用授权、确认、审计和执行层，不能直接旁路调用 HA。

需要确认的动作返回待确认结果；不可把外部调用方传入的简单 `confirmed: true` 当成已获用户确认。具体确认票据或交互方案单独设计，并绑定主体、目标、动作、参数、有效期及一次性消费。

## 5. 验收与观测

### 5.1 Token 和耗时基线

固定模型、配置和对话样本，对比全量、合并、按需三种模式。设备规模使用 10、50、200 个模拟授权实体，每个场景记录：

- 模型输入与输出 Token；每轮所有模型调用合计。
- 工具定义、设备上下文、工具结果的独立体积；无法准确分拆 Token 时明确标记为估算。
- 工具往返数、总耗时和 P50/P95。
- 匹配成功、澄清、误控和不确定执行结果数量。
- 若供应商返回缓存用量，分别记录缓存输入与非缓存输入；不把缓存折扣当作提示词变短。

硬性目标：普通闲聊提示词不含逐设备明细；增加设备数量不再线性扩大设备部分常驻输入；无越权和误控。节省比例与延迟变化以实测报告为准。

### 5.2 必测行为

| 场景 | 预期 |
|---|---|
| 普通闲聊 | 不携带全量设备清单，不额外搜索 |
| 名称/别名精确命中 | 不强制增加搜索往返 |
| 口语称呼或房间+类型 | 返回少量相关候选 |
| 两个候选均合理 | 澄清，不选择第一项执行 |
| 不存在的设备 | 明确未找到，不伪造成功 |
| “把它关掉” | 仅复用明确且未过期引用 |
| 授权撤销或隐私切换 | 搜索不泄露，执行重新拒绝 |
| HA 离线 | 提示不可用，不使用旧清单承诺操作 |
| 空调等确认动作 | 保持既有确认要求，参数变化后重新核对 |
| 全设备浏览 | 支持概览和分页，不截断后假称完整 |
| 主动建议 | 具体设备能力有查询依据 |
| MCP 写调用超时 | 不自动重发，验证并报告实际或不确定结果 |

## 6. 发布和回退

建议提供设备上下文模式开关：`full`、`compact`、`on_demand`，名称为设计建议。先使用回放样本验证，再将 `on_demand` 设为默认；保留短期回退。回退只改变提示词策略，不改变权限和确认检查。

MCP 使用独立配置开关，默认关闭。启用某个设备适配器时避免重复注册同名工具。回退前识别未完成写操作，禁止因切换后端而重复执行。

批次 A/B 验收后即可结束 Token 优化任务；C/D 按外部集成需求启动，不作为前阶段交付前提。

本文代码事实来自 2026-09-08 工作区检查。A/B 实施后的实际落点为：

- `device_context_mode` 支持 `full` / `compact` / `on_demand`，默认为 `on_demand`；普通对话不再常驻逐设备动作明细。
- `DeviceDirectory` 和 `search_devices` 已接入，支持名称/别名、房间、domain、动作、隐私过滤、可用性与游标分页，每页最多 5 项。
- 单一明确设备的近期指代会在同会话内短期复用，超过 3 轮或 10 分钟即过期；每轮仍根据当前授权能力重新校验。
- 未找到或歧义结果会建议调用 `search_devices`；原有执行权限、确认和审计闸门保留。
- 200 个授权实体的回归证明 `on_demand` 设备上下文不包含全量实体 ID。
