### 1. 背景与问题

当前大模型与用户的交互以**被动响应**为主：用户发消息 → 中枢组装上下文 → 模型生成回复。这种模式在纯文字/语音聊天中已经验证成熟（P5 文字稳定性、P6 Batch A 语音闭环），但存在以下天花板：

1. **模型看不到用户的真实环境**：用户说"帮我看看这段代码"，模型只能依赖文字描述，无法直接观察屏幕；用户说"手机弹了个通知"，模型无法读取通知内容。
2. **模型感知不到物理世界状态**：用户问"现在室温多少"，模型只能回答"我没有接入传感器"；用户说"我今天走了多少步"，模型无法读取穿戴设备数据。
3. **模型无法主动发起有意义交互**：当前 proactive 路径仅有基于时间的定时触发，缺乏基于环境变化的**事件驱动**触发能力（如检测到用户久坐提醒活动、心率异常提醒休息）。

这些问题不能靠"把更多信息塞进 Prompt"解决。必须让模型具备**调用外部工具获取信息**的能力，并在合适场景下**主动发起工具调用**。

本设计基于项目已有架构进行扩展，核心复用：

- `AdapterCapabilities` / `AdapterManifest`（14 文档）：能力声明与协商
- `RuntimeCapabilityProvider` / `RuntimeActionCapability`（`app/chat/capabilities.py`）：运行时现实能力边界
- `CapabilityModelService`（`app/model_capabilities.py`）：非文本模型能力路由
- `EgressGuard` / `PrivacyLevel`（12 文档、16 文档）：隐私分级与出站授权
- `EphemeralSignal` / `InputEnvelope`（14 文档）：信号与事件输入管道

### 2. 设计目标

#### 2.1 必须实现

1. 大模型能够通过标准 **Function Calling / Tool Use** 调用外部工具获取信息（屏幕截图、传感器读数、位置、剪贴板等）。
2. 工具调用结果必须能**回注模型上下文**，形成"调用 → 获取 → 再生成"的闭环。
3. 工具注册必须与现有 `Adapter` 体系兼容：新增设备能力只需实现 Adapter，不修改认知核心。
4. 什么场景调用什么能力不能仅靠模型自由发挥，必须有**结构化约束**（意图识别 + 上下文推断 + 权限检查三层决策）。
5. 主动感知必须可控：用户可关闭/打开具体感知通道，中枢必须记录触发原因和策略版本（不允许自由文本"内心活动"）。
6. 所有涉及用户隐私的能力必须复用现有 L0～L3 分级体系，屏幕、健康数据、剪贴板等**默认 L2 本地处理**。
7. 工具调用失败（设备离线、权限拒绝、超时）必须有降级路径，不影响基础聊天能力。

#### 2.2 非目标

- 不重新发明通用 Agent 框架（如 AutoGPT、LangChain 的复杂规划），本阶段只支持**单轮工具调用 + 结果回注**（Sequential Tool Use）。多轮复杂工具链（如"查天气 → 查路线 → 叫车"）后置到 M3B。
- 不要求所有模型都支持 Function Calling；不支持的模型按纯文字路径降级。
- 本阶段实现跨终端**受控信息获取**：对话终端和执行终端可不同，例如手机发起请求、已配对电脑返回当前网页。
- 不实现通用远程控制，如代替用户点击、输入、付款或在未解锁设备上执行命令。
- 不把工具调用结果持久化为长期记忆（记忆沉淀仍只基于对话文本）。

### 3. 架构总览：三层模型

```
┌─────────────────────────────────────────────────────────────────────┐
│ ① 模型决策层（LLM with Function Calling）                            │
│    ChatService 把可用工具列表注入 CompletionRequest.tools；          │
│    模型自主决策是否调用、调用哪个、传什么参数。                       │
│    支持 Tool Use 的模型：glm-5、Qwen3、GPT-4o 等。                   │
├─────────────────────────────────────────────────────────────────────┤
│ ② 工具编排层（Tool Registry + RuntimeCapabilityProvider）           │
│    工具注册、发现、执行、权限控制、隐私闸门、失败降级。               │
│    复用现有 AdapterRegistry + EgressGuard + PrivacyLevel。          │
├─────────────────────────────────────────────────────────────────────┤
│ ③ 能力执行层（Input Adapter / 设备 SDK / 系统 API）                 │
│    ScreenCaptureAdapter、SensorAdapter、LocationAdapter 等。        │
│    声明 input_parts=["screen_capture", "sensor_reading", ...]。     │
│    runs_local=True，privacy.max_input_level=L2。                    │
└─────────────────────────────────────────────────────────────────────┘
```

#### 3.1 多终端执行模型

对话发生在哪里，不决定工具必须在哪里执行。每台安装 Aria Client 的设备都是一个独立的受控能力端点：

```text
手机 / Web / 其他对话端
            │  “看一下我的电脑网页”
            ▼
Companion Hub
  ├─ Device Registry：所有权、别名、在线状态、能力和授权
  ├─ Target Resolver：将“我的电脑”解析为唯一 device_id
  └─ Command Gateway：签名命令、TTL、幂等键、取消和回执
            │  已鉴权的出站 WebSocket
            ▼
电脑 Aria Desktop Client
  ├─ 屏幕录制权限与本地隐私暂停
  ├─ Screen Adapter：活动窗口 / 指定显示器
  └─ Browser Bridge：当前标签页截图 + 结构化文本
            │
            ▼
临时结果回到原会话 → 本地 Vision / 明示单次云 Vision → Aria 回答
```

当前 `capture_screen` 已实现活动窗口、主显示器与 1～32 范围内的显式显示器编号；Hub 与 Desktop 双端校验目标参数。`active_window` 在通过权限和锁屏门禁后，由 Desktop 读取 macOS 前台应用 PID，从 CoreGraphics 有序窗口列表选取最前方的普通窗口，再按窗口 ID 非交互式截取；原生真机全链仍待验收。Desktop 进一步要求 macOS 未锁屏且存在“5 分钟内仅下一次截图”的本机内存态临时授权：锁屏会撤销授权和 capability，原生执行前再次检查以封住竞态。系统内容选择器仍待实现，必须明确标记为用户交互式能力，不得冒充可无人值守执行的命令。

核心约束：

- Client 主动向 Hub 建立长连接，不在终端开公网入站端口；
- 每台设备有独立凭据，可单独撤销；服务端只向在线、已授权且实时声明对应 capability 的设备下发命令；
- 客户端在执行前仍需检查系统权限、锁屏状态、本地隐私暂停和本次同意策略；
- 命令过期、重放、目标不唯一、设备离线或权限被拒绝时明确失败，不改选其他设备；
- 网页理解优先使用浏览器扩展返回当前页的标题、URL origin、可见文本和截图，比纯屏幕 OCR 更准且更容易脱敏；
- 手机可以发起对电脑的请求。手机截取自身屏幕则受 iOS/Android 系统约束，需要系统级录屏会话或用户手动分享，不承诺静默后台截屏。

### 4. 工具定义层

#### 4.1 ToolDefinition 与现有 LLM 契约的融合

扩展 `CompletionRequest`（`app/llm/contracts.py`）支持 `tools` 参数：

```python
@dataclass(frozen=True, slots=True)
class ToolDefinition:
    type: Literal["function"] = "function"
    function: FunctionDefinition

@dataclass(frozen=True, slots=True)
class FunctionDefinition:
    name: str                # 全局唯一，如 "capture_screen"
    description: str         # 模型靠这个理解何时调用
    parameters: dict         # JSON Schema

@dataclass(frozen=True, slots=True)
class CompletionRequest:
    trace_id: UUID
    messages: list[LLMMessage]
    tools: list[ToolDefinition] | None = None      # ← 新增
    tool_choice: "auto" | "none" | ToolChoice = "auto"  # ← 新增
    privacy_level: PrivacyLevel
    route: LLMRoute
    max_tokens: int
    temperature: float
```

`LLMProvider` 的实现（`app/llm/provider.py`）负责把 `tools` 翻译成各供应商的本地格式：

- **OpenAI 兼容**（含智谱、MiMo、本地 LM Studio）：直接透传 `tools` 数组。
- **不支持 Function Calling 的本地模型**：`tool_choice="none"`，工具列表不注入，降级为纯文字。

#### 4.2 工具与 RuntimeActionCapability 的双向映射

现有 `RuntimeActionCapability`（`app/chat/capabilities.py`）描述的是**动作能力**（如"打开电视"），工具使用描述的是**信息获取能力**（如"查看屏幕"）。两者统一扩展：

```python
@dataclass(frozen=True, slots=True)
class RuntimeActionCapability:
    capability_id: str
    label: str
    description: str
    capability_type: Literal["action", "sensor", "query"] = "action"  # ← 新增
    supports_tool_calling: bool = False                               # ← 新增
    tool_definition: ToolDefinition | None = None                     # ← 新增
```

- **`action`**：输出侧能力（已有），通过 `DeviceCommandPart` 执行，如控制灯光、打开应用。
- **`sensor`**：输入侧能力（新增），通过工具调用获取实时数据，如读取心率、获取屏幕截图。
- **`query`**：查询侧能力（新增），通过工具调用获取外部信息，如查询天气、查询本地文件。

`RuntimeCapabilityProvider.available_actions()` 返回的能力列表中，`supports_tool_calling=True` 的项会被 ChatService 提取为 `ToolDefinition[]` 注入 LLM。

#### 4.3 首批工具定义示例

| 工具名 | 类型 | 描述 | 参数示例 | 隐私级别 |
|-------|------|------|---------|---------|
| `capture_screen` | sensor | 截取指定设备的活动窗口或显示器 | `{ "device_id": "string", "target": "active_window" }` | L1-L2 |
| `inspect_webpage` | sensor | 读取电脑当前标签页的截图与结构化文本 | `{ "device_id": "string" }` | L1-L2 |
| `capture_mobile_screen` | sensor | 请求手机系统级屏幕分享 | `{ "device_id": "string" }` | L2 |
| `read_sensors` | sensor | 读取指定设备的传感器数据 | `{ "device_id": "string", "sensor_types": ["presence"] }` | L2-L3 |
| `get_location` | sensor | 获取当前地理位置 | `{}` | L1 |
| `read_clipboard` | sensor | 读取系统剪贴板文本 | `{}` | L3（每次确认）|
| `query_local_files` | query | 搜索本地文件 | `{ "query": "string", "path": "/Documents" }` | L2 |
| `get_weather` | query | 获取指定城市/区县天气 | `{ "location": "string?" }` | L1 |

### 5. 工具调用闭环流程

#### 5.1 正常流程（单次工具调用）

```
用户发送消息
    │
    ▼
ChatService.start_turn()
    ├── 查询 RuntimeCapabilityProvider → 可用工具列表
    ├── 筛选 supports_tool_calling=True 的项 → ToolDefinition[]
    ├── 组装 CompletionRequest(messages=..., tools=tool_defs)
    │
    ▼
LLMRouter.stream() → 模型返回
    ├── 情况 A：模型直接回复文本 → 正常流式输出，结束
    └── 情况 B：模型返回 tool_calls → 进入工具执行路径
            │
            ▼
    ToolExecutor.execute(tool_call)
            ├── 隐私检查：EgressGuard.authorize()
            ├── 权限检查：用户是否授权该工具
            ├── 解析目标设备并复核实时 capability
            ├── 本机能力：直接执行 Adapter
            ├── 远端能力：Command Gateway 下发有界命令
            │       ├── ScreenCaptureAdapter.capture() → image bytes
            │       ├── BrowserBridge.inspect() → image + structured text
            │       └── SensorAdapter.read() → JSON data
            └── 结果包装为 tool_result 消息
            │
            ▼
    回注模型上下文
            ├── 把 tool_result 追加为 assistant + tool 消息对
            ├── 再次调用 LLMRouter.complete()（或 stream()）
            └── 模型基于工具结果生成最终回复
            │
            ▼
    _commit_turn()：保存最终回复，记录 decision_meta.tool_calls
```

#### 5.2 流式场景下的工具调用

流式回复中模型可能先输出部分思考文本，再输出 `tool_calls`。处理策略：

1. **缓冲区策略**：在检测到 `tool_calls` 标记前，delta 正常流式输出；一旦检测到工具调用意图，暂停前端流，显示"正在查看..."状态。
2. **工具执行期间**：前端显示加载态，不暴露工具参数细节（隐私保护）。
3. **结果回注后**：重新流式输出最终回复。

如果模型同时输出文本片段和 tool_calls（某些模型的行为），文本片段丢弃，以工具执行后的最终回复为准。

#### 5.3 decision_meta 扩展

`decision_meta`（已存在于 `MessageRecord`）扩展工具调用记录：

```json
{
  "schema_version": 2,
  "tool_calls": [
    {
      "call_id": "call_xxx",
      "tool_name": "capture_screen",
      "arguments": { "display_index": 0 },
      "executed_at": "2026-08-20T10:00:00Z",
      "latency_ms": 320,
      "result_summary": "image/jpeg 1920x1080",
      "result_truncated": true
    }
  ]
}
```

> 注意：`arguments` 中若包含敏感参数（如 `device_id`），应做分级脱敏；L3 工具的结果摘要不得进入 L1 云端上下文的持久记录。

### 6. 场景-能力映射：什么时候调用什么

#### 6.1 三层决策机制

模型不能无条件获得所有工具。每次工具调用前必须经过三层检查：

```
┌─────────────────┐     ┌─────────────────┐     ┌─────────────────┐
│ 第一层：意图识别 │ ──→ │ 第二层：上下文推断│ ──→ │ 第三层：权限与隐私 │
│ Intent Detection│     │ Context Inference│     │ Privacy Guard   │
└─────────────────┘     └─────────────────┘     └─────────────────┘
```

**第一层：意图识别（已演进为能力就绪制）**
- v1 早期使用轻量关键词预筛；2026-08-27 起改为**能力就绪制**——设备工具按「在线能力满足（`DEVICE_TOOL_REQUIREMENTS`）+ 隐私/模型/视觉就绪」全量挂载，查询工具按配置开关挂载，何时调用由模型依据工具描述自行判断。
- 关键词表仅保留给确定性 HA 读回退（`_deterministic_home_read_call`）与选择器单测，不再作为工具注入的主路径。
- 模型未调用工具而仅描述动作时，属于提示词/模型行为，非代码缺陷（真机验收时注意话术引导）。

**第二层：上下文推断**
- 用户明确指定“这台电脑”或设备别名 → 只向该设备注入实时可用的屏幕/网页能力。
- 用户通过移动端连接 → 仍可使用其他已配对设备的能力；对话端不等于执行端。
- 检测到用户刚复制内容 → `read_clipboard` 优先级提升。
- 会话历史中有传感器查询 → `read_sensors` 保持可用。

**第三层：权限与隐私检查**
- `EgressGuard.authorize()`：L2 工具禁止在 L1 路由中使用；L3 工具必须显式用户确认。
- 首次使用敏感工具（屏幕、剪贴板、摄像头）→ 弹窗请求用户同意，同意记录持久化。
- 用户可在管理后台关闭特定工具通道。

#### 6.2 场景对照表

| 用户场景 | 触发条件 | 注入工具 | 是否需要用户确认 | 降级行为 |
|---------|---------|---------|---------------|---------|
| "帮我看看这段代码" | 视觉意图 + 有已配对电脑 | `capture_screen` + `vision` 分析 | 首次需要 | 请用户上传或描述 |
| "看一下我的电脑网页" | 网页意图 + 目标电脑在线 | `inspect_webpage` | 按设备策略 | 提示设备离线/未授权 |
| "手机弹了个通知" | 移动端会话 + 视觉意图 | `capture_mobile_screen` | 每次（敏感）| 请用户手动输入通知内容 |
| "今天走了多少步" | 健康意图 + 有穿戴设备 | `read_sensors(type="steps")` | 首次需要 | "无法读取，请查看健康 App" |
| "现在外面冷吗" | 天气意图 | `get_location` → 天气 API | 不需要 | 询问用户所在城市 |
| "把我刚复制的东西整理" | 剪贴板意图 | `read_clipboard` | 每次（极敏感）| 请用户粘贴内容 |
| "打开计算器帮我算" | 动作意图 | `launch_app("calculator")` | 不需要 | 纯文字回答计算结果 |
| "这照片里的文字是什么" | 图像 + OCR 意图 | `vision` 直接分析（已有能力）| 不需要 | 请用户输入文字 |
| "提醒我每坐一小时活动" | 主动规则设定 | 不调用工具，写入用户偏好记忆 | 不需要 | — |

### 7. 主动感知机制

#### 7.1 从被动到主动：两种触发模式

当前中枢的 proactive 路径（`02 §3.3`）只有**时间触发**（定时器）。本设计扩展为三种触发：

| 触发类型 | 来源 | 示例 | 实现方式 |
|---------|------|------|---------|
| **时间触发** | 定时器 / 用户设定 | 闹钟、日程提醒 | 已有，`cron` 或 `asyncio` 定时任务 |
| **事件触发** | 传感器 / 设备状态变化 | 心率过高、久坐检测 | 新增，见 7.2 |
| **上下文触发** | 会话状态 / 用户行为模式 | 检测到用户复制了代码 → 主动询问是否需要解释 | 新增，后置到 M3B |

#### 7.2 事件触发：感知循环（Perception Loop）

```
┌──────────────────┐
│ 轻量感知进程      │  ← 独立进程/线程，低功耗运行
│ (Perception Loop)│     与主 Hub 通过 MQTT/Unix Socket 通信
└────────┬─────────┘
         │ 1. 轮询或订阅传感器数据（5~30s 间隔）
         │ 2. 本地阈值判断（不调用大模型）
         │ 3. 满足条件时发送 EphemeralSignal
         ▼
┌──────────────────┐
│ 中枢 InputGateway │  ← 接收 signal，转换为 SemanticEvent
│ (app/ingress/)    │
└────────┬─────────┘
         │
         ▼
┌──────────────────┐
│ 认知核心          │  ← 组装上下文（环境状态 + 记忆 + 用户偏好）
│ (ChatService)     │     调用模型决策：should_respond?
└────────┬─────────┘
         │ 决策为 true → 生成 OutputIntent(proactive)
         │ 决策为 false → 静默，记录原因码
         ▼
┌──────────────────┐
│ OutputGateway     │  ← 仲裁、排队、投递到合适通道
│ (app/output/)     │
└──────────────────┘
```

**关键约束**：
- 感知循环只做**阈值判断**，不调用大模型。大模型只在触发后做"要不要回复、怎么回复"的决策。
- 用户必须能**独立关闭**每个感知通道（如关闭久坐提醒但保留心率告警）。
- 主动消息 `ttl_ms` 沿用现有 8000ms 默认值，过期不补发（`02 §3.8`）。
- 同一类型事件在 5 分钟内不得重复触发（去抖）。

#### 7.3 Adapter 扩展：proactive_reachable

`AdapterCapabilities.delivery.proactive_reachable`（已有字段）标记该 adapter 是否支持主动推送：

```jsonc
{
  "capabilities": {
    "delivery": {
      "proactive_reachable": true   // ← 该 endpoint 可接收主动消息
    },
    "input_parts": ["sensor_reading", "screen_capture"]
  }
}
```

支持主动感知的 Input Adapter 必须实现额外的生命周期方法：

```python
class ProactiveInputAdapter(InputAdapter, Protocol):
    async def subscribe_events(self, callback: Callable[[EphemeralSignal], Awaitable[None]]) -> None: ...
    async def unsubscribe_events(self) -> None: ...
```

### 8. 隐私边界

#### 8.1 工具级隐私分级

| 能力 | 隐私级别 | 处理位置 | 用户确认策略 |
|-----|---------|---------|-----------|
| `capture_screen` | L1-L2 | L1 执行设备本地截图后交给已配置的 GLM Vision；L2 只允许本地 Vision | macOS 屏幕录制授权；隐私暂停可随时关闭 |
| `inspect_webpage` | L1-L2 | L1/L2 会话开放浏览器标签页读取：L1 要求本轮路由模型支持工具调用（云端或本地由路由决定）；L2 保持本地工具模型；L0 公开模式不读取个人设备数据（2026-09-15 放宽，原 L2-only） | 浏览器扩展只读获取当前标签页；首次授权，可改为每次确认 |
| `capture_mobile_screen` | L2 | 本地截图 | 每次确认 |
| `read_sensors`（健康）| L2-L3 | 本地读取，摘要可 L2 | 首次使用弹窗 |
| `get_location` | L1 | 可调用云端天气/地图 API | 不需要 |
| `read_clipboard` | L3 | 严格本地，不持久化 | 每次确认 |
| `query_local_files` | L2 | 本地搜索 | 首次使用弹窗 |
| `launch_app` | L2 | 本地执行 | 不需要 |

#### 8.2 与现有隐私体系的集成

- `EgressGuard.authorize()` 在工具执行前检查：仅明确声明为 L1 的工具路径可进入云端对话路由；L2 数据仍禁止外发。
- `AdapterPrivacy.max_input_level` 限制 adapter 能处理的数据敏感度；`screen_capture` adapter 必须声明 `max_input_level="L2"`。
- 工具返回的原始数据（如截图原图）只走 `EphemeralSignal` 内存管道，不持久化；只有模型生成的回复文本进入 `InputEnvelope` 持久化。
- 远端 Client 完成上传并收到回执后立即释放原始图像；Hub 只允许当前回合内的短 TTL 缓冲，不写入资产库、工具台账或通用日志。
- 当前用户选择 L1 时，屏幕截图可交给配置的 GLM Vision；选择 L2 时强制使用本地 Vision。两条路径都不持久化原图。
- 涉及 L3 的剪贴板数据：工具结果不得进入任何记忆沉淀流程；`decision_meta` 中只记录"使用了剪贴板"而不记录内容摘要。

### 10. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|-----|------|---------|
| 模型滥用工具（如每轮都截屏）| 性能、隐私 | 三层决策机制限制；工具调用记录可观测；用户可关闭 |
| 工具执行慢（截图 500ms+）| 聊天卡顿 | 工具执行异步化；超时 3s 降级；加载态提示 |
| 传感器数据不准确 | 主动感知误报 | 阈值去抖（5min 冷却）；用户可手动关闭通道 |
| 屏幕内容敏感（密码、隐私页面）| 隐私泄露 | L2 处理不上云；首次使用明确告知；截图后仅用于当前轮次不保存 |
| 设备别名冲突或选错终端 | 读取错误屏幕 | 唯一候选才自动选择；多候选必须询问；结果标记设备名 |
| 命令重放或设备凭据泄漏 | 未授权采集 | 每设备独立凭据、短 TTL、幂等键、签名回执、可单独撤销 |
| 本地 Vision 模型未安装 | 截图无法分析 | 降级为"已截图但无法分析，请描述内容" |
| 供应商 Function Calling 格式差异大 | 接入成本高 | `LLMProvider` 层做格式翻译；不支持的工具列表不注入 |

2. `search_nearby`：查找附近医院、药店、充电站、餐厅等 POI；
3. `plan_route`：对已确认起终点计算步行、驾车或公交路线。

“离我最近的医院”不直接信任 POI 搜索顺序：`search_nearby` 先地理编码，再做周边搜索，最后对最近候选进行路网距离复核，返回“按直线/步行/驾车哪种口径最近”和数据时间。

#### 2. 范围

##### 2.1 必须实现

- 支持“济南今天天气”“明天会下雨吗”“璟樾花园附近的医院”“去最近医院怎么走”。
- 工具结果回注 LLM，最终回复与普通文字/语音回合共用同一提交、记忆、Timeline 和取消链。
- 每次回复必须带数据提供方、查询时间和位置解析结果；天气额外带 `report_time`。
- 模糊地名不猜；返回候选并要求用户确认。
- L2/L3 回合默认不调用云端地图/天气，必须切换为 L1 或显式开启单次 L1 出站。
- Key 仅服务端解析，日志、`decision_meta`、前端事件都不出现 Key。

##### 2.2 非目标

- 不自制地图导航引擎，不做车道级导航和实时语音导航。
- 不对“最好的医院”“最适合的科室”做医疗质量承诺；只返回可验证的距离、类型、地址和联系信息。
- 不把精确住址、经纬度或查询轨迹自动沉淀为长期记忆。
- 不在首版同时接入多家地图并做结果融合。

#### 3. 供应商与 API 决策

##### 3.1 首选高德

高德作为大陆地址、POI 和路网的首版唯一供应商，避免 WGS84/GCJ-02 与不同 POI 语义在同一轮内混用。使用：

- [地理/逆地理编码](https://lbs.amap.com/api/webservice/guide/api/georegeo/)：地址、小区名 → GCJ-02 坐标 + adcode；
- [POI 2.0 搜索](https://lbs.amap.com/api/webservice/guide/api-advanced/newpoisearch)：文本、周边和 POI ID 查询；
- [天气查询](https://lbs.amap.com/api/webservice/guide/api/weatherinfo)：adcode → 实况/预报；
- [路径规划 2.0](https://lbs.amap.com/api/webservice/guide/api/newroute)：步行、驾车、公交路线；
- [距离测量](https://lbs.amap.com/api/webservice/guide/api/direction)：候选地点批量距离复核。

配额不在代码内写死；以高德控制台当前“流量分析/配额管理”为准，运行时自己实施更低的并发和速率限制。

##### 3.2 可替换边界

业务层只依赖 `GeoWeatherProvider` 协议。将来可增加彩云天气或其他地图 provider，但不改工具 schema 和 ChatService。不同 provider 的坐标系转换必须封装在 provider 内。

#### 4. 系统架构

```text
用户文字/语音转写
        │
        ▼
ToolIntentFilter
  只在天气/地点/路线意图下暴露相关工具
        │
        ▼
ChatService.start_turn
  CompletionRequest.tools + tool_choice=auto
        │
        ▼
LLMRouter（仅选 supports_tool_calling=true 的端点）
        │
   文本 ─┴─ tool_calls
        │        │
        │        ▼
        │   ToolExecutor
        │     ├─ 隐私/授权/参数校验
        │     ├─ LocationResolver
        │     └─ AmapProvider（固定 HTTPS 域名）
        │        │
        │        ▼
        │   结构化 ToolResult（未信任外部数据）
        │        │
        │        ▼
        │   结果回注 + tools=[] + 第二次模型调用
        │        │
        └───────┴──► 最终流式文字 → 可选 TTS → 提交
```

单轮最多允许**一个模型工具回合**。一个工具内部可做有界的 provider 编排，例如 `search_nearby` 内部的“地理编码 → POI 搜索 → 距离复核”；这不向模型暴露多轮自主规划。

#### 5. 工具契约

##### 5.1 `get_weather`

```json
{
  "name": "get_weather",
  "arguments": {
    "location": "济南市历城区",
    "mode": "current_and_forecast",
    "forecast_days": 2
  }
}
```

参数：

- `location`：1～200 字；可省略，省略时走 §6 的位置解析链。
- `mode`：`current | forecast | current_and_forecast`。
- `forecast_days`：1～4，缺省 2。

结果最小字段：

```json
{
  "ok": true,
  "provider": "amap",
  "fetched_at": "2026-08-21T03:20:00Z",
  "report_time": "2026-08-21 11:00:00",
  "resolved_location": {"name": "济南市历城区", "adcode": "370112"},
  "current": {"weather": "多云", "temperature_c": 29, "humidity_percent": 62, "wind": "南风 2级"},
  "forecast": [{"date": "2026-08-21", "day_weather": "多云", "night_weather": "晴", "low_c": 27, "high_c": 33}],
  "source_url": "https://www.amap.com/"
}
```

空值保留 `null`，不允许模型补齐。“体感温度”等 provider 未返回字段不在首版推算。

##### 5.2 `search_nearby`

```json
{
  "name": "search_nearby",
  "arguments": {
    "origin": "济南市历城区望华南街6756号璟樾花园",
    "keyword": "医院",
    "category": "hospital",
    "radius_m": 5000,
    "limit": 5,
    "rank_by": "walking_distance"
  }
}
```

参数：

- `origin`：地址、POI 名或 `current_location`；缺省时走 §6。
- `keyword`：1～80 字，禁止接收 URL 和原始 provider 参数。
- `category`：`hospital | pharmacy | restaurant | charging_station | supermarket | park | custom`。类别由服务端映射高德 typecode，模型不能传 typecode。
- `radius_m`：500～20,000，缺省 5,000。
- `limit`：1～10，缺省 5。
- `rank_by`：`straight_line | walking_distance | driving_distance`；缺省 `walking_distance`。

执行规则：

1. 地理编码起点，必须拿到唯一坐标、城市和 adcode；
2. 周边搜索取直线最近的最多 10 个候选；
3. `straight_line` 直接排序；`walking_distance` 对 5km 内候选做批量步行距离复核；`driving_distance` 只对前 3 个候选规划驾车路线，并发度不超过 2；
4. 任一路网复核失败则回落直线距离，并设 `distance_basis="straight_line_fallback"`，不得写成“步行最近”。

结果包含 `name/address/poi_id/category/distance_m/duration_s/distance_basis/location/navigation_uri`，以及顶层 `resolved_origin/provider/fetched_at/query_radius_m`。电话、营业时间等仅在 provider 明确返回时显示。

##### 5.3 `plan_route`

```json
{
  "name": "plan_route",
  "arguments": {
    "origin": "璟樾花园",
    "destination": "济南大康民世医院",
    "mode": "walking"
  }
}
```

- `mode`：`walking | driving | transit`。
- 公交需起终点城市信息；跨城或缺少 citycode 时明确失败。
- 首版返回总距离、预计时间、最多 12 条简化步骤和高德导航 URI，不把整条 polyline 回注 LLM。
- 路况会变化，驾车时间必须标记“查询时预估”。

#### 6. 位置解析与隐私

##### 6.1 位置优先级

```text
本轮明确地址/城市
  > 本连接临时位置（TTL 15 分钟）
  > 用户手动设置的默认城市
  > 询问用户，不发起 provider 请求
```

- “济南今天天气”只发送城市/adcode，不发送精确住址。
- “我附近的医院”需要坐标或明确起点。浏览器定位必须由用户手动授权，收到 WGS84 坐标后由 provider 层转换为 GCJ-02。
- 小区名重名时，使用默认城市作为 hint 仍无法唯一确定的，返回 `location_ambiguous` 和最多 3 个候选。

##### 6.2 隐私矩阵

| 数据 | 级别 | 出站 | 持久化 |
|---|---|---|---|
| 城市/区县 | L1 | 允许 | 可作为用户手动设置偏好 |
| 用户在本轮显式输入的地址 | L1 | 本轮允许 | 不自动沉淀 |
| 精确经纬度/当前位置 | L2 原始信号，单次 L1 出站 | 需显式授权 | 仅内存 TTL，不入消息/Timeline/记忆 |
| 查询结果中的公开 POI/天气 | L0/L1 | 允许回注 | 只保存最终回复与脱敏工具摘要 |

`decision_meta.tool_calls[].arguments` 不保存原始地址或坐标，只保存 `location_source=explicit|ephemeral|default_city`、精度等级和参数摘要。精确坐标不得进日志。

#### 7. 配置契约

`HubConfig` 新增：

```yaml
tools:
  enabled: true
  max_tool_rounds: 1
  query:
    weather_enabled: true
    nearby_enabled: true
    route_enabled: true
    default_city: "济南市"
    precise_location_policy: ask_each_time  # ask_each_time | allow_session
  amap:
    enabled: true
    base_url: https://restapi.amap.com
    secret_ref: env:AMAP_WEB_SERVICE_KEY
    timeout_ms: 3500
    max_retries: 1
    max_concurrency: 2
    requests_per_minute: 30
```

规则：

- `tools.enabled=false` 时不向模型注入工具。
- 任意 query 工具启用时，必须有且只有一个启用 provider。
- `base_url` 生产配置必须为 HTTPS 且 host 在内置 allowlist；测试可注入 fake transport，不通过任意 URL 解锁。
- 生产只推荐 `secret_ref`；Admin 不回显已保存 Key。
- 模型端点新增 `supports_tool_calling: bool = false`；保守默认，必须通过真模型 probe 后才启用。

Admin “工具与外部能力”页支持开关、Key 引用、默认城市、隐私策略、限流配置和只读自检。自检使用固定城市编码，不发送用户位置。

#### 8. LLM 与 ChatService 契约改动

##### 8.1 LLM 契约

- `LLMMessage.role` 增加 `tool`，并支持 `tool_call_id/name`。
- `CompletionRequest` 增加 `tools/tool_choice`。
- `CompletionResult` 增加结构化 `tool_calls`，不把 provider 原始对象泄漏到业务层。
- LiteLLM 流式 provider 按 `index` 聚合 `delta.tool_calls[].function.name/arguments`，参数必须在流结束后再 JSON 解析。
- 工具意图请求只在 `supports_tool_calling=true` 端点间 fallback；没有合格端点时返回 `tool_model_unavailable`，不假装普通模型会查。

##### 8.2 单轮执行

1. `ToolIntentFilter` 用确定性关键词/语义规则缩小工具集；无命中时保持现有零工具延迟。
2. 工具意图的第一次模型流必须缓冲，不将工具前文字提前显示或 TTS。
3. 没有 `tool_calls` 时发布缓冲文字；有调用时丢弃工具前自然语言，执行工具。
4. 执行前用 Pydantic 严格校验参数，执行后把 provider 返回转换为内部 schema、限长和标注“外部未信任数据”。POI 名或地址中的提示词不得被解释为指令。
5. 回注 `assistant(tool_calls)` + `tool(result)`，第二次请求强制 `tool_choice=none`，不允许无界循环。
6. 最终文字走现有 `ControlStreamFilter`、记忆一致性、消息提交和 TTS。

文字/语音前端新增安全状态事件：

```json
{"type":"tool.started","tool":"search_nearby","label":"正在查找附近医院…"}
{"type":"tool.finished","tool":"search_nearby","ok":true,"latency_ms":620}
```

前端不展示 Key、精确坐标或原始 arguments。语音回合在工具执行期间不播报模型的半成品，可选播放本地固定提示音，工具结束后才合成最终回复。

#### 9. Provider 客户端与可靠性

`AmapProvider` 使用共享 `httpx.AsyncClient`，只请求编译时固定的 HTTPS path；不接收模型给出的 URL。

| 能力 | 超时 | 重试 | 内存缓存 TTL |
|---|---:|---:|---:|
| 城市/adcode 解析 | 3.5s | 网络错误 1 次 | 24h |
| 精确地址地理编码 | 3.5s | 网络错误 1 次 | 30min，仅进程内 |
| 天气实况 | 3.5s | 网络错误 1 次 | 10min |
| 天气预报 | 3.5s | 网络错误 1 次 | 30min |
| 周边 POI | 3.5s | 网络错误 1 次 | 5min |
| 步行/驾车距离 | 4.5s | 不重试 | 2min |

- 缓存 key 中的精确地址/坐标使用进程内 HMAC，日志只记 hash 前 8 位和精度等级。
- 重试只对 connect/read timeout 和 502/503/504，不对参数、权限、配额错误重试。
- 连续 5 次 provider 级失败后断路 60s；断路期直接返回 `provider_circuit_open`。
- 服务端限制单用户同时 1 个 query tool、全局并发 2、默认 30 请求/分钟；运行限额必须低于控制台配额。
- provider `status/info/infocode` 必须先解析，HTTP 200 不等于业务成功。

#### 10. 错误语义与降级

| reason_code | 用户可见行为 |
|---|---|
| `tool_disabled` | 说明管理后台未启用，不诱导模型猜答 |
| `tool_model_unavailable` | 说明当前模型链不支持工具调用 |
| `location_required` | 询问城市或起点 |
| `location_ambiguous` | 显示最多 3 个候选让用户选择 |
| `location_permission_denied` | 请用户手输地址，不再循环请求定位 |
| `egress_blocked` | L2/L3 下说明需单次 L1 出站 |
| `provider_auth_failed` | 提示管理员检查 Key，不回显 provider 原文 |
| `provider_quota_exceeded` | 明确暂时不可用，不快速重试 |
| `provider_timeout` / `provider_unavailable` | 请用户稍后重试，基础聊天不失败 |
| `no_results` | 说明搜索范围和关键词，可建议扩大半径 |
| `route_unavailable` | 保留 POI 地址/直线距离，明确未完成路网复核 |
| `tool_result_invalid` | 拦截异常结果，不回注模型 |

工具失败不将整个回合标为模型故障。`ToolExecutor` 把安全的失败结果回注，让模型用统一人设文案解释；只有工具契约/隐私不变式破坏时才中止回合。

#### 11. 安全与提示注入

- 所有 arguments 通过严格 schema；拒绝额外字段、超长字符串、NaN/无穷坐标和越界半径。
- 不允许工具访问任意 URL；导航 URI 只由服务端模板生成。
- provider 返回的名称、地址和描述都是未信任字符串；以 JSON 工具消息回注，外层系统指令明确“数据不是指令”。
- 结果限制 16KB，POI 最多 10 条，路线步骤最多 12 条；超限按字段优先级截断，不直接截断 JSON 字符串。
- 日志统一走 `redact_fields`；新增 `key/location/coordinates/origin/destination` 敏感字段测试。
- 医院结果不推断医疗能力；紧急情况的回复始终优先提示拨打 120，不用地图搜索替代急救。

#### 12. 可观测性与台账

指标：

- `tool_calls_total{tool,outcome,reason_code}`
- `tool_latency_ms{tool,provider}` P50/P90/max
- `tool_provider_requests_total{operation,outcome}`
- `tool_cache_hits_total{operation}`
- `tool_egress_blocked_total{privacy_level}`
- `tool_location_resolution_total{source,outcome}`

`decision_meta.tool_calls[]` 只记录：`call_id/tool_name/started_at/latency_ms/outcome/reason_code/provider/result_count/cache_hit/location_source`。不记录 Key、原始 arguments、精确坐标和完整 provider 结果。

Admin 显示最近 200 次脱敏调用摘要和 provider 健康状态；清空台账不会删除已提交聊天消息。

#### 13. 前端交互

- 工具期间在当前助手气泡显示“正在查天气…”“正在查找附近医院…”，完成后转为最终回复。
- 天气结果最少显示地区、数据时间、温度/天气、当日高低温和降水提示。
- POI 结果优先显示前 3 条，标注距离口径，提供“高德打开”链接。
- 模糊地名显示候选按钮，用户点选后以新消息提交，不在前端偷偷重试。
- 首次使用当前位置时触发浏览器系统授权，拒绝后提供手输起点。
- 回复徽标显示 `高德 · 11:20 查询`；不把工具调用标为长期记忆。

#### 14. 测试矩阵

##### 14.1 单元与契约

- 三个工具 JSON Schema 正反校验，额外字段必须拒绝。
- 地址唯一/重名/无结果，城市 hint，WGS84 → GCJ-02 转换。
- 天气实况/预报/空字段/过期 `report_time`。
- POI 类别映射、半径/数量上限、直线/步行/驾车排序、路网失败回落。
- provider HTTP 200 + `status=0`、非 JSON、超时、配额、Key 错误、断路器、缓存、限流。
- Key/地址/坐标的日志脱敏断言。
- provider 返回的 POI 名含提示注入文本时仍只被当数据。

##### 14.2 Chat/LLM 集成

- 普通聊天不注入工具，首 token 基线不回退。
- 天气意图只注入 `get_weather`；附近意图只注入 `search_nearby`；路线意图只注入 `plan_route`。
- 模型返回非法 arguments、不存在工具、多个工具调用：拒绝并返回稳定 reason code。
- 结果回注后第二次调用强制禁用工具，最终文字只引用结构化结果中存在的字段。
- L2/L3 调用被出站闸门拦截，provider fake 调用计数为 0。
- 取消回合会取消 provider HTTP 任务，不提交工具前半成品。
- 文字 WS 与语音 WS 都会收到 `tool.started/finished`；语音只播放最终回复。

##### 14.3 真实验收

- 真实 Key 自检通过，错 Key/限额返回可诊断状态且不泄密。
- “济南今天天气”连续 5 次不会因地名漂移到其他城市；缓存命中时结果显示原 `report_time`。
- “璟樾花园附近最近的医院”能解析济南起点，返回距离口径、查询时间和可打开导航链接；删掉默认城市后同样问法必须先澄清城市。
- 处于 L2 回合时询问天气，明确提示需 L1 出站，不会静默改隐私等级。
- 工具调用 P90：天气 ≤1.5s，附近 POI 直线模式 ≤2.0s，含路网复核 ≤3.5s（在本机网络的 20 次样本上记录，作为产品门槛而非单元测试断言）。

### 38 屏幕感知与主动话题

> 原文：`38-屏幕感知与主动话题设计`（38 - 屏幕感知与主动话题设计）。2026-09-15 按功能并入本文档，内容完整保留、标题降一级。

> 状态：v1 已实现（2026-08-27）
> 相关：[34-大模型工具使用与主动感知设计](./05-工具与感知.md)、[36-Home Assistant集成设计](./06-集成与认知.md)、[37-M3B认知调度闭环设计](./06-集成与认知.md)

#### 1. 功能定位

中枢按配置间隔周期性截取用户桌面设备（Aria Desktop）的各显示器画面，做感知哈希变化检测后交给视觉模型生成结构化摘要：

- **全量沉淀**：每份摘要写入 Timeline（`screen.observed` 事件），可检索"我下午看了什么"；
- **显著升级**：视觉模型判定 `memory_worthy` 的观察进入长期记忆（情景记忆、低重要度）；情景事件按事件追加，不参与稳定事实的相似度冲突裁决，截图层仍通过感知哈希跳过未变化画面；
- **主动话题**：判定 `notable` 的观察构造 `SemanticEvent(kind="screen.observed")` 进入感知管线，经 M3B 认知循环判定后由 ProactiveDeliveryService 投递到 Web 私聊/桌面通知/语音。

本功能是用户对 TASKS「暂缓：持续后台屏幕监控」的**显式推翻**：授权模型采用纯配置开关（Hub 侧 `screen_awareness.enabled`），设备端不再逐次点击授权，但保留三道硬闸门。

#### 2. 数据流

```
ScreenAwarenessLoop (tick, 默认 60s, 15~600s 可配)
  ├─ 读 config.screen_awareness（每 tick 重读，支持热更新）
  ├─ DeviceTargetResolver.resolve(capability="screen.monitor")
  ├─ 每显示器：
  │    gateway.issue(command="screen.monitor", args={target, display_index})
  │    → Desktop(TS) 不消费单次授权，Rust 端仍检查 TCC/锁屏
  │    → 资产 consume-on-read（原图即焚）
  │    → 感知哈希（Pillow 8x8 均值哈希）与上次比较，汉明距离 ≤ 阈值则跳过
  │    → analyze_vision（GLM-4v-flash @ L1）→ JSON {summary, notable, memory_worthy, topic}
  │    → TimelineStore.index_screen_observation（source_type=device, event_type=screen.observed）
  │    → memory_worthy → MemoryCandidate(EPISODIC, SYSTEM_EVENT, screen-v1) → MemoryIngester
  │    └→ notable → SemanticEvent(dedupe_key="screen:{hash}", evidence_ids=[timeline id])
  │         → PerceptionPipeline.submit(stable_for_seconds=10, handler=ProactiveDeliveryService.deliver)
  └─ 连续 3 次失败 → 该显示器冷却 10 分钟（不存在的显示器不空转）
```

#### 3. 隐私与安全边界

1. **原图即焚**：截图走 `EphemeralDeviceAssetStore`（2 分钟 TTL、consume-on-read、进程内存），分析后即消失；持久化的只有文本摘要。
2. **设备端三闸门**：TCC 屏幕录制授权；锁屏时 `screencapture` 前直接拒绝（`screen_locked`）；Desktop「隐私暂停」开关断开设备连接即全线停止。
3. **Hub 侧总开关**：`screen_awareness.enabled=false`（默认）时循环空转不发任何命令；Admin 状态页可见循环健康与各屏状态。
4. **能力交集**：Desktop 在 TCC 已授权且未锁屏且未暂停时声明 `screen.monitor`，还需 Admin 在设备设置里授权 `screen.monitor` 才进入有效能力。
5. **主动输出复用全局门禁**：`screen.observed` 不在 CRITICAL_EVENTS，受安静时段/每日预算约束；反馈降频按 trigger_kind 生效——用户忽略几次后自动安静。
6. **视觉分析固定走 L1**（云端 GLM-4v-flash）；L2 本地视觉不在 v1 范围（没有本地视觉模型时启用本功能即隐含接受截图上云，文档在此明示）。

#### 4. 语义事件契约

- kind：`screen.observed`
- source_kind：`screen`
- dedupe_key：`screen:{16hex 感知哈希}`（同画面跨轮去重；管线另有 300s 窗口）
- evidence_ids：`[TimelineEvent.source_id]`（观察记录可回溯）
- attributes：`message`（话题句）、`display`
- expires_at：5 分钟（过期不补发）

#### 5. 配置（config.screen_awareness）

| 字段 | 默认 | 说明 |
|---|---|---|
| enabled | false | 总开关，默认关闭 |
| interval_seconds | 60 | 15~600 |
| displays | [1] | 显示器编号列表，1=主屏；配置 [1,2,3] 覆盖三屏 |
| analysis_prompt | 内置 | 视觉分析指令前缀 |
| memory_enabled | true | memory_worthy 升级记忆 |
| proactive_enabled | true | notable 进主动管线 |
| unchanged_skip_threshold | 6 | 感知哈希汉明距离阈值（0~64） |

成本参考：60s 间隔 + 变化检测下，专注工作场景每小时通常只有个位数次云视觉调用；纯静态画面接近零调用。

#### 6. Admin

「能力接入 → 屏幕感知」（`/screen-awareness`）：运行状态 Tab（开关/间隔/循环健康/各屏哈希与最近分析/冷却状态/最近错误）与观察记录 Tab（最近 50 条 screen.observed 摘要）。

#### 7. v1 未做

- 原图缩略图留存（即焚）；OCR 全文索引；屏幕内容驱动的对话上下文注入（记忆检索自然带出）；L2 本地视觉路径；语音通道的实时播报节流。

### 42 浏览器观察记录

> 原文：`42-浏览器观察记录设计方案`（42 - 浏览器观察记录设计方案）。2026-09-15 按功能并入本文档，内容完整保留、标题降一级。

> 状态：v1 全量已实现（P1/P2 于 2026-09-08，P3 于 2026-09-10）
> 相关：本档「屏幕感知与主动话题」章节、[43-MCP整体架构与接入实施方案](./06-集成与认知.md)、[31-记忆时间线与历史回溯设计](./03-记忆与时间线.md)

#### 1. 功能定位

补齐浏览器插件（Aria Browser Bridge）与桌面屏幕感知对等的**观察记录**能力：当前插件是纯被动设备，只有助手按需下发 `browser.current_tab.read` / `capture` 时才读取页面，读到的原文走 `EphemeralDeviceAssetStore` 阅后即焚，事后没有任何可回看的档案——管理后台「命令记录」里只有命令级台账，没有内容级摘要。

本方案新增 `browser.observed` 观察事件：中枢周期性读取浏览器当前标签页，经变化检测与 LLM 摘要后写入 Timeline，可选进入长期记忆与主动提醒，并在管理后台提供与「屏幕感知 / 观察记录」对等的两个查看页。

- **全量沉淀**：每份摘要写入 Timeline（`browser.observed`），可检索"我看了哪些网站"；
- **显著升级**：`memory_worthy` 的观察进入长期记忆（情景记忆、低重要度，对齐屏幕感知）；
- **主动话题**：`notable` 的观察构造 `SemanticEvent(kind="browser.observed")` 进入感知管线，经认知循环判定后投递。

#### 2. 架构决策：Hub 拉取，而非插件推送

| | A. Hub 拉取（采用） | B. 插件主动推送 |
|---|---|---|
| 原理 | 服务端循环周期下发 `browser.current_tab.read`，复用现有命令通道 | 插件用 `chrome.alarms` 自行采样，新增 `observation.push` 帧 |
| 插件改动 | **零** | 新帧类型 + MV3 保活 + 设备端脱敏，改动大 |
| 安全模型 | 插件保持纯被动（只响应签名命令），与现有威胁模型一致 | 设备发起内容上行，隐私审面扩大 |
| 与屏幕感知一致性 | 完全同构（`screen.monitor` 也是每 tick 下发命令） | 异构，两套运维心智 |

方案 B 的唯一优势是不产生轮询命令记录，该缺点在 §10 三期用心跳指纹优化解决。

#### 3. 数据流

```
BrowserAwarenessLoop (tick, 默认 60s, 15~600s 可配)
  ├─ 读 config.browser_awareness（每 tick 重读，支持热更新）
  ├─ DeviceTargetResolver.resolve(capability="browser.current_tab.read")
  ├─ gateway.issue(command="browser.current_tab.read", args={})
  │    → 插件回传 BrowserDocument JSON，资产 consume-on-read（原文即焚）
  │    → 隐私闸门：origin 限 http/https、blocked_hosts 精确匹配跳过、正文截断
  │    → 变化检测：sha256(origin + "\n" + title) 前 16 hex，与上次相同则跳过
  │    → LLM 文本摘要（LLMRouter 文本槽位）→ JSON {summary, notable, memory_worthy, topic}
  │    → TimelineStore.index_browser_observation（source_type=device, event_type=browser.observed）
  │    → memory_worthy → MemoryCandidate(EPISODIC, SYSTEM_EVENT, browser-v1) → MemoryIngester
  │    └→ notable → SemanticEvent(dedupe_key="browser:{hash}", salience=0.75, stable 10s)
  │         → PerceptionPipeline.submit → ProactiveDeliveryService.deliver
  └─ 连续 3 次失败 → 冷却 10 分钟（多设备 ambiguous 记 last_error 跳过）
```

#### 8. 已知代价

1. **命令台账噪声**：每 tick 产生一条 `browser.current_tab.read` 记录（60s 间隔、设备在线时约 1440 条/天），与屏幕感知的 `screen.monitor` 完全一致，属既有行为；`idempotency_key` 生成时带 `browser-observe-` 前缀，便于后续在 DevicesView 命令记录页过滤。
2. **轮询成本**：变化检测在读取之后，稳态（页面不变）下仍每 tick 发一次命令；省略方案见 §10。
3. **多浏览器设备**：一期 `target=None`，多设备时 resolver 报 ambiguous → 记 `last_error` 跳过（与屏幕感知对多桌面设备的处理一致）；二期可加 `target_device` 配置。
