## 1. P0-1 前端代码分割 + Element Plus 按需导入

### 问题与证据

- 构建产物单 JS chunk 1.7MB + CSS 471KB；`web/apps/vite.config.ts` 无 `build.rollupOptions.manualChunks`。
- `web/apps/src/main.ts` 全量 `use(ElementPlus)` 并引入全量 CSS，未用按需导入。
- `web/apps/src/router/index.ts` 三个入口（ChatRoot / AdminShell / ModuleWorkspaceView）全部静态导入。
- `ModuleWorkspaceView.vue` 把全部 43 个 admin 视图静态 `import` 进同一 chunk——聊天页用户也要下载整个后台。

### 具体方案

1. **路由懒加载**：`router/index.ts` 中入口组件改为 `component: () => import('../views/ChatRoot.vue')` 形式；ChatRoot 与 AdminShell 自然分成两个 chunk。
2. **admin 视图动态 import map**：`ModuleWorkspaceView.vue` 的视图映射表从静态对象改为 `defineAsyncComponent(() => import(...))` 或 `() => import(...)` 的惰性映射，保留键名不变，43 个视图各自成 chunk（Vite 会自动聚合）。
3. **Element Plus 按需导入**：接入 `unplugin-vue-components` + `unplugin-auto-import`（需确认本机 npm 私服/离线 store 可提供这两个包，见已知网络限制），删除 `main.ts` 的全量 `use(ElementPlus)` 与全量 CSS 引入。
4. **manualChunks 兜底**：对 `element-plus`、`echarts`（如有）等大依赖单独拆 vendor chunk，避免业务改动打爆缓存。
5. **验证**：`pnpm --dir web/apps build` 后用 `vite-bundle-visualizer` 或 `ls -la dist/assets` 对比首包（入口 chunk + 懒加载清单）体积；回归聊天页与 admin 各一个页面手测路由切换与弹窗组件渲染。

### 验收口径

- 入口 chunk（聊天首屏）显著小于当前 1.7MB 单文件；admin 视图按需加载（Network 面板可见切换 Tab 时才拉取对应 chunk）。
- `vue-tsc` typecheck 通过；既有功能手测无白屏/异步组件加载闪烁（必要时给 AsyncComponent 配 loading 占位）。

## 2. P0-2 Dockerfile web 构建层缓存与可复现构建

### 问题与证据

`Dockerfile` 第 4~5 行：

```dockerfile
COPY web ./
RUN pnpm install --no-frozen-lockfile && pnpm -r build
```

- 任何 web 源码改动都会使 `COPY web ./` 缓存失效，重跑全量 `pnpm install`。
- `--no-frozen-lockfile` 意味着构建时可能解析出与 lockfile 不同的依赖树，与 CI 的 frozen-lockfile 纪律矛盾（供应链不可复现）。

### 具体方案

```dockerfile
FROM node:22-bookworm-slim AS web-build
WORKDIR /web
RUN corepack enable
# 先只拷贝依赖清单与 workspace 骨架，install 层可被源码改动复用
COPY pnpm-workspace.yaml ./
COPY web/package.json web/pnpm-lock.yaml ./web/
COPY web/packages/*/package.json ./web/packages/
COPY web/apps/package.json ./web/apps/
RUN pnpm -C web install --frozen-lockfile
# 再拷贝源码并构建
COPY web ./web
RUN pnpm -C web -r build
```

（具体路径以 `pnpm-workspace.yaml` 声明的包为准核对；lockfile 位置以仓库实际为准——根目录或 `web/` 内。）

注意事项：

- 改动后先本地 `docker build` 验证缓存命中：改一个 `.vue` 文件重建，install 层应显示 `CACHED`。
- `--frozen-lockfile` 若因 lockfile 与 package.json 漂移而失败，属暴露既有问题，按错误提示重新 `pnpm install` 更新 lockfile 并单独提交，不要回退到 `--no-frozen-lockfile`。
- pnpm 的 store/挂载细节（如 `node_modules` 符号链接）在多阶段 COPY 中通常无需特殊处理，构建产物只取 `dist`。

### 验收口径

- 改 web 源码重建：`pnpm install` 层命中缓存；改 lockfile 重建：install 重新执行。
- 镜像内应用正常启动，compose 冒烟通过。

## 3. P1-1 后端核心热路径与路由工厂拆分

### 问题与证据

- `server/app/chat/service.py` 3606 行：`start_turn` 574 行（约 :781 起）、`_commit_turn` 300 行（约 :2223 起）、`_run_postcommit` 184 行。已部分拆出 reply.py / postcommit.py，方向正确但主文件仍过重。
- `server/app/api/` 目录约 1.5 万行；`create_admin_config_router` 763 行（admin_config.py:520 附近）、`create_pnkx_router` 747 行（pnkx.py:199 附近）等路由工厂把校验/编排/持久化全写在闭包里，路由层无法单测、逻辑无法复用。
- 另有 `api/voice_ws.py` 2369 行、`api/device_commands.py` 1679 行、`cognition/action_plan.py` `execute_plan` 276 行。

### 具体方案

**不另立专项，挂在架构队列既有批次顺带做**（每批只动一个文件/一条路径，靠相关回归保护）：

1. **chat/service.py（结合 B-01 批次）**：
   - `start_turn` 按阶段提私有方法：参数与身份解析 → 上下文装配 → Run 创建 → 代理循环启动；主方法退化为编排（≤80 行）。
   - `_commit_turn` 把「预算结算 / 持久化 / 事件发布」切为三个协作对象方法。
   - 拆出的纯逻辑优先做成可注入的协作者（沿用现有 harness 端口风格），便于 fixture 单测。
2. **路由工厂下沉（结合 A-01 领域迁移批次）**：
   - 目标形态：路由函数只做「DTO 解析 → 调 service → HTTPException 映射」三件事，闭包捕获的仓库/客户端收敛为模块级 service 实例。
   - 优先级顺序：`admin_config` → `pnkx` → `voice_ws` → `device_commands`；每迁一个文件跑受影响族回归 + mypy + 架构门禁。
3. **禁忌**：不改对外路由路径与响应契约（契约生成校验会拦）；不顺手改行为；迁移中发现的 bug 记录到 TASKS，不在本批修。

### 验收口径

- 每批：受影响族回归通过、mypy/Ruff/架构门禁通过；拆分后文件 ≤1500 行、编排函数 ≤100 行。
- 行为等价：以现有测试 + diff 检查门禁为准，不重写测试断言。

## 4. P1-2 ChatRoot.vue 拆分

### 问题与证据

`web/apps/src/views/ChatRoot.vue` 2137 行、setup 内 33 个 async 函数，同时承担：认证/登录、会话 CRUD 与归档、WebSocket 连接与重连（`connectSocket` 约 :1349，重连退避约 :1379-1388）、消息收发、语音链路、BroadcastChannel 主题同步（约 :1578）、会话导出、勾选模式、全局监听器。

另外：`ModelsView.vue` 1889 行、`SkillsView.vue` 1211 行（含 30s 轮询 timer）；`ChatApi.onUnauthorized` 是模块级单例赋值（约 :1113），多实例挂载会互相覆盖且无解绑时机——拆分时一并处理。

### 具体方案

1. **先抽 composable（行为不变）**，按职责切：
   - `useChatSocket`：连接/重连退避/心跳/收发消息/onUnauthorized 订阅（改为返回 dispose，组件卸载时解绑）；
   - `useVoice`：语音链路状态与控制；
   - `useAuth`：登录态与 SSO 状态探测；
   - `useConversationExport`：导出与归档。
   - composables 放 `web/apps/src/composables/`，状态通过参数/返回值显式传递，不新建全局单例。
2. **再拆模板子组件**：聊天会话列表、消息区、输入区各自成 SFC，props/emits 显式连接；ChatRoot 退化为装配层（目标 ≤500 行）。
3. **ModelsView / SkillsView** 套用同一模式（列表 + 表单抽屉 + 轮询拆开），优先级低于 ChatRoot。
4. **风险控制**：纯机械搬移，不重构逻辑；每拆一个 composable 跑一次 `vue-tsc` + 浏览器手测聊天收发、断线重连、语音、主题切换四条路径。

### 验收口径

- `pnpm --dir web/apps typecheck` 通过；聊天页四条路径手测通过；ChatRoot 行数达标。
- onUnauthorized 在组件卸载后不再被调用（可用 console 断点验证）。

## 5. P2 / P3 清单

### P2-1 启动分层并行

- 证据：`server/app/wiring/registry.py` `start_all()`（:92 起）按 `self.order` 逐个 `await self.start(name)`；`wiring/lifespan.py` 注册约 30 个调度器/循环，多数 `requires=("conversation",)` 互相独立却串行启动。
- 方案：registry 增加「层」概念——同一拓扑深度内无依赖关系的模块用 `asyncio.gather` 并行启动；单个失败仍走现有 `stop_all()` 逆序清理，保持 `critical` 语义不变。停机保持逆序串行。
- 验收：冷启动到可服务状态的耗时对比日志；并行后人为让一个非关键模块抛错，确认清理与 reason_codes 行为不变。

### P2-2 N+1 / 循环内 await

- `server/app/tasks/review_core.py` `collect_items`（约 :50）：7 处循环内 await，且 `list_tasks(limit=200)` 取回后 Python 过滤——把日界/隐私过滤下推到 SQL where，循环改批量查询。
- `server/app/todo/sync.py` `sync_once`（约 :76）：逐条 `await self._client.update(...)`——改 `asyncio.gather` + `Semaphore(5)` 并发，或提供方支持时改批量端点。
- `server/app/runs/store.py` `cancel_work`（约 :197）：3 处循环内逐行 UPDATE——合并为单条批量 UPDATE。
- 验收：各自模块回归通过；review_core 场景下 SQL 日志中查询次数明显下降。

### P2-3 异常吞噬治理

- 证据：全库约 148 处 `except Exception:`（chat/service.py 17 处、observability/selfcheck.py 6 处、safety/service.py 5 处）；`server/app/workflows/drafts.py:629` 附近有裸 continue 静默吞噬。
- 方案：
  1. 约定固化进 ruff：启用 BLE（blind-except）与 TRY 相关规则，先以 warn/白名单方式落地存量清单；
  2. 存量逐个补 `logger.warning("...中文标签...", exc_info=True)` 或结构化 reason_code（日志规范见既有约定：中文标签前置）；
  3. `workflows/drafts.py` 的静默 continue 补日志；
  4. 新代码经 ruff 门禁拦截。
- 验收：ruff 门禁通过；抽查吞噬点在测试中触发时日志可见。

### P2-4 CI 补盲区

- 证据：`.github/workflows/ci.yml` 未覆盖 browser-extension（Makefile 有 `browser-check` 但 CI 未调）与 `integrations/xiaoai_gateway`（独立 npm/Docker 构建，无任何 lint/test）。

- 验收：CI 全绿；故意引入扩展类型错误确认 job 会红。

### P2-5 全量测试并行化

- 证据：`server/tests/` 307 个测试文件、全量约 4479 用例，CI 单 job 串行；pyproject 仅 `-q`。
- 方案：引入 `pytest-xdist`，CI 用 `-n auto`；注意两个已知约束——PG 大规模混跑曾 OOM（分块执行是既有经验），且部分测试可能依赖端口/全局单例，先 `-n 4` 试跑再放开。xdist 下 fixture 隔离问题用 `-p no:randomly` 类排查法定位。
- 验收：分块与并行结果一致（同过同跳）；全量耗时显著下降且无 flaky 新增。

### P2-6 错误 toast 统一封装
