> 目标阶段：M3A 设备能力与主动感知
> 相关真源：[02-功能设计](./00-产品与架构.md)、[12-安全边界同意与陪伴伦理](./07-安全与管理后台.md)、[14-输入输出扩展契约](./01-平台运行时.md)、[34-大模型工具使用与主动感知设计](./05-工具与感知.md)

> 实施进度：HA-0/HA-2 已落地，包括 REST/WebSocket 状态同步、实体白名单、字段脱敏、`home_get_state`、`home_get_history`、`home_control`、动作白名单、服务端确认门禁、脱敏调用台账和后台可视化配置。真实实例 `https://ha.pnkx.top:8` 已联通，当前授权 11 个实体；灯/开关可控，空调写操作要求当前用户消息明确确认。Perception Pipeline 第一批已将 HA `person` 与存在传感器状态接入 M3B 认知调度闭环，主动消息经 `ProactiveDeliveryService` 统一投递至 Web/桌面通知/语音。

### 1. 目标与结论

本方案将 Home Assistant（以下简称 HA）作为物理设备控制平面，将 Aria Hub 作为对话、意图理解、记忆、隐私策略、确认和主动交互平面。Aria 不重复适配 Zigbee、Matter、米家等协议，而是通过 HA 的标准 API 读取实体状态、执行受控动作，并将稳定状态变化转换为中枢语义事件。

最终边界为：

- HA 负责设备接入、实体状态、服务调用、场景和确定性自动化；
- Aria 负责自然语言理解、目标解析、能力暴露、风险判断、用户确认、审计和主动提醒；
- HA WebSocket 用于状态同步和事件订阅；
- HA REST API 用于执行服务；
- MQTT Discovery 仅用于把 Aria 自身状态暴露给 HA，不作为读取全部 HA 实体的主链路；
- 模型永远不能直接传入任意 HA `domain/service` 或请求 URL。

```text
用户文字 / 语音
       │
       ▼
Aria Chat / Voice
       │ Function Calling
       ▼
Home Assistant Tools ──► Confirmation Engine
       │                         │
       └─────────────┬───────────┘
                     ▼
            Home Assistant Bridge
            ├─ REST：执行动作
            ├─ WebSocket：订阅状态
            └─ MQTT：向 HA 暴露 Aria
                     │
                     ▼
              Home Assistant Core
```

### 2. 范围

#### 2.1 首版包含

1. 连接一个 HA 实例，支持健康检查、鉴权、状态同步、断线重连；
2. 读取管理员明确授权的灯、开关、风扇、空调、窗帘、媒体播放器和传感器状态；
3. 控制管理员明确授权的灯、开关、风扇、空调、窗帘、媒体播放器和场景；
4. 中文名称、区域、别名和 `entity_id` 的确定性解析；
5. 实体级读权限、动作白名单、隐私等级、风险等级和确认策略；
6. 高风险动作确认、TTL、幂等、结果回读和审计台账；
7. 将稳定 HA 状态变化转换为 Aria 语义事件；
8. Admin 连接状态、实体同步、授权策略和动作台账；
9. 可选 MQTT Discovery，将 Aria 在线状态和 DND 状态暴露给 HA。

#### 2.2 首版不包含

- 任意 `shell_command.*`、`command_line.*`、`hassio.*`；
- `homeassistant.restart/stop` 等管理动作；
- 未逐项登记的 `script.*` 和 `automation.*`；
- 动态模板、任意代码或任意 HA 服务调用；
- 摄像头持续监控、麦克风监听和原始健康数据持久化；
- 由 HA 事件直接触发新的设备控制；
- 用 Aria 替代 HA Automation 成为第二套通用自动化引擎；
- 多 HA 实例同时路由。数据模型预留 `instance_id`，实现先支持一个启用实例。

### 3. 通信方案

#### 3.1 WebSocket 状态链路

连接 `ws(s)://<ha-host>/api/websocket`：

1. 等待 HA 发送 `auth_required`；
2. 发送 `{"type":"auth","access_token":"..."}`；
3. 收到 `auth_ok` 后获取初始状态；
4. 订阅 `state_changed`；
5. 立即丢弃未授权实体事件；
6. 对授权实体更新内存快照并进入去抖/语义事件管线；
7. 心跳失败或连接断开后按 1、2、4、8、16、30 秒上限退避重连；
8. 重连成功后重新做全量状态同步，但同步流量不得触发主动提醒。

Bridge 只能缓存管理员授权实体。HA 原始属性可能包含位置、图片 URL、人员、设备标识等敏感数据，进入缓存前必须按实体 domain 和字段白名单裁剪，完整 WebSocket payload 不得写日志。

#### 3.2 REST 动作链路

动作通过以下接口执行：

```text
POST /api/services/<domain>/<service>
Authorization: Bearer <token>
Content-Type: application/json
```

模型只产生受控语义动作。例如：

```json
{
  "target": "客厅主灯",
  "action": "set_brightness",
  "parameters": {"brightness_pct": 40}
}
```

服务端完成目标解析、授权检查、参数校验和风险判断后，才映射为：

```json
{
  "domain": "light",
  "service": "turn_on",
  "service_data": {
    "entity_id": "light.living_room_main",
    "brightness_pct": 40
  }
}
```

动作调用返回后必须回读目标状态。HTTP 超时不能直接重试写操作，应先回读状态；无法判断结果时记为 `unknown_outcome`。

#### 3.3 历史与设备日志

- 连续状态使用 `GET /api/history/period/<start>` 读取 Recorder 历史，如温度、湿度和 PM2.5；
- 人工可读事件使用 `GET /api/logbook/<start>`，如灯的开关记录；
- 后台按实体配置 `history_allowed` 和 `history_max_hours`，默认拒绝；
- 当前实例真实验收：客厅灯 History/Logbook 有记录，家庭温度、湿度和水浸告警 History 可读。连续数值传感器的 Logbook 可以为空，以 History 为准。

#### 3.4 MQTT 的职责

HA 控制和状态读取不依赖 MQTT。MQTT 只承担：

- Aria Hub 在线/离线；
- Aria DND 状态和可选开关；
- Aria 主动感知健康状态；
- 将来 ESP32 等原生 MQTT 设备接入。

建议主题：

```text
homeassistant/sensor/aria_hub_status/config
homeassistant/switch/aria_dnd/config
aria/hub/availability
aria/hub/status
aria/hub/dnd/state
aria/hub/dnd/set
```

Discovery 配置包含稳定 `unique_id`、device、origin 和 availability；HA Birth 后重发配置和状态。不得把 `hub/devices/#` 原样桥接到 `homeassistant/#`。

### 4. 配置模型

新增顶层 `integrations`，避免把外部系统连接生命周期混入地图 Query Tools：

```yaml
integrations:
  home_assistant:
    enabled: true
    instance_id: home-main
    base_url: https://ha.pnkx.top:8
    # 连接地址、令牌、运行参数和实体白名单由管理后台保存；
    # YAML 仅保留首次启动的未启用默认值。
    verify_tls: true
    allow_insecure_local_http: false

    connect_timeout_ms: 5000
    request_timeout_ms: 8000
    reconnect_min_seconds: 1
    reconnect_max_seconds: 30
    state_cache_ttl_seconds: 300

    event_subscription:
      enabled: true
      debounce_ms: 1000
      unavailable_grace_seconds: 30

    controls:
      max_targets_per_action: 8
      confirmation_ttl_seconds: 60
      default_policy: deny

    mqtt_discovery:
      enabled: false
      discovery_prefix: homeassistant
      topic_prefix: aria
```

约束：

- token 默认通过后台密码框写入受管理员鉴权保护的数据库配置版本；仍兼容 `secret_ref` 环境变量引用；
- token 在界面中按密码字段遮蔽，不写日志、不进入聊天前端；
- 生产使用 HTTPS 或受控 VPN；本地明文 HTTP 必须显式开启且只允许私网地址；
- 后台保存后立即重连，无需重启 Hub；
- token 轮换后重新鉴权，不要求重启整个 Hub。

#### 4.1 当前目标实例

本项目已有可用 HA 服务，首个集成目标固定为：

```text
https://ha.pnkx.top:8
```

2026-08-24 从当前开发环境完成只读探测：

- 根路径返回 HTTP 200 和 `text/html`；
- `/api/` 在未携带 token 时返回 HTTP 401，符合 HA API 鉴权预期；
- 公网 DNS 可解析且 TLS 主机校验通过；
- 当前证书 CN 为 `*.pnkx.top`，由 Let's Encrypt 签发；
- 当前探测到的证书有效期截止 2026-10-15，部署方应确认自动续期并增加证书到期监控。

因此不再部署新的 HA 容器，Aria Bridge 直接连接该实例。配置中的 `base_url` 去掉末尾 `/`，REST 路径由 client 统一拼接；WebSocket 地址由 client 转换为 `wss://ha.pnkx.top:8/api/websocket`。

该地址是公网入口，落地时额外要求：

- HA token 通过后台配置中心或部署环境密钥注入，不能提交到仓库；
- 使用专门为 Aria 创建的 HA 用户和独立 token，不复用日常管理员 token；
- 反向代理保留 WebSocket Upgrade，并对登录/API 做速率限制；
- 可行时通过 VPN、源 IP 白名单或访问控制层限制入口；
- Aria 发出的日志不得包含 URL query、Authorization header 或响应正文；
- 首次带 token 联调只执行 `GET /api/`、状态读取和订阅，写服务在实体白名单完成前保持关闭。

#### 4.2 现有工具配置重构

当前 `ToolsConfig` 将总工具开关和高德 provider 强绑定。实现 HA 前应改为各域独立启停：

```yaml
tools:
  max_tool_rounds: 1
  query:
    enabled: true
    weather_enabled: true
    nearby_enabled: true
    route_enabled: true
  home_assistant:
    enabled: true
```

开启 HA 不得要求高德已配置。旧配置继续兼容，首次保存时迁移为新结构。

### 6. 数据模型

#### 6.1 `home_assistant_entity_policy`

| 字段 | 类型/约束 | 含义 |
|---|---|---|
| `id` | UUIDv7 PK | 策略 ID |
| `user_id` | UUID FK | 所属用户 |
| `instance_id` | string | HA 实例 |
| `entity_id` | string | HA 实体 ID |
| `display_name` | string | Aria 显示名 |
| `aliases` | JSON array | 中文别名 |
| `area_name` | string nullable | 所属区域 |
| `domain` | string | light/switch/... |
| `read_allowed` | boolean | 是否允许读取 |
| `allowed_actions` | JSON array | 允许语义动作 |
| `privacy_level` | L0～L3 | 服务端隐私基线 |
| `risk_level` | R0～R4 | 动作风险 |
| `confirmation_policy` | never/first_time/always | 确认策略 |
| `enabled` | boolean | 总开关 |
| `created_at/updated_at` | timestamp | 审计时间 |

唯一约束：`(user_id, instance_id, entity_id)`。同步发现新实体时默认 `enabled=false`、`read_allowed=false`、无允许动作。

#### 6.2 `home_assistant_action_execution`

| 字段 | 含义 |
|---|---|
| `id` | 动作请求 ID |
| `user_id/conversation_id/turn_id` | 请求归属 |
| `instance_id/entity_id` | 执行目标 |
| `semantic_action` | 受控动作枚举 |
| `arguments_redacted` | 脱敏参数 |
| `request_hash` | 完整规范化请求摘要 |
| `idempotency_key` | 幂等键 |
| `risk_level` | R0～R4 |
| `status` | 动作状态 |
| `confirmation_expires_at` | 确认过期时间 |
| `confirmed_at/executed_at` | 生命周期时间 |
| `result_code` | 稳定结果码 |

状态机：

```text
planned ──► awaiting_confirmation ──► confirmed ──► executing
   │                 │                                  │
   │                 ├─► rejected                       ├─► succeeded
   │                 └─► expired                        ├─► failed
   └────────────────────────────────────────────────────└─► unknown_outcome
```

不持久化 HA 全量状态。当前状态只保存在有界内存缓存；需要长期保留的事实必须先转换为允许持久化的 Aria 语义事件。

### 7. LLM 工具

#### 7.1 `home_get_state`

```json
{
  "targets": ["客厅主灯", "卧室温度"],
  "attributes": ["state", "brightness", "temperature"]
}
```

- 最多 10 个目标；
- 只返回字段白名单；
- 目标歧义时返回候选，不自动猜测；
- 状态过期或 HA 离线时明确返回 unavailable；
- L3 原始值不进入模型自由文本链路，优先使用服务端确定性模板回答。

#### 7.2 `home_control_device`

```json
{
  "target": "客厅主灯",
  "action": "set_brightness",
  "parameters": {"brightness_pct": 40}
}
```

`action` 是固定枚举，参数使用按 domain/action 区分的 Pydantic 联合模型。单次最多 8 个明确目标，禁止通配符和隐式“全屋”。

#### 7.3 `home_activate_scene`

```json
{"scene": "睡眠模式"}
```

场景必须逐项授权和标记风险，不能因为 domain 为 `scene` 就自动视为低风险。

#### 7.4 `home_confirm_action`

```json
{"request_id": "uuid"}
```

主要确认路径由聊天确认卡片调用服务端 API；文字/语音确认作为辅助路径。确认必须绑定当前用户、会话和原始参数。模型编造或复用 request ID 不能越权。

`home_list_entities` 只供 Admin 使用，不注入模型上下文。

#### 7.5 工具选择

新增 `select_home_tools(text, capabilities)`，依据意图词和当前真实能力选择最小工具集。工具是否可见取决于：

```text
HA 在线
∩ 实体存在且可用
∩ 属于当前用户
∩ 管理员已启用
∩ 动作在白名单
∩ 当前隐私路由允许
```

普通灯光和开关工具允许 L0/L1；精确位置、摄像头、卧室存在等维持 L2/L3。不能继续使用“所有设备工具仅在 L2 可见”的统一条件。

### 8. 动作映射与风险

允许的首版映射：

| Domain | 语义动作 | HA Service |
|---|---|---|
| `light` | turn_on/turn_off/set_brightness/set_color_temp | `light.turn_on/turn_off` |
| `switch` | turn_on/turn_off | `switch.turn_on/turn_off` |
| `fan` | turn_on/turn_off/set_percentage | `fan.turn_on/turn_off/set_percentage` |
| `climate` | turn_on/turn_off/set_temperature/set_hvac_mode | 对应 `climate.*` |
| `cover` | open/close/stop/set_position | 对应 `cover.*` |
| `media_player` | play/pause/volume_set（已接入 Action Engine v2） | 对应 `media_player.media_play/media_pause/volume_set` |
| `scene` | activate | `scene.turn_on` |

风险基线：

| 风险 | 示例 | 默认策略 |
|---|---|---|
| R0 | 授权状态读取 | 直接执行 |
| R1 | 灯、普通开关、媒体播放 | 显式授权后直接执行 |
| R2 | 空调、窗帘、风扇、普通场景 | first_time 或 always |
| R3 | 门锁、车库门、报警、阀门 | 每次确认；首版可整体关闭 |
| R4 | HA 管理、Shell、任意脚本 | 永久拒绝 |

门锁、报警和阀门若在首版启用，只能走 R3 每次确认，且需要 Admin 单独打开 feature flag。`toggle` 默认不开放，因为重试和状态过期时不容易保证期望终态；优先使用明确的 `turn_on/turn_off`。

### 9. 确认、幂等和对账

1. 模型产生语义动作候选；
2. 服务端解析目标并验证策略；
3. 规范化参数并计算 `request_hash`；
4. 生成与 user/conversation/target/action 绑定的幂等键；
5. 需要确认时仅写 `awaiting_confirmation`，不调用 HA；
6. 确认卡片展示目标、动作和关键参数；
7. 确认在 60 秒后失效且只能消费一次；
8. 执行前重新验证连接、实体可用性和策略版本；
9. 执行后回读状态并判定是否达到期望终态；
10. HTTP 超时先回读，不能直接重复写；仍无法确定则进入 `unknown_outcome`；
11. 取消、拒绝、过期和失败都返回稳定 reason code。

任何确认都不能扩大原请求：例如用户确认“客厅灯亮度 40%”不能被复用为“全屋灯 100%”。

### 10. 入站事件与主动感知

#### 10.1 事件处理流水线

```text
HA state_changed
  → 实体授权过滤
  → 属性白名单与服务端隐私重分类
  → 内存快照
  → 去抖/阈值/恢复同步抑制
  → EphemeralSignal 或 InputEnvelope
  → Perception 语义事件
  → ProactiveEngine 策略
  → 允许时输出提醒
```

推荐映射：

| HA 变化 | Aria 事件 |
|---|---|
| `person.* → home` | `user_arrived_home` |
| `person.* → not_home` | `user_left_home` |
| 授权门窗持续打开 | `home.entry_open_too_long` |
| 授权实体 unavailable 超过宽限期 | `device.offline` |
| 人体存在稳定变化 | `presence.changed` |
| 温湿度越过配置阈值 | `environment.threshold_crossed` |

禁止将每次 `state_changed` 都持久化。数值抖动不产生 durable event；HA 或 Hub 重启后的初始同步不产生主动提醒。

#### 10.2 主动控制边界

首版 HA 事件只能触发提醒，不能触发新的设备写操作。用户希望“回家后开灯”等确定性规则时，优先创建或指导创建 HA Automation。以后如允许 Aria 创建规则，必须使用单独的规则草稿、预览、确认、发布和回滚流程。

### 11. 隐私

沿用现有 L0～L3：

| 数据 | 建议级别 | 处理 |
|---|---|---|
| 灯光、普通开关 | L0 | 可用于普通对话 |
| 环境聚合、设备在线 | L0/L1 | 可转语义事件 |
| 人员在家状态 | L0～L2，由管理员配置 | 最小化持久化 |
| 精确位置、门锁历史 | L2 | 本地模型和严格审计 |
| 摄像头、麦克风、卧室原始存在 | L3 | 不落库、不进日志 |
| 健康和高频原始遥测 | L3 | 仅临时处理 |

强制规则：

- 上游 HA 分类只是输入，服务端策略可以上调，不能由消息自行下调；
- L3 不写通用 event、Timeline、日志、备份或动作参数；
- L3 不发送云端 LLM；
- L3 尽量由服务端确定性格式化，不进入模型自由文本上下文；
- 快照按 TTL 删除；
- Admin 页面默认不显示敏感原值，只显示通道健康和最近更新时间；
- token、Authorization header、完整 HA payload 和精确位置永不记录。

## M3B 认知调度闭环（原编号 37）

> 文档类型：Active 架构设计
> 日期：2026-09-01
> 状态：v1 认知闭环已落地；个人管家 ACT-01～03 已完成，ACT-04 已接通灯光亮度、媒体控制和 L0/L1 桌面通知，提醒与桌面打开动作待完成
> 目标阶段：M3B 认知调度闭环
> 关联：docs/05、docs/03、TASKS.md §D

---

### 1. 设计目标

当前中枢的主动引擎基于**确定性规则**：Home Assistant 状态变化 → 匹配固定模板 → 检查安静时段/冷却 → 推送。这是一个安全、可控的提醒引擎，但还不是**认知引擎**。

M3B 的目标是让中枢形成持续、可控的闭环：

```text
感知变化
  ↓
理解当前世界
  ↓
判断是否值得处理
  ↓
结合目标、记忆和权限做决定
  ↓
沉默 / 提醒 / 询问 / 建议 / 执行
  ↓
检查执行结果
  ↓
根据用户反馈调整以后行为
```

关键约束：
- 不实现 24 小时循环思考，而是**事件驱动**的认知管线；
- 大模型只在必要时被调用，廉价确定性规则优先过滤；
- 所有决策必须结构化、可审计，不保存自由文本"内心活动"；
- 自主写动作（`act`）在 v1 保持关闭，只建立框架；
- 被动聊天和主动事件走**同一个认知循环**，人格与能力边界一致。

---

### 2. 六层架构

#### 2.1 Semantic Event：把所有输入变成"发生了什么"

不要直接把传感器原始数据喂给模型。先由确定性规则或轻量感知进程转换为语义事件。

**典型事件类型**：

| 事件 | 来源 | 示例 |
|-----|------|------|
| `user.message_received` | 聊天/语音 | 用户发送文字或语音 |
| `user_arrived_home` | HA 存在传感器 | 用户到家 |
| `room_temperature_high` | HA 温度传感器 | 室温持续偏高 |
| `light_on_too_long` | HA 规则 | 灯开启超过阈值 |
| `device_offline` | 设备心跳 | Desktop Client 离线 |
| `water_leak_detected` | HA 水浸传感器 | 紧急安全事件 |
| `commitment_due` | 目标调度器 | 承诺即将到期 |
| `conversation_interrupted` | 语音通道 | 用户打断 TTS |
| `screen_context_available` | Desktop | 屏幕截图就绪 |

**契约**（代码真源：`server/app/cognition/models.py:50-70`）：

```python
class SemanticEvent(StrictModel):
    event_id: UUID
    user_id: UUID
    kind: str                       # 事件类型
    summary: str                    # 人类可读摘要
    occurred_at: datetime
    privacy_level: PrivacyLevel
    confidence: float               # 0..1
    evidence_ids: list[str]         # 原始证据引用
    expires_at: datetime | None     # TTL
    passive: bool = False           # True=用户主动输入
```

约束：主动事件（`passive=False`）必须有 `evidence_ids`，禁止无证据进入认知链路。

**事件流入方式**：
- 被动：`ChatService.start_turn()` 将用户消息包装为 `user.message_received`；
- 主动：`PerceptionPipeline` 接收 HA 状态变化，经稳定窗口和去抖后提交事件。

---

#### 2.2 World State：维护"此刻世界是什么样"

长期记忆不能代替实时世界状态。严格分开：

| 系统 | 回答的问题 | 持久化 |
|---|---|---|
| Memory | 用户通常喜欢什么、以前说过什么 | 长期 |
| Timeline | 某段时间发生过什么 | 长期 |
| World State | 此刻人在哪里、设备是什么状态、刚发生什么 | **不持久化**，每次事件到来时动态组装 |
| Goals | 接下来希望什么状态成立 | 长期 |

**组装逻辑**（代码真源：`server/app/cognition/world.py:38-147`）：

```python
class WorldState(StrictModel):
    built_at: datetime
    timezone: str
    last_interaction_at: datetime | None   # 最近用户交互时间
    active_capabilities: list[str]          # 当前在线设备的能力交集
    active_goals: list[GoalView]            # 未到期目标
    memory_evidence_ids: list[str]          # 与事件相关的记忆引用（只存ID）
    timeline_evidence_ids: list[str]        # 与事件相关的历史引用（只存ID）
    recent_proactive_count: int             # 24h 内已主动提醒次数
    same_trigger_recent_count: int          # 4h 内同类型事件数
    ignored_same_trigger_count: int         # 用户忽略/禁止过的同类型数
    dnd: bool                               # 当前是否免打扰
```

注意：**不是"把所有输入都塞进上下文"**。正确方式是每个事件到来后，只检索与该事件相关的状态、记忆和历史证据。

---

#### 2.3 Attention Engine：决定值不值得调用模型

大模型不应该处理每次温度波动、心跳、在线状态变化。

**评分公式**（代码真源：`server/app/cognition/attention.py:12-57`）：

```text
salience = base_score(event.kind) * confidence
         + time_sensitive_bonus
         + active_goal_bonus
         - duplicate_penalty * same_trigger_recent_count
         - feedback_penalty * ignored_same_trigger_count

should_deliberate = critical_event or salience >= threshold(0.55)
```

| 因子 | 规则 |
|------|------|
| 基础分 | `water_leak=1.0`, `user_arrived_home=0.7`, `light_on_too_long=0.62`, 默认 `0.4` |
| DND | 非紧急事件直接丢弃；紧急事件（`water_leak`）绕过 DND |
| 重复惩罚 | 同类型事件每多一次 `-0.15`，上限 `-0.45` |
| 反馈惩罚 | 用户每忽略/禁止一次 `-0.1`，上限 `-0.3` |
| 目标上下文 | 有活跃目标时 `+0.05` |
| 时间敏感 | 有过期时间时 `+0.05` |

被动请求（`passive=True`）直接通过，因为用户已经主动发起交互。

---

#### 2.4 Deliberation Engine：真正的"想一下再决定"

输入不是一句聊天，而是：

```text
触发事件
+ 当前 World State
+ 相关记忆
+ 有效目标/承诺
+ 最近主动行为
+ 当前真实能力
+ 隐私和授权策略
```

**输出必须是结构化决策**，不允许自由文本"内心活动"：

```python
class CognitiveDecision(StrictModel):
    decision: DecisionKind        # ignore / record / inform / ask / suggest / act / escalate
    reason_codes: list[str]       # 简短枚举，如 ["sustained_temperature_high", "user_present"]
    evidence_ids: list[str]       # 引用的证据
    confidence: float             # 0..1
    urgency: Urgency              # low / normal / high / critical
    message: str | None           # 面向用户的中文消息（ask/suggest/inform/escalate 必填）
    approval_required: bool       # 是否需要用户确认
    policy_version: str           # 策略版本号，用于审计
    model_provider: str | None    # 使用哪个模型做的决策
    model_name: str | None
```

**双层实现**（代码真源：`server/app/cognition/deliberation.py`）：

- **`RuleBasedDeliberator`**：确定性规则，处理已知事件类型。安全、快速、可预测。
- **`RouterDeliberator`**：模型结构化判断（JSON mode），system prompt 严格限制输出格式。**任何 `act` 输出都会被硬性拒绝并回退到规则 deliberator**。

安全回退链：

```text
RouterDeliberator 异常 / act 输出 / 格式错误
  → 自动回退到 RuleBasedDeliberator
  → 仍失败则返回 DecisionKind.IGNORE
```

---

#### 2.5 Action Engine：行动、确认和结果回读

"会主动说话"和"会自主行动"是两个风险完全不同的阶段。

**行动分级**（v1 框架建立，A2/A3 保持关闭）：

| 级别 | 名称 | 说明 | v1 状态 |
|------|------|------|---------|
| A0 | 观察记录 | 只记录事件，不向用户输出 | 开放 |
| A1 | 主动提醒 | inform / ask / suggest / escalate，通过已有输出通道投递 | 开放 |
| A2 | 预授权低风险动作 | 执行用户预先授权的低风险动作（如关灯） | **关闭** |
| A3 | 高风险动作 | 门锁、摄像头、购买、删除数据等，每次明确确认 | **关闭** |

**决策到级别的映射**：

```text
ignore    → A0 (记录但不输出)
record    → A0 (记录)
inform    → A1 (告知)
ask       → A1 (询问)
suggest   → A1 (建议)
escalate  → A1 (紧急提醒)
act       → A2/A3 (v1 被安全门拒绝)
```

**结果回读**（v1 框架；Action Engine v2 已接入 HA 写后回读）：

```python
class ActionResult(StrictModel):
    decision_id: UUID
    outcome: ActionOutcome         # observed / prompted / blocked / unknown_outcome
    reason_code: str | None
    verified: bool                 # 是否已验证实际结果
    observed_state: dict           # 回读的状态快照
```

v1 阶段：
- A1 决策通过 `ProactiveDeliveryService` 投递后，由 ActionEngine 记录 `outcome="prompted"`；
- A2/A3 直接返回 `outcome="blocked"`，`reason_code="autonomous_action_disabled"`；
- 未来开放 A2 时，增加"执行 → 回读实际状态 → 确认成功/失败/未知"闭环。

**ACT-01 动作安全目录（2026-09-01）**：

认知决策级别继续描述“观察、提醒或请求现实动作”；新增的 `ActionRegistry` 描述具体动作自身的风险和执行契约。两者是不同维度，不能用认知模型输出直接绕过动作目录。

每个 `ActionDefinition` 固定声明：

- 稳定 `action_id`、用户可见名称和说明；
- 参数 Pydantic Schema 与绑定到工具的固定参数；
- A0～A3 动作风险及匹配的 `never/preauthorized/always/prohibited` 确认策略；
- 可逆性、补偿动作、超时和 `owner_action_arguments` 幂等范围；
- `none/receipt/read_after_write` 验证策略与验证器 ID；
- 最大隐私等级和实际 `tool_name`。

首批目录包含灯光/开关的打开与关闭、空调设温共 5 个动作。灯光和开关是 A1 预授权候选，空调设温是 A2 每次确认。鉴权查询接口为 `GET /api/v1/cognition/actions/catalog`。

**ACT-02 持久计划与确认执行（2026-09-01）**：

- `action_plan/action_step` 保存 owner、请求哈希、TTL、动作/风险/确认快照、工具参数、幂等键和步骤结果；
- `POST /api/v1/cognition/action-plans` 只接受注册动作并确定性编译参数；
- `confirm/cancel/execute` 均验证当前用户和合法状态，A1 默认仍需确认，A2 每次确认；
- Runner 只获得步骤中预编译的 `tool_name/tool_arguments`，不能临时改写动作或扩大参数；
- 顺序执行在失败时停止，已完成步骤保留，后续步骤标记 `skipped`；超时或协程取消进入 `unknown_outcome`，不得自动重试；
- `0024_action_plan` 已通过 SQLite 空库迁移，真实 PostgreSQL 升级仍需单独执行。

上述 API 打开的是“用户显式确认后的计划执行”，不是模型自治。`CognitiveDecision.ACT` 仍被 v1 策略拒绝。

**ACT-03 写后回读与补偿计划（2026-09-01）**：

- `ToolActionRunner` 在 HA 写动作返回成功后读取授权实体的当前状态；灯光/开关核对最终 `on/off`，空调核对目标温度并使用 0.1°C 容差。
- HA REST 服务调用返回的状态会立即刷新桥接缓存，避免写后回读继续读取调用前的陈旧快照。
- `ActionStep` 保存 `verification_status`、最小化 `verification_result` 和 `verified_at`。工具成功但回读不匹配、设备离线或验证器不可用时，结果是 `unknown_outcome`，不会自动重试未知副作用。
- 已完成且注册表声明可逆的步骤可生成独立补偿计划；步骤按原计划逆序排列，并保存原计划/补偿计划、原步骤/补偿步骤关联。补偿计划复用正常风险和确认策略，必须重新确认，且不能递归撤销。
- 接口 `POST /api/v1/cognition/action-plans/{plan_id}/undo` 只创建补偿计划，不直接执行现实写操作。

**ACT-04 首批动作（2026-09-01）**：

- 注册表新增灯光亮度、媒体播放、暂停和音量设置，总计 9 个 HA 动作；不接受模型自造服务名或额外参数。
- 灯光亮度限制为 1～100%，按 HA `brightness` 的 0～255 值换算后以 ±1% 回读；播放/暂停核对 `playing/paused`；音量限制为 0～1 并以 ±0.01 回读。
- `set_brightness/play/pause` 是 A1 预授权候选，默认配置下仍需确认；`volume_set` 是 A2，必须逐次确认。
- 语义动作由服务端固定映射到 HA `turn_on/media_play/media_pause/volume_set`，仍需同时通过实体 domain、管理员动作白名单和隐私策略。
- `desktop.notification.show` 只接受 L0/L1，复用已配对桌面的 `notification.show` 能力；执行使用行动步骤幂等键，只有设备命令终态为 `succeeded` 才记录 `verified`，证据只保留命令 ID、设备 ID 和状态。
- 通知动作仍经过计划确认，不复用主动推送绕开 Action Engine；L2 正文、离线设备、未授权能力和失败回执均确定性拒绝或失败。

#### 2.6 Reflection：让它越来越懂你

不是让模型随意改 Persona，而是基于真实反馈产生**带证据的候选偏好更新**。

**反馈类型**（代码真源：`server/app/cognition/models.py:43-48`）：

```python
class FeedbackKind(StrEnum):
    ACCEPTED = "accepted"       # 用户接受了提醒
    IGNORED = "ignored"         # 用户未响应或关闭
    SNOOZED = "snoozed"         # 用户说"稍后"
    FORBIDDEN = "forbidden"     # 用户说"别再提醒这个"
```

**反馈入口**：每条主动消息附带快捷反馈按钮（Web/通知），调用 `POST /api/v1/cognition/decisions/{id}/feedback`。

**分析维度**：

- 哪些主动消息被用户接受；
- 哪些被忽略、关闭、标记烦人；
- 什么时间用户愿意被提醒；
- 什么类型的建议有用；
- 哪些预测后来被证明错误；
- 哪些承诺已经完成或失效。

**候选生成**（`ReflectionCandidate`）：

```python
class ReflectionCandidate(StrictModel):
    content: str                  # 如"用户工作日晚间不希望收到非紧急环境提醒"
    evidence_ids: list[str]      # 支撑该结论的反馈记录ID
    confidence: float             # 0..1
    requires_confirmation: bool   # 是否需要用户确认后才生效
```

**v1 实现**：
- `ReflectionEngine.analyze_feedback_patterns()`：按 `trigger_kind` 聚合最近 30 天反馈，计算接受率；
- 连续 `N` 次 `ignored`/`forbidden` → 自动生成候选，标记 `requires_confirmation=True`；
- 候选不直接写入 Persona 或 Memory，而是进入待确认队列，由用户或管理员审阅后采纳；
- 新增 8 个回归测试覆盖 Action Engine 分级映射、A2/A3 v1 阻断、结果回读持久化、Reflection Engine `_analyse` 单元、FeedbackSummary 聚合和候选生成。

**待完善（v2）**：
- 定时调度器（每天/每周跑一次有界反思任务）；
- 模型辅助的深层模式识别（不仅仅是计数）；
- 候选到 Memory/Persona 的自动/半自动写入。

### 3. 统一认知循环

被动和主动走同一个 `CognitiveCycle`：

```text
用户消息 ─────┐
语音输入 ─────┤
HA 状态变化 ──┤
定时任务 ─────┼→ CognitiveCycle.evaluate(event)
设备事件 ─────┤
目标到期 ─────┘
```

**流程**（代码真源：`server/app/cognition/cycle.py:28-52`）：

```python
async def evaluate(self, event: SemanticEvent) -> CognitiveDecision:
    state = await self.world.build(event)           # 组装 WorldState
    attention = self.attention.evaluate(event, state)  # 注意力评分
    if not attention.should_deliberate:
        return IGNORE 决策                            # 静默，保存原因
    decision = await self.deliberator.deliberate(event, state, attention)
    await self.store.save_decision(decision)         # 持久化审计
    return decision
```

**区别策略**：

| 场景 | 行为差异 |
|------|---------|
| 被动请求 | `passive=True`，Attention 直接通过，必须产生响应 |
| 主动事件 | 允许 `ignore`，低分直接丢弃 |
| 紧急事件 | `water_leak` 等绕过 DND，进入 `escalate` |
| L3 隐私 | 决策不落库（零持久化） |

## MCP 整体架构（原编号 43（含 41 Token 优化））

> 日期：2026-09-08  
> 状态：已定稿；MCP-C0（2026-09-08）、C1（2026-09-10）、C2/D（2026-09-11）已实现  
> 范围：Companion Hub 作为 MCP Client 接入外部工具；Aria MCP Server 暂不启动

### 1. 架构结论

MCP 是 Hub 的外部工具适配层，不替换内部工具目录、Action Plan、权限、隐私、确认和审计。模型优先使用 Aria 的稳定工具名与结果结构，MCP Server 的远端名称和 Schema 由适配层转换。

```text
聊天模型
  ↓ 本轮少量工具定义
内部工具目录
  ↓ 身份 / 隐私 / 白名单 / 确认 / 审计
  ├─ 本地工具
  ├─ Home Assistant REST/WebSocket 适配器
  └─ MCP Client 适配器 → 外部 MCP Server
```

Hub 作为 MCP Server 是另一条产品线：只有其他 AI 客户端确实需要复用 Aria 能力时再做，且必须复用同一授权、确认和审计层。

### 2. 模块边界

`server/app/integrations/mcp/` 承担：

- Server 配置、连接生命周期与健康状态；
- `tools/list` 全分页发现、白名单过滤、本地目录缓存与名称空间；
- 远端 Schema 到内部工具定义的转换；
- `tools/call` 执行和有界结果裁剪；
- 稳定错误码和可观测状态。

MCP 层不承担：

- 用户是否已确认写操作；
- 模型是否可在当前隐私级别使用某工具；
- 业务语义下的写后回读、撤销和补偿。

这些继续由 Tool Registry、Egress Guard 和 Action Plan 负责。

### 3. 连接与配置

第一批只开放 Streamable HTTP，默认要求 HTTPS。本地调试需显式允许 loopback HTTP。不开放管理员可自由填写的 stdio shell 命令，避免配置面变成任意代码执行入口。

每个 Server 配置包含：`server_id`、`enabled`、`endpoint`、凭据引用、工具白名单、连接/调用超时、目录缓存时间、最大并发和写工具开关。凭据仅通过 secret 通道解析，不进入模型或管理 API 回包。

### 4. 工具发现与 Token 预算

1. SDK 完成协议协商，Hub 逐页读取工具目录。
2. 远端目录先与本地 `allowed_tools` 求交集，再进入应用缓存。
3. 内部名称使用 `mcp.{server_id}.{remote_name}`，防止多 Server 重名。
4. 普通对话不注入 MCP 目录；根据意图检索后，每轮最多加载 `max_tools_per_turn` 个定义。
5. 工具描述、Schema 和返回结果均设独立体积上限。

工具发现是 Hub 行为，不等于把全部工具告诉模型。

### 5. 安全执行链

```text
用户与会话身份
  → 隐私级别
  → Server 开关
  → 工具白名单
  → JSON Schema 校验
  → 风险分级
  → 确认票据 / Action Plan
  → MCP 调用
  → 结果裁剪与审计
```

远端描述和返回文本都是不可信数据，不得覆盖 Aria 系统规则。`readOnlyHint` 等远端注解只是参考，本地策略才是权威。未显式标记为只读的工具默认按写工具处理。

写操作超时后不自动重发；先回读验证，不能确定时返回 `unknown_outcome`。模型传入 `confirmed=true` 不能代替服务端确认票据。

### 6. 可观测性

Admin 提供 Server 健康、协议版本、服务端身份、工具数、目录刷新时间和最近错误。调用台账后续记录 Server/工具、用户、隐私、风险、延迟和稳定错误码，不保存凭据和未裁剪敏感原文。

### 7. 实施批次

| 批次 | 交付 | 验收 |
|---|---|---|
| MCP-C0 | 配置、SDK 边界、连接管理、分页目录、白名单、错误码、Admin 状态 | 未配置时零连接；假 Server 可验证发现/失败/重名隔离 |

### 41 设备工具 Token 优化与 MCP 接入批次

> 原文：`41-设备工具Token优化与MCP接入方案`（设备工具 Token 优化与 MCP 接入方案）。2026-09-15 按功能并入本文档，内容完整保留、标题降一级。

日期：2026-09-08  
状态：A/B 与通用 MCP-C0 已实现（2026-09-08）；C1/D 等有明确外部 MCP 目标后启动。  
适用范围：Aria Companion Hub 的 HA 设备工具、聊天提示词及后续 MCP 扩展。

#### 1. 结论与实施顺序

先移除聊天提示词中的全量设备动作明细，增加本地设备检索，继续使用现有 HA REST/WebSocket 链路。随后把设备访问封装为稳定适配器接口，再按实际外部服务需求引入 MCP 客户端。

MCP 是工具发现和调用协议，本身不会减少模型输入。节省 Token 的关键是控制交给模型的工具定义、设备候选和调用结果。设备目录和 MCP 工具目录可以缓存在应用内，不必全部写入模型上下文。

实施分为四批：

1. A：建立基线，合并重复能力描述，提供回退开关。
2. B：按需检索设备，移除全量明细，完成会话指代与回归验收。
3. C：增加 MCP 客户端适配器，先试点一个只读外部工具。
4. D：根据需要接入 MCP 写工具、评估 HA 替换，或另建 Aria MCP Server。

#### 2. 当前代码事实

| 位置 | 当前行为 | 优化关注点 |
|---|---|---|
| `server/app/chat/service.py` | 每轮获取 `available_actions(user_id)`，通过 `render_reality_grounding` 写入 system message | 普通聊天路径未按当前问题筛选设备；存在特定意图例外，实施时保留其行为 |
| `server/app/chat/capabilities.py` | 将传入的每个能力逐行渲染为 ID、名称、说明 | 同一设备多个动作重复携带名称和说明 |
| `server/app/home_assistant/manager.py` | 枚举已配置、允许读取、非 L3 且状态可用的实体；输出状态、历史和各控制动作 | 是可用实体能力集合，不等于 HA 全部实体；当前实现忽略传入的 user_id |
| `server/app/home_assistant/bridge.py` | `resolve` 对实体 ID、名称、别名做去首尾空格及忽略大小写后的精确匹配 | 本地执行，不消耗模型 Token；不支持房间或模糊检索 |

HA 当前通过 `/api/states` 读取状态，通过 `/api/services/{domain}/{service}` 控制设备，通过 `/api/websocket` 订阅状态变化。MCP 不在现有控制链中。

#### 3. 第一阶段：当前可实施方案

##### 3.1 提示词改造

将现实能力边界拆成两部分：

- 保留现有人设及现实执行约束，不因本次优化改写伴侣角色行为。
- 设备部分只写能力类别、在线概况和使用规则，不逐设备列出动作。

建议设备部分文案：

> 当前可通过工具查询和控制已授权的家庭设备。设备名称、可用性及支持动作以工具返回为准。名称明确时可以直接调用设备工具；无法匹配时先检索，存在歧义时询问用户。不得编造具体设备，不得在工具确认成功前声称操作完成。提出涉及具体设备的主动建议前，应先确认该设备及相应能力可用。

HA 未连接时使用明确的不可用概述。其他设备类别保持各自的可用性判断。后台完整能力集合仍可用于权限、调度和工具挂载，不因为精简模型文本而删除。

批次 A 可先将每台设备的多个动作压成一行，便于快速验证。它只是过渡模式，最终默认采用按需检索。

##### 3.2 本地设备目录

新增 `DeviceDirectory`（建议文件 `server/app/home_assistant/directory.py`），从现有授权配置、HA 实体/设备/区域元数据构建索引。

目录字段：实体 ID、显示名称、别名、HA domain、房间/区域、允许动作、隐私级别、状态可用性。品牌与型号仅在元数据可靠时纳入，不从名称猜测后作为确定事实。

目录留在应用内存；配置发布、HA 重连或元数据刷新时重建。状态变化更新可用性。查询和执行时仍检查当前权限，不能把索引中的旧授权当作执行许可。

房间来源优先使用 HA 区域信息，允许后台覆盖；没有区域信息时返回 null，并允许按名称检索。按实际持久化结构决定是否需要配置升级或数据库迁移。

当前 HA provider 忽略 user_id：不能把它描述为已有按用户隔离。若项目仍使用全局家庭授权，保持并明确该范围；对多用户或对外 MCP 开放前，必须增加用户/家庭作用域，并使其参与查询过滤和缓存键。

##### 3.3 新增 search_devices 工具

建议参数：

```json
{
  "query": "小米台灯",
  "room": "卧室",
  "domain": "light",
  "action": "turn_on",
  "limit": 5,
  "cursor": null
}
```

字段均可选；limit 默认 5、最大 5。无过滤条件时返回第一页授权设备，用于浏览；cursor 使用不透明游标。room/domain/action 是过滤条件，query 用于名称、别名及可信元数据检索。

建议返回：

```json
{
  "devices": [
    {
      "entity_id": "light.bedroom",
      "name": "卧室台灯",
      "room": "卧室",
      "available": true,
      "actions": ["turn_on", "turn_off", "set_brightness"],
      "confirmation_required_actions": [],
      "match_kind": "alias_exact"
    }
  ],
  "has_more": false,
  "next_cursor": null
}
```

以上为示例数据。默认不返回完整 HA attributes、原始注册表、凭据或不相关动作说明。读取授权和当前隐私级别过滤必须发生在排序、计数和分页之前，避免通过候选泄露未授权设备。

排序建议：实体 ID/名称/别名精确命中优先，其次房间和类型约束下的关键词匹配，再做轻量文本相似度排序。第一版不引入向量库或额外模型。相似度只决定候选顺序，不产生执行授权。

##### 3.4 查询与控制流程

1. 名称明确时，模型直接调用现有 `home_control` 或查询工具。
2. 后端精确匹配唯一实体后，检查当前授权、隐私、可用动作、参数和确认条件。
3. 精确匹配失败，返回 `ha_entity_not_found` 及建议调用 `search_devices` 的结构化提示。
4. 多个匹配返回 `ha_target_ambiguous`；模型查询候选或询问用户，不自动选择第一项。
5. 检索结果明确符合用户指定条件时，使用实体 ID 调用工具。仅有弱相似候选或条件不一致时仍需澄清，即使只返回一个候选。
6. 执行前重新校验，执行后沿用已有状态验证链路；结果不确定时报告未确认完成。

建议每轮最多两次设备检索；仍无法确定则询问用户，避免模型循环搜索。分页浏览可以进入下一用户回合。

##### 3.5 会话设备指代

建议新增会话级 `RecentDeviceReference`：entity_id、显示名称、来源 turn_id、确定方式、更新时间和授权作用域。只记录用户明确选定或成功精确匹配的设备，不把全部搜索候选保存成当前对象。

默认保留最近 3 个已完成用户回合且不超过 10 分钟（可配置的初始值）。只有一个明确的近期对象时，向模型附带一行引用信息；多个对象或切换话题后无法判断时询问。使用引用时重新校验权限。

设备引用仅解决“它是哪台设备”，不能作为用户对某个动作的确认。确认仍绑定实际设备、动作及参数，复用项目现有确认机制并检查各路径是否一致。

##### 3.6 工具挂载与结果预算

第一版保留少量通用家庭工具定义：检索、状态、历史、控制；根据连接状态和配置决定是否可用。不要把每个设备或动作注册成单独的模型工具，也不要仅靠关键词隐藏工具，导致口语表达无法调用。

历史查询限制条数和字段，优先摘要；搜索最多 5 项；工具输出尽量结构化。工具往返产生的消息也计入本轮 Token 统计。应用本地目录缓存不会自动减少已写入提示词的 Token。

##### 3.7 建议改动清单

| 文件/模块 | 改动 |
|---|---|
| `chat/service.py` | 用简短设备概述替代设备明细；挂载搜索工具；注入有限近期引用 |
| `chat/capabilities.py` | 区分内部完整能力和模型可见摘要；保留现实边界 |
| `home_assistant/manager.py` | 暴露目录查询入口，复用可用性与授权配置 |
| 新增 `home_assistant/directory.py` | 精确索引、筛选、排序、分页与更新 |
| `home_assistant/tools.py` | 新增搜索工具、错误指引和精简返回；保留执行门禁 |
| `config/models.py` 与后台实体页 | 必要时增加区域覆盖与别名维护字段 |
| `main.py` / 工具注册位置 | 注册新工具及目录依赖 |
| `server/tests/` | 新增真实行为回归，覆盖搜索、权限与提示词体积 |

具体注册位置与确认接口在实现时重新核对；当前工作区存在其他进行中的修改，不应覆盖它们。

#### 4. 第二阶段：引入 MCP

##### 4.1 两种方向分别实施

- Aria 作为 MCP 客户端：调用外部 MCP Server，扩展设备或其他外部服务。
- Aria 作为 MCP Server：把 Aria 的受控工具提供给其他 AI 应用。

本阶段优先第一种。第二种只有在出现对外复用需求时实施。

##### 4.2 统一接口与适配器

```text
聊天模型
   ↓ 统一工具接口
参数校验 / 身份与隐私 / 授权 / 确认 / 审计
   ├─ HA 适配器 → HA REST / WebSocket
   └─ MCP 适配器 → 外部 MCP Server → 目标系统
```

保持 `search_devices`、`home_get_state`、`home_get_history`、`home_control` 对模型的接口稳定。MCP 服务的工具名称和数据结构由适配器转换，不要求模型了解不同供应商细节。

建议新增 `server/app/integrations/mcp/`，包括连接管理、工具目录、schema 映射、调用适配和结果裁剪。SDK 版本和传输类型在实施时按目标服务及当时官方文档确定。

##### 4.3 MCP 工具发现与按需加载

1. 建立连接并协商服务能力，调用 `tools/list` 获取目录。
2. 目录缓存在应用侧；服务声明支持目录变化通知时响应变化，否则按需或定期刷新。
3. 只有配置允许的工具进入内部注册表，保留服务命名空间避免名称冲突。
4. 家庭功能仍向模型暴露稳定的少量通用工具；目录不直接全量注入。
5. 跨领域工具增多时再增加工具检索入口，按当前任务加载定义。动态加载必须接入模型调用循环，不能只注册检索工具却不把检索到的定义提供给后续请求。
6. 调用通过 `tools/call` 执行，结果转换为现有 `ToolResult` 并裁剪字段、条数和体积。

工具发现是应用行为；模型看到什么仍由 Aria 控制。更换协议后保留原全量提示词，不会实现本方案的 Token 目标。

##### 4.4 连接与执行约束

建议配置包含：server_id、enabled、transport、endpoint 或受信任启动命令、凭据引用、允许工具列表、超时、工具目录缓存时长。凭据通过现有 secret 通道管理，不进入模型上下文。

读操作可对短暂连接失败有限重试。写操作超时后先验证实际状态，不能自动重复调用或切换 HA 直连重发，防止 toggle 等动作执行两次。主备切换应发生在确定尚未发送动作时，或由后续明确的新请求触发。

外部返回文本仅作为工具数据，不能覆盖 Aria 的系统规则和授权范围。远端工具的描述或注解不能取代项目自己的写操作分类和确认判断。

##### 4.5 试点与 HA 替换条件

先接入一个有实际需求的只读 MCP 工具，验收连接、发现、映射、隐私过滤、超时与 Token 预算，再接入写工具。

HA MCP 是否替换直连需逐项核对，不能假定与现有 API 等价：

| 能力 | 必须验证 |
|---|---|
| 设备查询 | 能否检索并稳定映射 entity_id；能否限制授权范围 |
| 当前状态 | 字段、时效和不可用状态是否足够 |
| 历史与日志 | 是否提供项目现有历史/Logbook 需求 |
| 控制动作 | 亮度、温度、媒体和音量等动作及参数是否齐全 |
| 状态订阅 | 是否支持主动感知需求；缺失时继续保留 HA WebSocket |
| 执行结果 | 能否验证成功、失败和不确定结果 |

允许混合模式，例如 MCP 提供额外能力，HA WebSocket 继续承载实时状态。无需为统一协议而移除必要链路。

##### 4.6 可选：Aria MCP Server

在需要其他 AI 客户端复用 Aria 时，暴露上述稳定工具接口。入口完成调用方认证与用户/家庭作用域映射，复用授权、确认、审计和执行层，不能直接旁路调用 HA。

需要确认的动作返回待确认结果；不可把外部调用方传入的简单 `confirmed: true` 当成已获用户确认。具体确认票据或交互方案单独设计，并绑定主体、目标、动作、参数、有效期及一次性消费。

#### 5. 验收与观测

##### 5.1 Token 和耗时基线

固定模型、配置和对话样本，对比全量、合并、按需三种模式。设备规模使用 10、50、200 个模拟授权实体，每个场景记录：

- 模型输入与输出 Token；每轮所有模型调用合计。
- 工具定义、设备上下文、工具结果的独立体积；无法准确分拆 Token 时明确标记为估算。
- 工具往返数、总耗时和 P50/P95。
- 匹配成功、澄清、误控和不确定执行结果数量。
- 若供应商返回缓存用量，分别记录缓存输入与非缓存输入；不把缓存折扣当作提示词变短。

硬性目标：普通闲聊提示词不含逐设备明细；增加设备数量不再线性扩大设备部分常驻输入；无越权和误控。节省比例与延迟变化以实测报告为准。

##### 5.2 必测行为

| 场景 | 预期 |
|---|---|
| 普通闲聊 | 不携带全量设备清单，不额外搜索 |
| 名称/别名精确命中 | 不强制增加搜索往返 |
| 口语称呼或房间+类型 | 返回少量相关候选 |
| 两个候选均合理 | 澄清，不选择第一项执行 |
| 不存在的设备 | 明确未找到，不伪造成功 |
| “把它关掉” | 仅复用明确且未过期引用 |
| 授权撤销或隐私切换 | 搜索不泄露，执行重新拒绝 |
| HA 离线 | 提示不可用，不使用旧清单承诺操作 |
| 空调等确认动作 | 保持既有确认要求，参数变化后重新核对 |
| 全设备浏览 | 支持概览和分页，不截断后假称完整 |
| 主动建议 | 具体设备能力有查询依据 |
| MCP 写调用超时 | 不自动重发，验证并报告实际或不确定结果 |

#### 6. 发布和回退

建议提供设备上下文模式开关：`full`、`compact`、`on_demand`，名称为设计建议。先使用回放样本验证，再将 `on_demand` 设为默认；保留短期回退。回退只改变提示词策略，不改变权限和确认检查。

MCP 使用独立配置开关，默认关闭。启用某个设备适配器时避免重复注册同名工具。回退前识别未完成写操作，禁止因切换后端而重复执行。

批次 A/B 验收后即可结束 Token 优化任务；C/D 按外部集成需求启动，不作为前阶段交付前提。
