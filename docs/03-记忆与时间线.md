### 1. 背景与问题

当前长期记忆系统已经具备持久化、检索、来源溯源、冲突、纠错、删除台账、L2 隐私隔离和 pgvector 召回等能力，但它有一个根本假设：**长期记忆默认都是“关于用户”的**。

这一假设会导致助手自身的稳定信息无法形成跨会话连续性。例如：

```text
会话 A：
用户：你的三围是多少？
助手：91-63-88。

会话 B：
用户：你的三围是多少？
助手：82-58-84。
```

两个回答即使使用同一个 Persona 版本，也可能不同。原因不是 Persona 发布失败，而是第一次回答中的“助手自述事实”没有被长期记忆系统保存并在下一次对话中召回。

这个问题不应通过把所有事实写死到 Persona 中解决。Persona 应描述“她是谁、怎么说话、行为边界是什么”，长期对话中逐步形成的自述信息、用户信息和共同经历应由记忆系统持久化。

本设计将现有单主体记忆扩展为：

```text
用户记忆 user
助手记忆 assistant
共同记忆 shared
```

并确保它们在沉淀、检索、冲突、隐私、删除和管理后台中使用同一套可追溯机制。

---

### 2. 设计目标

#### 2.1 必须实现

1. 用户稳定信息可以跨会话持续记住，维持现有能力。
2. 助手自己明确说出的稳定信息可以持久化，并在后续独立会话中召回。
3. 共同约定、共同经历可以作为独立主体保存，而不是强行归到用户或助手。
4. 同一稳定属性出现新值时不得静默覆盖旧值，必须进入冲突/纠错流程。
5. 助手重复复述已注入的记忆时，不得把自己的复述当成新证据，防止记忆“自我喂养”。
6. 已有 `user_id` 数据隔离、L0～L3 隐私闸门、版本链、来源链和硬删除语义必须保持。
7. 管理后台可以清楚区分“关于用户 / 关于助手 / 关于双方”。
8. 直接询问稳定属性时，已有记忆应高概率确定性命中，不能只依赖模糊向量召回。
9. 生成回复如果明显违反已建立的稳定事实，应有一致性检查，不允许矛盾答案直接成为新事实。

#### 2.2 非目标

- 不把长期记忆重新塞回 Persona。
- 不把“助手说过一句话”全部保存为永久记忆。
- 不把模型自由文本当作可信现实世界事实。
- 不因为助手拥有“角色身体设定”就认为它拥有现实世界身体能力。
- 不在本阶段实现多助手市场、完整世界模型或知识图谱。

### 3. 核心概念

#### 3.1 所有权与主体必须分离

现有 `memory.user_id` 的真实语义应继续保持为：

> **这条记忆属于哪个用户的数据空间。**

它是授权和隐私边界，不能因为记忆内容“关于助手”就删掉。

新增的主体字段回答另一个问题：

> **这条记忆描述的是谁。**

因此一条助手记忆仍然属于某个用户的数据空间：

```text
owner/user_id = 浩宇
subject_kind = assistant
subject_key = assistant:primary
content = 助手自述三围为 91-63-88 厘米
```

这样不同用户之间的“助手关系记忆”不会串库。

#### 3.2 三类主体

| subject_kind | 含义 | 示例 |
|---|---|---|
| `user` | 关于用户本人 | 用户不吃香菜；用户在杭州工作 |
| `assistant` | 关于当前伴侣/助手自身 | 助手喜欢甜食；助手自述身高 160 cm |
| `shared` | 关于双方关系、共同经历、共同约定 | 双方约定晚上一起看电影；第一次使用名称“雏田” |

#### 3.3 subject_key

仅有 `subject_kind` 对当前单助手实例已经够用，但为了以后支持多个伴侣实例，本阶段直接预留 `subject_key`：

```text
user:self
assistant:primary
shared:user-assistant
```

未来如果出现多个伴侣实例，无需改表，只需把 key 扩展为：

```text
assistant:<companion_uuid>
shared:<companion_uuid>
```

当前系统只有一个 Persona 发布链，因此 `assistant:primary` 是稳定身份，不随 Persona v3 → v4 或名称 Aria → 雏田改变。

Persona 版本更新默认继承既有助手记忆。未来如果真正创建“另一位独立伴侣”，再创建新的 `subject_key`。

### 4. 数据模型

建议新增迁移：

```text
0010_memory_subject_scope
```

#### 4.1 memory 表新增字段

```sql
ALTER TABLE memory ADD COLUMN subject_kind VARCHAR(16) NOT NULL DEFAULT 'user';
ALTER TABLE memory ADD COLUMN subject_key VARCHAR(160) NOT NULL DEFAULT 'user:self';
ALTER TABLE memory ADD COLUMN fact_key VARCHAR(160) NULL;
ALTER TABLE memory ADD COLUMN origin_kind VARCHAR(32) NOT NULL DEFAULT 'user_statement';
```

约束：

```text
subject_kind ∈ user | assistant | shared

origin_kind ∈
  user_statement
  assistant_statement
  shared_turn
  system_event
  manual
```

#### 4.2 为什么需要 fact_key

现有冲突判断主要依赖向量相似度。对数字属性并不可靠：

```text
“助手三围为 91-63-88”
“助手三围为 82-58-84”
```

两句话语义高度相似，但最终不能靠一个通用余弦阈值决定它们是支持还是冲突。

对“槽位型稳定事实”增加可选 `fact_key`：

```text
profile.name
profile.nickname
profile.birthday
profile.height
profile.weight
profile.measurements
preference.food
preference.drink
preference.color
```

例：

```text
subject_kind = assistant
subject_key  = assistant:primary
type         = semantic
fact_key     = profile.measurements
content      = 助手自述三围为 91-63-88 厘米
```

`fact_key` 只在提取器能稳定确定时填写。无法可靠归一化的普通经历仍为 `NULL`，继续走现有混合相似度判定。

#### 4.3 索引

新增：

```text
ix_memory_user_subject_status
  (user_id, subject_kind, subject_key, status, importance)

ix_memory_fact_slot
  (user_id, subject_kind, subject_key, fact_key, status)
```

现有向量索引继续保留。

#### 4.4 现有数据迁移

现有全部记忆都是按“关于用户”语义生成，因此升级时无歧义回填：

```text
subject_kind = user
subject_key = user:self
fact_key = NULL
origin_kind = user_statement / manual
```

不改任何已有 memory id、版本链、source、向量或删除台账。

### 6. 记忆沉淀管线

#### 6.1 从“只提取用户消息”改为“提取完整已完成回合”

当前流程：

```text
user message
  → 回复生成
  → 只对 user message 做 MemoryExtractor
```

目标流程：

```text
user message
  → 记忆检索
  → LLM 回复
  → 回复完整提交
  → TurnMemoryExtractor
       ├─ 用户候选 user
       ├─ 助手候选 assistant
       └─ 共同候选 shared
  → MemoryIngester
```

只对 **completed** 回合进行助手记忆沉淀。被取消、被打断、生成失败的半句话不得成为助手稳定事实。

#### 6.2 TurnMemoryExtractor 输入

建议接口：

```python
extract_turn(
    *,
    user_message: MessageView,
    assistant_message: MessageView,
    persona_name: str,
    privacy_level: PrivacyLevel,
    retrieved_memory_ids: Sequence[int],
    backend: ExtractionBackend | None,
) -> list[MemoryCandidate]
```

必须使用解析后的可见 `AgentReply.text`，不把 `<aria_control>` 控制块、TTS 元数据或动作 JSON 送进记忆提取器。

#### 6.3 LLM 提取输出

utility 模型建议输出：

```json
{
  "candidates": [
    {
      "subject": "assistant",
      "type": "semantic",
      "fact_key": "profile.measurements",
      "content": "助手自述三围为 91-63-88 厘米",
      "importance": 0.75,
      "confidence": 0.92,
      "assertion": "explicit"
    }
  ]
}
```

`assertion` 仅作为提取阶段判定字段，不一定需要落库：

```text
explicit         明确事实陈述
uncertain        不确定、猜测、可能
hypothetical     假设/举例
quoted           引用他人说法
roleplay_action  纯舞台动作或虚构现场行为
```

默认只自动沉淀 `explicit`。

#### 6.4 用户消息提取

维持当前原则：

- 用户说“我不吃香菜” → `subject=user`
- 用户说“我周五要汇报” → `subject=user`
- 用户说“记住，你的生日是 12 月 27 日” → 可以产生 `subject=assistant`，但来源仍是 user message
- 用户说“以后我们周五晚上看电影” → 可以产生 `subject=shared`

#### 6.5 助手消息提取

只保存具有长期价值且明确的自述：

- “我的三围是 91-63-88” → assistant / semantic
- “我喜欢桂花味的甜点” → assistant / preference
- “你以后可以叫我雏田” → assistant / semantic 或 shared 约定

不保存：

- 普通寒暄
- 临场措辞
- 舞台动作描写
- “也许”“大概”“如果我是……”等不确定表达
- 为解释问题临时举出的数字
- 模型引用用户内容形成的复述

#### 6.6 共同记忆生成边界

`shared` 必须比 assistant 更严格，防止模型凭一句台词创造现实经历。

可以保存：

- 用户和助手在对话中明确达成的约定
- 有用户消息或系统事件作为证据的共同经历
- 系统真实检测到的事件，并且双方随后围绕它互动

不能仅凭助手一句：

```text
“昨天我们一起去了训练场。”
```

就写成 shared 现实经历。

如果没有用户消息、设备事件或既有记忆支持，这类内容最多视为角色叙述，不得成为“共同现实事件”。

### 7. 防止记忆自我强化

这是助手记忆最重要的保护之一。

假设数据库已有：

```text
#42 助手自述三围为 91-63-88
```

本轮检索把 #42 注入模型，助手随后回答：

```text
“我的三围是 91-63-88。”
```

如果再把这句话当作新证据，系统会形成：

```text
记忆 → prompt → 模型复述 → 新证据 → 提高重要性 → 更容易被检索
```

这是错误的正反馈。

因此每轮提取必须拿到 `retrieved_memory_ids`。

规则：

1. assistant candidate 与本轮已注入记忆表达同一事实时，标记为 `echo`；
2. `echo` 不创建新 memory；
3. `echo` 不执行 `register_support`；
4. `echo` 不增加 importance；
5. 正常的“被检索访问”仍由现有 `access_count` 记录。

只有真正独立的新证据才能增加支持度。

### 8. 冲突与纠错

#### 8.1 槽位事实优先使用 fact_key

如果候选有 `fact_key`，优先查询：

```text
same user_id
same subject_kind
same subject_key
same type
same fact_key
status = active
```

结果：

```text
没有旧值       → CREATED
同值/等价值     → SUPPORTED
不同值         → CONFLICT
```

不允许新值自动覆盖旧值。

#### 8.2 无 fact_key 的普通记忆

继续使用现有相似度策略：

```text
>= support_threshold  → 支持
>= conflict_threshold → 冲突
否则                  → 新增
```

但相似检索必须增加主体过滤，不能拿“用户喜欢咖啡”去和“助手喜欢咖啡”做同一事实冲突。

#### 8.3 冲突例子

已有：

```text
assistant / profile.measurements / 91-63-88 / active
```

新候选：

```text
assistant / profile.measurements / 82-58-84
```

必须：

```text
旧值保持 active
新值进入 conflict
conflict_with → 旧值 id
```

管理后台或明确用户纠错后才能 adopt 新值。

#### 8.4 来源权威等级

权威等级只用于帮助 UI 和未来自动策略，P5 默认仍不静默替代：

##### user 主体

```text
用户明确纠错 > 用户明确自述 > 系统推断
```

##### assistant 主体

```text
管理员手工确认
> 用户明确设定/纠错
> 助手明确自述
> 模型推断
```

##### shared 主体

```text
系统真实事件
> 双方明确约定
> 单方陈述
```

P5 阶段不根据权威等级自动覆盖，只用于冲突排序和人工裁决展示。

### 9. 检索设计

#### 9.1 每轮默认可见主体

当前用户与主助手的一轮对话默认检索：

```text
user:self
assistant:primary
shared:user-assistant
```

所有候选仍必须首先通过：

- user_id 数据隔离
- privacy_level
- status=active
- valid_from / valid_to
- embedding_version

#### 9.2 主体意图提示

加入轻量 `SubjectHint`：

```text
“我不吃香菜对吧”      → user 高权重
“你的生日是什么”      → assistant 高权重
“我们上次聊了什么”    → shared 高权重
无法判断              → 三类都检索
```

它只影响排序，不作为安全过滤，避免中文代词复杂句误判后直接漏掉正确记忆。

#### 9.3 稳定属性的直接槽位召回

对于明显的属性询问，先做 `fact_key` probe，再跑向量/词法召回：

```text
“你的三围是多少”
  → subject_hint=assistant
  → fact_key=profile.measurements
  → 精确查询 active slot
  → 再补充普通混合检索
```

这样不依赖 embedding 是否恰好把“三围”“比例”“身材数据”排进 Top-K。

#### 9.4 排序

现有：

```text
相关性 0.55
重要性 0.25
pin +0.2
episodic recency
```

建议新增：

```text
subject_hint bonus 0～0.15
exact_fact_key bonus 1.0，保证槽位事实优先
```

`exact_fact_key` 不参与普通归一化竞争，它属于确定性候选，优先占用一个 Top-K 位置。

#### 9.5 配额

继续保留类型配额，同时增加保护规则：

```text
精确 fact_key 命中不得被类型配额挤掉
```

暂不设置死的 subject 配额，避免“只问助手事实却被强塞用户记忆”。

### 10. Prompt 注入格式

现有：

```text
【相关记忆】以下是关于用户的长期记忆……
```

改为：

```text
【长期记忆】
以下内容来自可追溯的长期记忆。优先遵守 active 的稳定事实；不要把不同主体混淆。

[关于用户]
- [preference] 用户不吃香菜

[关于你自己]
- [semantic][profile.measurements] 你此前明确自述三围为 91-63-88 厘米

[关于你们]
- [episodic] 你们上周讨论过《星际穿越》

规则：
1. 已有稳定事实时不要自行给出不同值。
2. 不确定时可以说不确定，不要假装“记得”。
3. 助手可以拥有完整、稳定、生活化的角色自我档案，包括身高、体重、三围、外貌、生日、偏好、习惯和穿衣风格等；这些属于角色连续性，可以像长期伴侣一样自然回答，不应因为软件运行载体而主动否认。
4. 角色身体设定不等于现实物理执行能力。移动、触碰、做饭、设备控制等现实动作仍以【当前可执行能力】为唯一依据。
5. 用户明确询问现实系统身份或是否具有真实人类生物身体时应保持诚实，但不需要在普通陪伴对话中反复主动声明“我是 AI”。
```

这一条把“角色连续性”与“现实能力”明确拆开：角色层可以完整、自然并长期稳定，执行层必须严格服从真实能力注册表。

```text
记忆可以说：我此前一直把自己的身高设定为 160 cm
能力不能说：那我们现在去训练场吧
```

除非训练场/导航/设备能力真的存在于运行时能力列表。

### 11. 生成后事实一致性检查

只靠 prompt 不能保证强模型永远不违背记忆，因此增加 `MemoryConsistencyGuard`。

#### 11.1 第一阶段：确定性检查

只检查本轮检索到的高置信槽位事实，尤其是：

- 数字
- 日期
- 名称
- 枚举型偏好

例：

```text
注入：profile.measurements = 91-63-88
回复：82-58-84
```

检测到明显冲突后：

1. 不提交矛盾回复；
2. 用原请求 + 冲突事实做一次 repair；
3. repair 最多一次，防止循环；
4. repair 仍失败时使用安全降级回复，例如“我记得之前说的是 91-63-88”。

#### 11.2 第二阶段：语义矛盾检查

后续可让 utility 模型做 NLI/contradiction 判断，但不作为 P5 首批阻塞项。

#### 11.3 记录

`decision_meta.memory` 增加：

```json
{
  "consistency": {
    "checked": true,
    "repaired": false,
    "conflict_memory_ids": []
  }
}
```

### 12. 隐私设计

#### 12.1 user_id 仍是硬隔离边界

不论 subject 是 user / assistant / shared，所有 memory 均必须带 owner `user_id`。

任何检索都不能跨 user_id。

#### 12.2 L3

保持现状：

```text
L3 永不进入持久记忆
```

#### 12.3 L2

保持保守默认：

```text
来自 L2 回合的任何持久候选仍为 L2
L2 memory 只进入 private 本地模型上下文
```

即使内容是助手自述，也不因为“看起来不是用户隐私”自动降成 L1。

这样避免从亲密上下文中自动抽取出可云端外发的衍生信息。

如果未来确实需要某条助手设定跨 L1/L2 全局一致，必须走显式“提升为全局助手记忆”的人工操作，并留下审计记录，不能自动降隐私级别。

#### 12.4 L2 提取策略调整

当前 L2 utility 提取器只允许事件级概括，禁止身体/生理细节。

本设计首批实现仍保持该规则，不为了一个示例破坏既有隐私边界。

因此：

- L1 中建立的助手稳定事实可正常持久化；
- L2 中出现的敏感细节默认不会被抽成具体身体数据；
- 如用户明确希望某项设定永久化，可通过管理后台手动创建对应 subject=assistant 的记忆，并选择合适隐私级别。

### 13. Persona 与记忆的职责边界

#### Persona 保存

- 名称/当前身份展示
- 性格核心
- 说话风格
- 与用户关系基线
- 行为边界
- 默认情绪
- 表情/声音映射

#### assistant memory 保存

- 聊天中逐步建立的自述事实
- 自己的稳定偏好
- 明确形成的长期习惯/称呼
- 需要跨会话连续的角色细节

#### shared memory 保存

- 双方共同经历
- 共同约定
- 关系里程碑

原则：

```text
Persona = 角色规则和基线
Memory = 角色在时间中形成的经历与连续性
Runtime Capability = 此刻现实中真正能做什么
```

三者不能互相替代。

---

### 14. Reality Grounding 与助手记忆

助手可以有“角色记忆”，但不能把角色叙事升级成现实能力。

例如允许：

```text
“我记得我之前告诉过你，我喜欢桂花糕。”
```

不允许仅因为 Persona 是忍者或记忆里提过训练：

```text
“我们现在去训练场，我给你演示柔拳。”
```

现实动作建议必须继续由 `RuntimeCapabilityProvider` 提供的当前在线、已授权能力约束。

未来接入电视后：

```text
device.tv.living_room.power
```

存在且在线时，助手才可以自然转移话题：

```text
“不聊这个啦，要不要看会儿电视？我可以帮你打开。”
```

记忆负责“我是谁、我们经历过什么”，能力系统负责“现在真的能做什么”。

### 22. 失败与降级策略

#### 提取器不可用

- 用户记忆继续使用现有 RuleBasedExtractor 回退；
- 助手/共同记忆首批可以选择“本轮不沉淀”，不能用过度宽松规则错误写入；
- 聊天回复绝不能因为记忆提取失败而失败。

#### embedding 不可用

- 槽位事实仍可通过 fact_key 精确检索；
- 普通记忆降级到 lexical；
- 回合继续。

#### consistency guard 失败

- 检查器异常时记录 warning；
- 不修改已有 active memory；
- 不把矛盾新值自动写成 active；
- 后续提取最多产生 conflict。

### 27. 架构决策

#### ADR-MEM-01：事实不写进 Persona

Persona 是行为基线，不是长期事实数据库。聊天中形成的信息全部进入 MemorySystem。

#### ADR-MEM-02：user_id 是 owner，不是 subject

保留现有 `user_id` 作为权限边界，新增 subject 描述记忆对象，避免破坏隔离语义。

#### ADR-MEM-03：助手自述可以形成长期连续性

助手明确、稳定、非假设性的自述允许形成 assistant memory。它是“角色连续性事实”，不是现实世界证明。

#### ADR-MEM-04：共同经历需要外部或用户证据

assistant 单方叙述不能创造 shared 现实事件，避免模型把幻觉固化成共同经历。

#### ADR-MEM-05：槽位事实必须显式冲突

带 `fact_key` 的稳定属性不依赖向量阈值判定冲突，新值不得静默覆盖旧值。

#### ADR-MEM-06：禁止记忆自我喂养

本轮由 memory 注入导致的 assistant 复述不是独立证据，不提升重要性，也不创建新 memory。

#### ADR-MEM-07：角色连续性与现实能力分离

MemorySystem 决定“记得什么、自己是谁以及长期形成了哪些稳定自我信息”，RuntimeCapabilityProvider 决定“现在现实中真正能做什么”。助手的角色身体档案、生活偏好和自我叙述可以作为长期自我记忆自然表达，但不能因此推导出未接入的现实移动、触碰或设备执行能力。任何现实动作建议必须服从后者。

---

### 28. 最终验收定义

本设计真正完成，不以“数据库多了 subject 字段”为标准，而以用户体验为标准：

```text
第一次会话：
助手建立一个新的稳定自述事实 F。

第二个完全独立的新会话：
用户用不同措辞询问 F。
助手能够召回同一事实，而不是重新编造。

第三个会话：
用户提出与 F 冲突的新值。
系统保留冲突证据，不静默覆盖。

删除或纠错 F 后：
后续对话只使用当前 active 版本。
```

同时必须满足：

```text
不跨用户串记忆
不跨隐私边界出站
不把助手复述当新证据
不把角色设定当现实能力
不因记忆故障阻断聊天
```

达到这些条件后，才算“助手自身信息作为持久化记忆”真正完成。

### 1. 目标

系统不要求 AI 永远把所有历史都放在“长期记忆”中。更自然的目标是：

> **重要的信息平时就记得；不重要的细节允许忘记；需要时可以根据时间、人物、设备、主题等线索回查历史证据。**

因此把“记忆”和“历史”分开：

- `Memory` 回答“什么值得长期记住”；
- `Timeline` 回答“过去发生过什么”；
- `Source` 保存真实原始证据；
- AI 可以明确表示“现在想不起来”，但在有线索时可以发起历史检索；
- 搜不到时必须承认没有证据，不得补写一个看似合理的答案。

---

### 2. 四层结构

```text
Working Context
  当前会话 / 当前状态
        ↓
Long-term Memory
  平时就记得的重要信息
        ↓
Timeline Index
  可按时间和语义翻阅的历史目录
        ↓
Source Records
  message / event / device / tool 等原始事实源
```

#### 2.1 Working Context

- 最近对话消息；
- 当前回合状态；
- 当前环境最小快照；
- 当前可用设备/工具能力；
- 生命周期为当前会话或短时间窗口。

#### 2.2 Long-term Memory

由 `30` 定义：

- 主体：`user / assistant / shared`；
- 类型：`semantic / preference / commitment / episodic / emotional`；
- 稳定槽位 `fact_key`；
- 来源、冲突、纠错、版本链、隐私和删除闭环。

长期记忆不是完整历史仓库，只保存具有持续价值的信息。

#### 2.3 Timeline Index

统一索引对未来可能有回溯价值的历史信息：

- 对话主题与消息引用；
- 设备状态变化和聚合事件；
- 工具执行结果；
- 日历/提醒事件；
- 感知引擎产生的持久语义事件；
- 系统中其他允许持久化的事实来源。

#### 2.4 Source Records

原始事实仍保留在其领域表中，例如：

- `message`；
- `event`；
- 未来 device state / aggregate；
- tool execution；
- calendar/reminder 等外部连接记录。

Timeline 是索引，不应无条件复制全部原始正文。

### 4. 什么进入 Timeline

#### 4.1 对话

`message` 本身已经带时间和会话 ID，因此第一版不需要为每一句话完整复制正文。

建议两种方式并存：

1. message 可直接作为 Source 被 HistoryRecall 搜索；
2. 对具有主题价值的对话片段生成 `conversation.topic` TimelineEvent，保存摘要和消息范围引用。

例如：

```text
21:30～21:42
conversation.topic
summary = 双方讨论周末观看《星际穿越》
source = conversation + message range
```

#### 4.2 设备

禁止把高频遥测全部永久塞入 Timeline。

```text
raw telemetry
   ↓ 短期窗口/短期保留
aggregate
   ↓
meaningful event
   ↓
Timeline
```

示例：

- 每秒温度 24.31/24.32/24.31：不进 Timeline；
- 09:00～10:00 平均 24.5℃：可作为聚合数据中期保留；
- 09:37 温度快速升至 31℃：可生成 TimelineEvent。

具体 retention 仍以 `10` 为统一真源。

#### 4.3 Tool / Calendar / System

只有成功完成且未来可能需要追溯的结果进入 Timeline。失败重试日志留在可观测系统，不应伪装成“发生过的用户事件”。

---

### 5. 历史回溯触发

普通聊天默认只使用 Working Context + Long-term Memory。只有满足以下条件之一才进入 History Recall：

1. 用户明确询问过去：`之前 / 昨天 / 上周 / 那次 / 以前 / 去年`；
2. Memory 没有答案，但问题明显依赖历史事实；
3. 用户提供时间、人物、设备、地点或主题线索并要求查找；
4. 模型需要验证一个可能来自历史的事实，而不是凭空补全。

不会因为“Memory 没命中”就每轮自动扫描全部历史。

### 7. TemporalQueryParser

时间范围是一等公民，不只是 embedding 文本的一部分。

第一版支持：

```text
刚才
今天早上 / 下午 / 晚上
昨晚
前几天
上周 / 上周末
这个月 / 上个月
去年
过去/最近 N 分钟|小时|天|周
```

全部转换为用户时区下的绝对 `start_at/end_at`。

2026-09-15 相对时长解析增强（`app/timeline/recall.py`）：

- 数量词同时接受阿拉伯数字与中文数字（一~九十九，含"两"与"十X / X十"组合），例如"最近三小时""过去两周"；
- 单位新增"周"；
- 无明确时长的"最近"（如"总结下最近的浏览记录"）不再静默放弃，按最近 24 小时生成时间窗——否则活动回顾整条链路对这类高频问法解析不出窗口。

第二阶段支持锚点时间：

```text
我回家以后
吃饭之前
上次打开电视的时候
```

流程是先搜索锚点事件，再生成相对时间窗口。

### 8. 历史检索策略

Timeline 排序综合：

- 时间范围匹配；
- lexical / FTS；
- embedding 语义相关度；
- entity 命中；
- actor / event_type；
- importance。

第一版不固定永久权重，通过 P5/P6 的真实数据校准。

#### 8.1 渐进扩大范围

禁止无边界扫库。

例如“前阵子说的那个游戏”：

1. 先查 30 天；
2. 无结果则扩大至 90 天；
3. 仍无结果时，优先向用户询问更具体线索；
4. 单回合 Timeline Search 最多 2～3 次。

### 9. Source Expansion

Timeline 命中只是候选目录。需要准确回答时，再根据 `source_type/source_id` 回原始领域表取有限范围证据。

例如：

```text
Timeline: 21:30～21:42 讨论电影
   ↓
Source Expansion
   ↓
读取该范围 4～8 条 message
   ↓
构造证据上下文
```

不把整段会话、整天设备数据全部塞回 LLM。

### 10. 回答模式与可观测性

每轮回答增加内部 `recall_mode`：

```text
working     当前上下文即可回答
memory      长期记忆命中
timeline    通过历史索引找到
source      进一步读取原始证据后回答
none        没有足够证据
```

建议写入：

```json
{
  "recall": {
    "mode": "timeline",
    "timeline_ids": [9182, 9189],
    "memory_ids": [],
    "time_range": {
      "start_at": "...",
      "end_at": "..."
    },
    "search_count": 1
  }
}
```

日志只记录 ID、范围、原因码和耗时，不复制敏感正文。

### 11. “忘记”是允许的

系统必须区分三种体验：

#### 11.1 平时就记得

来自 Memory：

> 你不吃香菜，我记得。

#### 11.2 一时想不起，但可以翻历史

> 我没有把这个当成长期记忆，不过你说大概是上周。我查了一下，是上周三晚上我们聊到的《星际穿越》。

#### 11.3 没有证据

> 我查了那段时间的记录，没有找到能确定的内容。你如果还记得大概月份或当时的话题，我可以再缩小范围。

禁止第四种行为：**Memory 没有、Timeline 没有、Source 也没有，但模型编出一个答案。**

### 12. Memory Promotion

新增 `MemoryPromotionService`，把 Timeline 中反复出现或明显重要的信息转成 MemoryCandidate。

#### 12.1 高优先级

- 用户明确“记住……”；
- 稳定身份事实；
- 稳定偏好；
- 明确承诺；
- 重要关系事件；
- 经过多次独立证据支持的稳定模式。

#### 12.2 默认只留 Timeline

- 今天午饭吃了什么；
- 临时看到什么；
- 一次性设备状态；
- 普通闲聊细节；
- 没有未来价值的偶发信息。

#### 12.3 从历史形成印象

例如连续数周的 Timeline 都显示“睡前打开卧室风扇”，反思任务可提出：

```text
user preference / routine candidate:
用户睡前通常会打开卧室风扇
```

候选仍必须经过现有 MemoryIngester、冲突和隐私规则，不能直接写成 active 事实。

### 13. 与多主体记忆的关系

`30` 与本文不是替代关系：

```text
30：长期记忆描述谁、事实如何稳定
31：什么要长期记、忘了以后如何回查
```

长期记忆继续区分：

```text
user
assistant
shared
```

Timeline 则更偏向事件视角，记录 `actor`、参与者、来源和时间。

### 14. 隐私与数据保留

隐私等级仍采用项目 L0～L3：

| 隐私 | Timeline | Memory | 原始数据 |
|---|---|---|---|
| L0 | 可按策略持久化 | 可 | 按 retention |
| L1 | 用户域内可持久化 | 可 | 按 retention |
| L2 | 仅允许策略批准的脱敏事件/摘要 | 可脱敏沉淀 | 强制本地处理 |
| L3 | **禁止持久化** | **禁止** | 仅实时有界内存 |

设备的 `raw_retention / aggregate_policy / timeline_policy` 归 `10` 的数据保留体系管理，本文只定义进入 Timeline 的语义。

### 15. 删除闭环

Timeline 不能成为删除后的数据旁路。

删除 Source 时必须重新处理相关：

```text
Source
  ↓
Timeline index
  ↓
Memory source refs / derived memory
```

要求：

- TimelineEvent 具有可追溯 `source_type/source_id`；
- 删除会话时清理或失效相应 Timeline；
- 如果某 Memory 还有其他独立来源，不因删除单一来源误删整条事实；
- deletion ledger 扩展到 timeline 实体；
- 备份恢复后重放删除台账，防止 Timeline 索引复活。
