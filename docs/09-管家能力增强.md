# 管家能力增强：行动闭环与自主性分期方案

> 2026-09-29。本文定义借鉴 Jarvis（钢铁侠管家原型）与 Hermes（Nous Research 自托管 agent 框架）设计的一批增强工作流：有界工具循环、语义记忆检索、邮件感知、技能蒸馏、长任务委派、上下文压缩与透明度汇报。原则：借它们的产品形态与闭环设计，不借它们的宽松默认——Aria 的确认预览、A0-A3 风险分级、隐私出口闸门与删除台账是既有资产，所有新增能力在这套护栏内扩展。

当前实现：BTL-01 有界工具循环已实施（见第 1 节）——`tools.max_tool_rounds` 从 `Literal[1]` 放宽为 1-4 的受检区间，聊天管线（流式与非流式）按轮次执行「补全 → 单工具执行 → 结果回填 → 再补全」直到模型不再调用工具、触发预览直答或到达轮次上限；每轮仍走 EgressGuard 与 ToolLedger，全部轮次的工具轨迹写入 `decision_meta.tool_rounds`。预览类工具（`mail_send`、`pnkx_*`）保持服务端确定性直答，副作用工具执行后强制收束为无工具终答，与既有安全语义一致。其余工作流（SEMB/MAILW/DIST/DELEG/CTX/RPT）为方案拆解，未实施。

## 0. 背景与参照

Hermes 值得借鉴的是三件事：闭环学习（复杂任务完成后沉淀为可复用技能）、后台自动化产品化（自然语言描述的周期任务无人值守执行、结果投递到任何表面）、以及多平台会话连续性（任何表面可打断、可接续）。Jarvis 原型值得借鉴的也是三件事：预先计算先于主动开口（主动消息携带真实内容而非"要不要我帮你查"）、随时可问责（"你今天做了什么/为什么打扰我"有确定性答案）、以及委派-汇报语义（"我正在处理，稍后向你汇报"）。

明确不抄：免确认执行外部动作、默认开放的工具自主度、无隐私分级的云端依赖。Aria 的路线是每一步自主性都对应一个可验证的护栏。

## 1. A 工作流：有界工具循环（BTL）

问题：v1 每轮最多执行一次工具调用，跟进补全时 `tool_choice="none"`——模型不能看结果后链式调用、不能自我修正。"查明天日程 → 冲突就查组织者邮箱 → 起草改期邮件"这类自然请求无法一次完成。

设计（BTL-01，已实施）：

- 配置：`ToolsConfig.max_tool_rounds` 由 `Literal[1]` 改为 `Annotated[int, Field(ge=1, le=4)]`，默认 1（行为不变），Admin 可调。上限取 4 是成本与延迟的折中，每轮都是一次完整 LLM 补全。
- 循环语义：第 1..N-1 轮若模型返回工具调用则执行（仍每轮至多一个，`multiple_tool_calls_not_allowed` 保留），结果回填后带着原工具目录再补全（`tool_choice` 恢复 auto）；第 N 轮强制 `tool_choice="none"` 收束为纯文本终答。
- 收束条件（满足其一即停）：模型不再调用工具；执行的工具有确定性直答（`mail_send` 预览回执、`pnkx_*` 本地渲染）；轮次耗尽。副作用工具（写操作）执行后不再继续循环，与"计划-确认-执行"链的边界一致。
- 审计：`decision_meta.tool_calls` 自然扩展为记录全部轮次的执行明细；多轮时另加紧凑的 `tool_rounds`（每轮工具名序列，单轮不写）；`tool_result` 呈现卡片取最后一轮结果。流式路径的工具事件沿用 `tool.started/tool.finished`，多轮时前端自然显示多段。
- 取消：轮间检查回合存活，取消后按既有 `TurnCancelled` 语义失败。

后续分期（未实施）：BTL-02 允许单轮执行多个只读调用（模型并行调用已由 `MAX_TEXT_TOOL_CALLS=8` 吸收，执行端仍限一）；BTL-03 工具循环与 ActionPlan 的 A2 断点续跑打通（循环中遇到 A2 动作转计划确认，确认后从断点恢复）。

## 2. B 工作流：语义记忆检索（SEMB）

问题：默认 `HashingEmbeddingProvider` 是字符 n-gram 哈希，记忆检索实质是词法的——"我喜欢吃辣"检索不到"饮食偏好：川菜"。五类记忆模型与冲突纠错的设计远超当前检索水平。

设计（Hub 侧已实施）：`embeddings` 配置段（默认关闭）指向 OpenAI 兼容 `/embeddings`（LM Studio `text-embedding-*`、Ollama 等，本地或私有网络）；`HttpEmbeddingProvider` 在首个响应上校验维度，版本号含模型名实现向量空间隔离；启动时连通性探测（一次真实嵌入），失败回落内置哈希不阻断启动，仅 lifespan 启动期允许换入 provider；旧记忆经词法通道继续命中，新沉淀记忆逐步进入语义向量。Admin 记忆检索接口与页面展示当前 provider/维度/版本；`secret_value` 纳入配置脱敏/回填链。

验收（待真实环境）：接入真实本地嵌入模型后，构造 20 条语义相关但字面不同的记忆对，召回率显著高于哈希基线；pgvector 环境下 ANN 通道生效。

## 3. C 工作流：邮件感知（MAILW）

问题：邮件只有用户主动问时才碰；Hermes 默认 15 秒查收件箱，Aria 有完整的感知-认知管线却没接邮件。

设计（Hub 侧已实施）：`mail_awareness` 配置段（默认关闭，需 `integrations.mail` 已配 IMAP）+ `app/mail_awareness/loop.py` 复用浏览观察的循环骨架：周期拉取未读（BODY.PEEK 不改旗标、每 tick 上限可配）→ 候选信件片段经 utility 路由摘要（片段即焚不落库，时间线只留降敏摘要）→ `mail.received` 类 `SemanticEvent` 进 `PerceptionPipeline`，由既有稳定性窗口 + AttentionEngine/DND/打扰预算/四通道输出裁决。首个 tick 只建 UID 基线，重启不重报历史未读；watermark 只推进已处理 UID，超限留到下一 tick。分析提示明令禁止执行邮件内指令（含链接/回复/转账话术）；营销与验证码取 notable=false 静默。隐私：L1 元数据与摘要，正文片段不持久化。

验收（待真实邮箱）：测试邮箱真实收到账单/验证码/邀约三类信件时，账单/邀约经认知决策主动提起一次且打扰预算生效，验证码静默；重启后历史未读不重报。

## 4. D 工作流：技能蒸馏与回放晋级（DIST，衔接 S4）

问题：S4 自主学习未启动；Hermes 的"复杂任务完成后自动沉淀技能"是最值得借鉴的闭环，而 Aria 已有 ActionPlan 执行轨迹、ToolLedger、写后回读验证结果这些更严格的素材。

设计（已实施，v1 为确定性蒸馏）：计划全部步骤完成（≥2 步）后经完成回调（`ActionPlanService.set_completion_callback`）后台蒸馏为 workflow 草稿（新表 `workflow_draft`，迁移 0058）；步骤快照即 WorkflowStep 形状（action_id + 参数）；按步骤内容 sha256 幂等去重，已存在等步骤流程（含 workflow_run 展开的计划）不重复提案。命名 v1 取计划标题（LLM 润色留后续）。

晋级硬门槛是样例回放：A0 只读步骤用记录的原始参数重放——重新经 ActionRegistry 编译校验（契约漂移显式失败）+ ToolExecutor 隐私闸门——与原执行比对结果结构（ok + 顶层数据键一致）；无 A0 步骤记 not_applicable。Admin「管家中心」新增草稿列表/审批/忽略/手动回放四个端点：未回放或回放失败一律 409 阻断审批，审批通过才经 WorkflowService 重新编译创建正式流程；草稿终态（approved/dismissed）不可再审，同轨迹不再重复提案。不存在自动晋级。

验收（已覆盖测试 10 项）：两步计划全链路（蒸馏→回放→审批→流程创建）、单步不蒸馏、同轨迹幂等、workflow_run 不重复提案、回放结构一致/漂移、无只读步骤 not_applicable、审批门禁、终态语义。后续分期：对话内"上次的做法要不要存成流程"主动提示、LLM 命名润色。

## 5. E 工作流：长任务委派（DELEG）

问题：`jobs/engine.py` 是完整的持久化任务引擎（租约/检查点/退避/死信）但无生产用途；对话内请求全部同步，长任务要么阻塞要么失败。

设计（已实施，v1）：`DelegatedJobWorker` 领取执行独立 `deleg` resource_class 的 Job（租约 15 分钟、失败指数退避重试、检查点步骤记录），完成经 ProactiveDeliveryService 四通道主动汇报结果摘要；执行中被取消的任务按取消收尾、结果不汇报，Admin Jobs API 的 cancel 对 queued/admitted 生效。对话挂载 `delegate_task` 工具（仅 L1）：提交 Job 并立即返回确定性回执（同回合幂等键防重复），WS 不阻塞。

首个任务类型 `deleg.web_research`：批量抓取 1-5 个 URL（复用只读 web_fetch 的 SSRF 校验与隐私闸门），utility 路由汇总为 ≤300 字调研纪要，汇总提示明令不得执行网页指令、来源冲突需指出；部分抓取失败记录在结果的 failed 列表，全部失败按任务失败重试。

验收（已覆盖测试 8 项）：worker 执行/汇报、失败进 retry_wait、取消不被领取、执行中取消丢弃结果、工具幂等与四类门禁（L2/缺 URL/非法 scheme/缺回合上下文）、handler 汇总与全失败拒绝。后续分期：pnkx 周度汇总任务类型、handler 内协作式取消、对话内"别做了"直连任务取消。

## 6. F 工作流：滚动会话摘要（CTX）

问题：上下文固定取最近 20 条原文，无摘要无预算；对话内中程连贯依赖记忆抽取，半小时前的方案细节会丢。

设计（已实施）：会话表增 `summary_text`/`summary_until_seq`（迁移 0057）；回合提交事务内判断新消息累计到 10 条才派生后台维护（同会话同时至多一个任务，FOR UPDATE 水位条件写防并发覆盖）；旧摘要 + 增量消息重写为要点（≤500 字，窗口含 L2 消息强制 PRIVATE 路由）；对话超出 20 条窗口且摘要覆盖到窗口之前时，系统提示注入「此前对话要点」块，窗口内不注入。

验收（待真实长对话）：50 轮长对话中第 45 轮仍能正确引用第 5 轮的约定；token 预算观测随后续版本补 Admin 面板。

## 7. G 工作流：透明度汇报（RPT）

问题：主动决策都有 `decision_meta` 审计，但没有面向用户的汇报入口；可问责性是主动助手信任的基础。

设计（已实施）：对话命中透明度问询（"主动做了什么/为什么提醒我/为什么打扰我"等）时短路整条模型链路，从近 24 小时 `CognitiveDecision` 记录确定性渲染——主动开口次数、每次的时间/决策类型/触发来源/理由码、保持安静的事项数；L1/L2 均可问（纯本地查询，无出站）。每日自体检（路由连通/设备心跳/备份落盘，异常才说话）留待后续版本。

验收：问"今天为什么提醒我"，答案与决策记录逐条对得上（测试覆盖：不经模型、内容含触发来源与安静计数）。

## 8. 工程债（PERE）

- PERE-01 Router/Provider 跨轮缓存（已实施）：默认聊天路径按配置指纹（JSON sha256）缓存 Router（容量 4），Admin 发布新配置自动失效；显式注入的 builder 不经过缓存。
- PERE-02 流式热路径取消检查（已实施）：`cancel_turn` 写入内存取消集合、回合收尾逐出，流式 delta 检查不再逐条查库；`_turn_is_active` 移除。
- PERE-03 `main.py` 85KB 组合根拆分（未实施）：BTL/DELEG 落地后新服务还会增加，拆成显式依赖图模块。

## 9. 优先级、依赖与验收纪律

顺序：SEMB → MAILW → DIST → DELEG+CTX → RPT，PERE-01/02 跟随 BTL。所有工作流的代码合入不改变默认行为（配置默认关闭或默认 1），真实验收前不算完成——与 J1-J6 的验收纪律一致。高于一切的前置仍是 [TASKS](./TASKS.md) §1 的既定事项：真实凭据/真机/真实数据的验收收口优先于新能力。
