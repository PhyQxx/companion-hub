## 1. 阅读顺序

第一次接触项目时，按下面顺序阅读即可：

1. 根目录 [`README.md`](../README.md)：项目是什么、当前做到哪里、如何启动；
2. [`01-需求分析.md`](./01-需求分析.md)：产品目标、功能需求、非功能需求与范围；
3. [`02-功能设计.md`](./02-功能设计.md)：系统总体架构和模块关系；
4. [`03-开发规划.md`](./03-开发规划.md)：阶段、质量闸门与实现顺序；
5. 再按具体主题进入下面的专项设计；
6. `15～29` 中的阶段记录主要用于理解“当时实现了什么”，不应覆盖 Active 设计文档中的当前规则；当前阶段记录优先看 `32`（P5 使用期）、`33`（P6 语音化）与 `35`（M3A 地图/天气）。

当前执行任务以根目录 [`TASKS.md`](../TASKS.md) 为准。

## 2. 文档类型

| 类型 | 含义 | 使用规则 |
|---|---|---|
| **Active** | 当前设计真源 | 新开发和修改优先遵循 |
| **ADR** | 已接受的架构决策 | 除非新 ADR 明确替代，否则持续有效 |
| **Phase Record** | 某阶段实现/验收记录 | 用于追溯，不作为新功能的唯一设计依据 |
| **Current Record** | 当前阶段进度与问题记录 | 可持续更新，但不承载长期架构定义 |

## 5. 已发现并收敛的重复

### 5.1 总体架构重复

`02` 是总体架构真源；`04` 中的总体架构图只保留为视觉示意；`11/14` 分别负责数据/API 通则和 I/O 契约，不再由 `02` 重复定义完整字段。

### 5.2 前端阶段文档重复

`26` 记录技术决策；`27/28` 只记录迁移验收；新的 UI/管理设计应回写 `05/06/20` 等 Active 文档，不继续堆进验收记录。

### 5.3 记忆文档重复

`21～25` 冻结为 Memory v1 的历史实现基线；`30` 负责多主体长期记忆；`31` 负责时间线与历史回溯。`02 §3.6` 仅保留高层架构和链接。

### 5.4 配置生命周期重复

配置不再统一采用一种发布模型。当前规则：

- 模型 / 路由 / 日志运行配置：**保存即生效**，数据库 revision 仅作为内部审计实现；
- Persona：**草稿 → 发布 → 回滚**；
- Theme / 主动规则等未来配置：按风险选择版本发布，不套用模型配置 UI 语义。

## 7. 文档维护规则

1. 新的长期规则优先修改 Active 文档，不在 Phase Record 里追加第二套定义；
2. 阶段验收记录发布后原则上冻结，只允许勘误和指向当前设计的注释；
3. 新文档创建前先检查本索引，能并入现有 Active 文档就不新增；
4. `README.md` 不复制完整设计，只保留入口、运行方式和高层状态；
5. `TASKS.md` 只维护执行状态，不承担详细架构设计；
6. 发生设计替代时，必须在本索引记录“新真源”和被替代文档；
7. 数据库真实结构以 Alembic migration 为最终事实，API/Schema 以代码和 `11/14` 的契约规则为准。
