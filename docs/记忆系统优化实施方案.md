## 0. 一页速览（给最忙的人）

小助手现在会"记事情"了：聊天里说过的家庭、生日、习惯会被整理成一条条记忆，
下次聊天时自动想起来。分级记忆 v1 已上线，但压测和代码核查发现了 **2 个正确性问题、
4 个质量/性能问题、若干体验项**：

| 编号 | 严重度 | 一句话说明 | 不修会怎样 |
|---|---|---|---|
| A1 | ★★★ 正确性 | 查重时只翻"最重要的前500本"，翻不到的重复书会再买一本 | 记忆库越大，重复记忆越多 |
| A2 | ★★★ 正确性 | 换了新的"记忆索引方式"后，旧记忆没重新贴标签，索引静默失效 | 一瞬间所有记忆只能靠"翻页"找，找不准 |
| B1 | ★★ 性能 | 找记忆时没有目录页，每次一页页翻全库 | 记忆到百万条时，每轮对话明显变慢 |
| B2 | ★★ 质量 | 记忆系统从来没有"考试"，所有找人的标准都是拍脑袋定的 | 无法回答"记忆找得准不准"，调参靠猜 |
| B3 | ★★ 质量 | 新上线的"AI 判断重要程度"还不知道真实模型判得准不准 | 可能大量漏判或误判为"核心" |
| B4 | ★ 质量 | 生日、纪念日这类"会到期的事实"不会自动提醒召回 | 到了日子助手也想不起来 |
| C1~C6 | 体验 | 长消息断点重提、归因增强、质量仪表盘等 | 见第 6 章 |

建议分三批实施：**第一批修 A1+A2（正确性，约 4~6 人日）**；
**第二批做 B1+B2（索引+考试，约 6~8 人日）**；**第三批 B3+B4 与体验项（按真实验收节奏）**。

## 1. 背景与目标

分级长期记忆 v1 已交付：六档强度、宽进提取、按使用晋级/自然遗忘降级、热层召回、
管理页治理。本轮基于代码核查与已登记的容量基线，形成一份可落地的优化方案，目标是：

1. **正确**：记忆不重复、不丢失（修 A1/A2）；
2. **快**：库到十万、百万条时，每轮对话找记忆仍然很快（修 B1）；
3. **可度量**：找得准不准有数字、有考试，不再凭感觉调参（修 B2/B3）；
4. **贴心**：生日这类日子临近时能主动想起（修 B4）。

不在本轮范围内：真实环境验收、生产部署（仍按项目验收惯例单独立项）。

## 2. 现状架构（先看懂系统，再看问题）

用一个**图书馆**来类比整个记忆系统。

### 2.1 图 A：一条记忆是怎么形成的（写入线）

```
 你说了一句话（聊天消息）
        │
        ▼
 ┌──────────────────┐   "提取员"（AI）阅读后，
 │  提取：拆成原子事实 │   拆成一条条独立的小事实：
 │  （异步后台进行）   │   「女儿叫小晴」「小晴生日5月6日」「住在青岛」
 └──────────────────┘   并给每条打三个分：重要程度 / 可信度 / 初始等级
        │
        ▼
 ┌──────────────────┐   "编目员"查重：
 │  沉淀判定          │   · 以前记过一样的 → 只加一个"佐证"标签，不新建
 │  建新 / 补佐证 / 冲突│   · 说的不一样 → 挂起等你裁决谁对
 └──────────────────┘   · 全新事实 → 正式入库
        │
        ▼
 ┌──────────────────┐   入库登记：
 │  写入记忆库         │   正文 + 来源（哪句话说的）+ 分类号(fact_key)
 └──────────────────┘   + 等级（默认中级，AI/管理员可建议更高）
                          + 一张"等级变更登记单"（审计，谁改的都能查）
```

要点：**每条记忆都能回答"你凭什么记这个"**（来源可回指）；说错的话可以纠错
（旧版本保留、新版本替代）；删除有台账，恢复备份后不会"死而复生"。

### 2.2 图 B：想一件事时是怎么"想起"的（读取线）

```
 你问："我女儿生日是哪天？"
        │
        ▼
 ┌──────────────────┐   门口查票（硬性过滤，一票否决）：
 │  候选池            │   只看你的记忆（别人的不行）、只看没作废没挂起的、
 └──────────────────┘   隐私等级够格的、还在有效期内的
        │
        ▼
 ┌──────────────────┐   三路并进找线索：
 │  找线索            │   ① 语义路：意思接近的（电脑算"向量相似度"）
 │                    │   ② 关键字路：字面对得上的（"生日"两个字）
 │                    │   ③ 精确槽位：固定栏目直接查（生日栏、身高栏）
 └──────────────────┘      （冷存档的记忆也能被精确槽位找到）
        │
        ▼
 ┌──────────────────┐   排队入场：
 │  打分与配额        │   总分 = 0.55×意思接近 + 0.25×重要程度
 │                    │        + 0.15×等级 + 置顶/主体加成
 └──────────────────┘   每类最多占几个席位（防止一类刷屏），取前 8 条
        │
        ▼
 ┌──────────────────┐   两种用途分开：
 │  注入 / 证据       │   当"聊天背景"：宽松，8 条都给你看
 └──────────────────┘   当"确定记得的证据"：严格，必须真对得上才算数
        │
        ▼
 助手回答后，后台核对：这条记忆真的被答案用上了吗？
 用上了才记 1 次"有效使用" → 累计够了才升级（读本身不加分）
```

要点：**相关 > 等级 > 重要程度**。等级只加分，不能让一条无关的"核心记忆"
把真正能回答问题的低等级记忆挤出场。

### 2.3 图 C：记忆的保鲜与遗忘（生命周期）

```
 新记忆 ──默认──► 中级 ──30天没用──► 一般 ──60天没用──► 不重要 ──180天──► 冷存档
   │               │
   │ AI/管理员可建议 │ 有效使用攒分：
   │ 直接定为       │  30天≥6分且≥3天 → 重要
   │ 重要/核心      │  90天≥18分且≥8天且停留14天 → 核心
   ▼               ▼
 重要 ──90天没用──► 回中级      核心 ──180天没用──► 重要
 （自然遗忘只降级，永不删除；冷存档仍可被精确查找唤醒）
```

要点：遗忘像冰箱保鲜期，只改"新鲜度"不改内容；用户可以给关键记忆"钉住"（固定等级）。

### 2.4 名词小卡片（非技术人员版）

| 词 | 意思 |
|---|---|
| 向量 / 嵌入 | 把一句话变成一串数字，意思接近的话数字也接近，电脑靠比较数字找"意思相近" |
| 嵌入模型版本 | 生成这串数字的"算法版本"。换了版本，旧数字就和新算法对不上号 |
| fact_key（事实槽位） | 像人事档案的固定栏目：生日栏、身高栏。问"生日"直接翻这一栏，不用全文找 |
| 热层 | 常用记忆的"前台书架"（核心/重要/中级），冷层在后库，需要时调阅 |
| 索引 | 书前的目录页。有目录翻页定位，没目录只能一页页扫全书 |
| 去重 / 沉淀 | 新事实入库前查"以前记过没"：记过只加佐证，矛盾挂起，全新才建 |
| 审计行 | 一张不可改的登记单，记录"谁在什么时候把等级从 A 改到 B、为什么" |

## 4. 第一批（P0）：修正确性 —— A1 + A2

### 4.1 A1：查重窗口漏判

**现象（通俗）**：编目员查重时，不去全书找"这本书有没有"，而是只翻**按热门程度排好的
前 500 本**。一本冷门的旧书如果和新书是同一本，编目员翻不到它，就当成新书又买一本。
时间久了，同一事实出现好几条重复记忆。

**为什么现在会这样**：查重函数"找相似记忆"时没有提供查询词，于是走了通用候选池的
"按重要性排前 500 条"兜底路径。重要性低的记忆（很多正确记忆重要性并不高）不进窗口。

**技术细节**（供开发）
- `find_similar`（store.py）当前：嵌入当前候选内容 → `retrieval_candidates(limit=500)`
  （无 query_text → 按 importance 排序截 500）→ 进程内余弦比对 → ≥0.85 判支持、
  ≥0.60 判冲突（consolidation_core.py）。
- 影响面：所有入库路径（聊天提取、补录技能、管理端手动添加）的去重与冲突判定。

**实施方案（分步）**
1. 新增仓储方法 `similar_candidates`：按"同用户 + 同主体 + 同类型"圈定范围后，
   **PG 用 pgvector 按向量相似度取前 N**（复用检索已有的 `vector_recall` 通道，
   不限制等级与状态范围，但保留 active/挂起等调用方指定状态）；
   **SQLite 无 ANN**，用"同类型同主体 + 按最近新增优先"窗口（时间衰减下最近的最可能重复），
   窗口大小随库量自适应（如 min(2000, 总量)），并记录回退窗口命中率日志。
2. `find_similar` 改走 `similar_candidates`，比对与阈值逻辑不变（0.85/0.60 暂不动，
   留给第二批考试校准）。
3. 增加"规模断言"测试：合成 ≥600 条同类型记忆（重要性与新事实交错），构造一条
   与**重要性排序尾部**记忆几乎相同的候选，断言判为 supported 而不是 created
   （该用例在现实现下必失败，作为守门验证）。
4. 无表结构变化，不需要数据库迁移；两库（SQLite/PG）行为对齐测试。

**验收标准**
- 新守门用例在 SQLite 与 PG 均通过；stash 修复后按预期失败（守门惯例）。
- 现有沉淀/来源围栏/补录技能回归零新增失败。
- PG 路径用 EXPLAIN 确认走向量索引，不走全表扫描。

**风险与回退**：窗口策略改动只影响"查重读什么"，判定阈值不动；出问题可一键切回
旧窗口实现（保留旧路径为回退分支）。工作量估计 **2~3 人日**。

### 4.2 A2：嵌入换版无回填，向量检索会整库静默失效

**现象（通俗）**：记忆的"语义索引"依赖一种编号算法（嵌入模型）。系统启动时会自动
探测"有没有更好的编号算法"，有就切换。但切换后，**旧记忆还是旧编号**，新检索只认
新编号——于是整座图书馆的语义检索瞬间失灵，而且**没有任何报警**，只剩关键字
翻页这一条笨办法。

**为什么危险**：这是静默故障——表面上一切正常，实际"意思接近"这条路全断了，
只发生一次（换算法那次启动），极难被发现。

**技术细节**（供开发）
- 检索相似度在版本不匹配时按 0 处理（retrieval.py `similarity_of`）；
  `vector_recall`、`find_similar` 均按 embedding_version 过滤。
- `set_embedding_provider` 允许启动期热切换（SEMB 探测成功即换）。
- 全仓 grep 确认**无任何重嵌入/回填任务**。

**实施方案（分步）**
1. **切换前置门**：启动期切换嵌入 provider 前先统计"版本不匹配行数"；
   若 >0，本次启动**暂不切换**（维持旧 provider），并把数量写入健康接口与管理页
   （新增一个只读字段，如 `embedding_stale_rows`）。语义：换算法变成显式的、
   有准备的动作，不再是一瞬间的静默行为。
2. **回填任务**：新增后台维护任务（复用现有 Job 体系与 worker 身份审计）：
   分批（如每批 100 条）把版本不匹配的行重算嵌入并原子更新
   （embedding + dimension + version 同事务更新）；每批记 checkpoint，可断点续跑；
   受预算开关约束，可暂停/恢复。
3. **切换流程**（运维手册一页）：跑评估样本（抽 200 条旧记忆对比新旧算法的
   检索命中）→ 确认质量不退化 → 开启切换开关 → 回填任务跑到 0 → 健康页归零确认。
4. **观测**：管理页显示当前 provider 版本、不匹配行数、回填进度。

**验收标准**
- 有 5 条旧版本记忆 + 开关关闭时：启动不切换、健康页显示 stale=5；回填任务跑完后
  stale=0，向量检索命中恢复。
- 回填中断（模拟杀进程）后重启能续跑，不重复计算已完成的批。
- 回填期间检索、入库不阻塞不报错（新旧版本行并存，各自按既有隔离逻辑工作）。

**风险与回退**：不切换就不影响现状；回填是逐行原子更新，中断无半成品。
保留旧向量不备份——回填用同一内容重算，可随时重跑。工作量估计 **2~3 人日**
（A1+A2 同批共享环境搭建，合计 **4~6 人日**）。

## 5. 第二批（P1）：修性能与度量 —— B1 + B2

### 5.1 B1：给记忆库装"目录页"（词法索引）

**现象（通俗）**：现在找记忆像在一本没有目录的书里找词——把要找的词在**全库每页**
都比对一遍。记忆到百万条时，一次查找要翻 2.43 秒（已有压测数据），对话会明显变慢。

**技术细节**（供开发）
- 热层排序对每行做最多 24 个 `content LIKE %token%`（store.py 热层排序段）；
  词法比对用字符一元+二元 n-gram 余弦（similarity.py）。
- 需要 DDL 变更 → 按项目门禁：新迁移 `0073`、双库（SQLite/PG）隔离迁移验证、
  `mapped_ddl_sha256` 等架构快照同步登记。

**实施方案（分步）**
1. SQLite：建 FTS5 外部内容表（`memory_fts`，content 指向 memory 表）+ 三触发器
   （增/改/删同步）。查询路径：词命中排序改走 `MATCH`，取近邻集合后仍进入现有
   打分重排（打分公式不变，只换"找得到"的速度）。
2. PG：`content` 加生成列 `tsvector`（含中文二元分词预处理，与 n-gram 口径一致）
   + GIN 索引；同样只替换召回定位，不动重排。
3. 兼容开关 `ARIA_MEMORY_LEXICAL_INDEX`（默认开，置 0 走旧 LIKE 路径），
   灰度与回退用。
4. 一致性测试：同一批查询，开关开/关两路的召回集合一致（索引只改速度不改结果）；
   触发器一致性测试（改/删记忆后索引同步）。
5. 复测容量基线：1万/10万/100万 三档与旧数字并排记录进 docs/baselines。

**验收标准**：百万级词命中从 ~2.43 秒降到百毫秒量级（SQLite 目标 p95 < 300ms，
以实测为准并如实记录，不预设达标）；两库召回集合零差；架构门禁与快照全绿。
工作量估计 **3~4 人日**。

### 5.2 B2：给记忆系统"开考试"（评测集与影子对比）

**现象（通俗）**：记忆系统的所有"找人的门槛"（多像才算同一条、多像才算记得准）
都是开发时拍的数字，从来没有一套标准考题来验证。没法回答"记忆找得准不准"。

**技术细节**（供开发）
- 现有检索策略版本 hybrid-lifecycle-v7；04B 登记的"生产影子评测/标注集"未落地。
- 已有离线对照测试（新旧检索策略、冷层精确命中）可复用为考题骨架。

**实施方案（分步）**
1. **建考题集**：80~120 条标注用例（合成数据，不含真实隐私），覆盖：
   冷层精确命中、跨会话指代（"我女儿生日"→先前对话）、干扰项（无关核心记忆在场）、
   盘点型问题、多事实一句话、高隐私边界。
2. **跑分脚本**：离线批量执行 retrieve + grounded_hits，产出 recall@8、
   grounded 准确率/误报率、p95 延迟；结果 JSON 存 docs/baselines（沿用现有惯例）。
3. **影子对比**：同一考题集跑"当前策略 vs 候选策略"（改阈值/配额后的变体），
   差异报告人工审阅后决定是否切换；策略版本号随之 bump。
4. **考题进 CI**：考题集作为回归测试常驻，任何打分/召回改动必须附新旧跑分对比。

**验收标准**：考题集两库跑通并落基线 JSON；至少完成一次真实调参决策
（如 grounded 词法阈值）有前后对比数据支撑。工作量估计 **3~4 人日**。

## 10. 术语表（技术版补充）

| 术语 | 定义 |

**B1（词法索引）**：迁移 `0073_memory_lexical_index`——SQLite 建 FTS5 独立表
`memory_lex(grams)`（rowid=memory.id，n-gram 口径与 app.memory.similarity 一致，
Python 批量回填）；PG 建 pg_trgm GIN 索引（`ix_memory_content_trgm`，扩展保留）。
store 写入/删除同事务维护 FTS 行（add/edit/_purge_memory_ids 三个收口点，
事务内复用当前会话探测表存在性，迁移前库自动跳过）。查询改两段式：命中行经索引预筛
（SQLite FTS5 MATCH / PG OR-LIKE+trigram BitmapOr）后按原排序取满名额，不足再按
(importance, id) 补零命中行——与旧单趟排序**严格等价**（命中行排满名额时补齐段不执行，
不存在排序缺口），等价性由 `tests/test_memory_lexical_index.py` 双库锁死（开关开/关
产出完全相同的候选 ID 序列与端到端命中）。开关 `ARIA_MEMORY_LEXICAL_INDEX` 默认开。
测试夹具 `open_storage` 镜像建 FTS 表使测试覆盖真实路径。

**容量复测（诚实结论：本方案 §5.1 的"百万级 p95<300ms"验收目标未达成）**：
SQLite 合成 100万行双场景——稀疏命中（真实语义：查特定事实）2223→**1826ms（-18%）**；
密命中（病态：查询词命中全部行）2859→3554ms（+25%，纯 JOIN 开销）。10万行：
稀疏 238→226ms。**下限由补齐段的 importance 全量排序主导**（任何有界候选池排序设计
都有此地板），索引只省预筛；要达百毫秒需 importance 复合索引或按用户候选分页，
登记为 B1 后续增强。当前真实规模（个人库 ≤ 万条、现网 56 条）延迟 50ms 级，
实际部署（PG）另有 trigram 索引收益。见
[基准 JSON](./baselines/memory-lexical-index-bench.json)。
