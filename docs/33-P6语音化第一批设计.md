## 1. P6 入口复核（ADR-018 预留复核点）

ADR-018 在 P6 入口要求复核「桥接 Open-LLM-VTuber vs 自建渲染/语音」。复核结论：**维持 B 方案**。

- **语音链路自建**（本批落地）：docs/03 M2.1~2.5 定义的 `/ws/voice`、VAD、ASR、TTS 全部在中枢内实现。理由：语音闭环与 ChatService 回合、隐私路由（L1 云端 / L2 强制本地）、打断取消、记忆沉淀深度耦合，交给 OLV 进程会绕开中枢的隐私闸门与决策元数据——这与 P5 刚验证过的 L2 隔离直接冲突。
- **OLV 仅作 Live2D/桌宠壳**（P6 后续批次）：形象渲染、口型驱动、Tauri 桌宠形态复用 OLV 与 `integrations/open_llm_vtuber/` 桥接，不深度 fork（ADR-018 既定策略）。触发条件：语音闭环（M2 验收指标）达标后再进入，避免形象层分散语音核心验证——与 M1/M2 的既有排期原则一致。
- **C 方案（全量自建 pixi 渲染）继续后置**：等 OLV 桥接在桌宠场景暴露维护成本上限后再评估。

## 3. Batch A 设计

### 3.1 通道契约（/ws/voice）

- 鉴权：与 `/ws/chat` 相同的 `authenticate` 帧（AuthService 会话）。
- 握手 `voice.hello`：`{conversation_id, privacy_level, format: "pcm_s16le", sample_rate: 16000, channels: 1}`。Batch A 只接受 PCM16/16k/单声道；不匹配返回 `voice.format_unsupported` 后关闭。
- 上行：
  - 二进制帧 = PCM16 音频；
  - `utterance.begin` / `utterance.end`：PTT 显式边界（与 VAD 自动断句二选一，显式优先）；
  - `interrupt`：客户端主动打断（调试/按键）。
- 下行：
  - `voice.transcript`：ASR 结果（含 `is_final`）；
  - `voice.sentence`：即将合成的一句话（`index`、`mime`）；
  - 二进制帧 = 该句的 TTS 音频分片（与最近一个 `voice.sentence` 对应）；
  - `voice.sentence.end`：一句音频结束（客户端可衔接播放）；
  - `turn.accepted/reply.committed/turn.cancelled`：复用聊天回合生命周期事件语义；
  - `voice.interrupted`：服务端检测打断，附 `interrupted_at_seq`（打断点）。
- 错误：`voice.asr_unavailable`、`voice.tts_unavailable`（L2 无本地 TTS 时，回合仍走文字）。

### 3.2 组件与协议（server/app/voice/）

```
VoiceActivityDetector（协议） EnergyVad：audioop RMS 阈值 + hangover 尾帧
SpeechRecognizer（协议）      MiMoAsrRecognizer：WAV 包装 + base64 上云，整段转写
SpeechSynthesizer（协议）     synthesize(text, privacy) -> AsyncIterator[bytes]
                             MiMoTtsSynthesizer：pcm16 直出（24kHz），主通道
                             EdgeTtsSynthesizer：mp3 分片，免费兜底
TtsProviderChain              逐句选择提供方：首块成功才选定，失败冷却 60s，
                             L2 只允许 runs_local=True 的提供方
SentenceBuffer                流式 delta 按强标点切句，60 字上限强制 flush
```

- **提供方并存与故障转移**：MiMo 为主、edge-tts 为备。逐句独立选择：主通道首块前失败或空流时无感切换备选，并进入 60 秒冷却；中途断流则该句音频跳过、回合继续（文字不丢）。`voice.sentence` 事件携带实际提供方的 `mime` / `sample_rate` / `provider`，客户端逐句自适应格式。
- **隐私**：上行语音转写按回合 `privacy_level` 走既有 ChatService 闸门（L2 强制本地 LLM）；MiMo ASR/TTS 与 edge-tts 均为云端——L2 音频禁止交给云端识别器（`voice.asr_unavailable: local_asr_required`），L2 回复文本禁止出站合成（提供方链只保留 `runs_local=True`，当前没有则降级纯文字并下行告知原因）。
- **配置中心化**：`HubConfig.voice` 节（`asr` 单选 + `tts` 有序链，密钥走 `secret_value`/`secret_ref` 双模式）进数据库配置中心，后台「模型与路由 → 语音」页可视化管理，`PUT /admin/config/current` 保存即生效；`ConfigVoiceSource` 每条话语解析一次提供方，管理端改配置无需重启。MiMo API Key 直接在后台填写，不落 .env.local。
- **句级切分**：LLM 流式 delta 累积，遇 `。！？!?\n` 或超过 60 字 flush；首句立即送 TTS（docs/02 §3.2 全链路流式）。
- **打断**：回合进行中持续接收上行音频；单帧人声能量（无 hangover 的高灵敏判定）→ `ChatService.cancel_turn(generation_id)` + 中止 TTS 任务 + 发 `voice.interrupted`。
- **降级**：当前配置没有可解析的 ASR → `voice.asr_unavailable: not_configured`；TTS 链为空或没有可用 provider → 降级文字。若配置了 edge-tts，可作为 L0/L1 兜底；L2 只允许 `runs_local=True` 的本地 TTS。LLM 路由耗尽 → 沿用聊天 WS 的 `turn.failed` 语义。

### 3.3 MiMo 接入要点

- ASR（`mimo-v2.5-asr`）：OpenAI 兼容 `https://api.xiaomimimo.com/v1/chat/completions`，`input_audio.data` 仅收 wav/mp3 base64（≤10MB）——服务端把 PCM16/16k 包 WAV 头再上传；语言由 `HubConfig.voice.asr.language` 提供（默认 auto）。
- TTS（`mimo-v2.5-tts`）：`messages` 的 assistant 内容为待合成文本，`audio={"format":"pcm16","voice":"冰糖"}`，SSE 流式返回 `delta.audio.data`（base64 PCM16 24kHz 单声道）；音色由 `HubConfig.voice.tts[*].voice` 提供，预置：冰糖/茉莉（中文女）、苏打/白桦（中文男）、Mia/Chloe/Milo/Dean（英文）。
- 计费：TTS 限时免费，ASR ¥0.5/小时。

### 3.4 依赖

新增运行时依赖 `edge-tts`（纯 asyncio）与 `httpx`（原为 litellm 传递依赖，转正显式声明）。faster-whisper/silero-vad/onnxruntime 留到 Batch B 作 L2 本地路径按需引入。

当前 `EnergyVad` 使用 Python 标准库 `audioop`，本轮 pytest 已出现“Python 3.13 将移除 audioop”的弃用警告，因此 Batch B 的 silero-vad 替换同时属于兼容性收口，不只是识别质量优化。

## 6. M2 真机延迟诊断（2026-08-21）

`make llm-first-token-bench` 使用与语音窗口相近的 8 条短上下文，直接流式请求运行配置中的 dialogue 端点，不创建会话/消息，不输出密钥。首轮结果：

| 端点 | 首 token | 总耗时 | 结果 |
|---|---:|---:|---|
| `sensenova_deepseek-v4-flash` | 1.623s | 1.635s | 成功 |
| `sensenova_6.8-flash-lite` | — | 20s | 超时 |
| `glm-4.7-flash` | — | 0.226s | RateLimit |
| `glm-5.3` | — | 0.196s | RateLimit |
| `sensenova_glm-5.2` | — | 0.189s | RateLimit |

结论：当前可用组合的理想分段下限约为 0.832s ASR + 1.623s LLM + 0.846s TTS = 3.301s，已高于 1.8s 验收线。不应通过放宽统计口径“达标”；要保留原指标，需同时改为增量/流式 ASR 和独立的低延迟语音 LLM 路由。
